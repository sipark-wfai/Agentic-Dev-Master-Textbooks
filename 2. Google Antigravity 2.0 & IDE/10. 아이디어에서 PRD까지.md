# 10. 아이디어에서 PRD까지 — 에이전트 친화적 기획서 작성 완벽 가이드

> **학습 목표**
> - 에이전트 친화적 PRD(Product Requirements Document)의 특징을 이해한다
> - /ask 명령어로 아이디어를 구조화된 PRD로 발전시키는 과정을 실습한다
> - PRD의 필수 구성 요소를 모두 갖춘 문서를 작성할 수 있다
> - BoardHub 멀티 게시판 허브의 완전한 PRD를 완성한다
> - PRD 품질 자가 검증 체크리스트 20항목을 통과한다

---

## 1. 에이전트 친화적 PRD란

### 1.1 일반 PRD vs 에이전트 친화적 PRD

**일반 PRD (전통 방식)**:
```
"사용자가 게시판을 이용할 수 있어야 합니다.
 게시글 작성, 수정, 삭제 기능이 필요합니다.
 댓글도 달 수 있어야 합니다.
 관리자 기능도 필요합니다."
```

이런 PRD를 에이전트에게 주면:
- "게시판"이 몇 종인지 모름
- 삭제가 물리적 삭제인지 소프트 딜리트인지 모름
- "관리자 기능"이 무엇인지 모름
- 기술 스택을 추측으로 선택

**에이전트 친화적 PRD**:
```
## FR-001 게시글 작성
- 대상: 인증된 사용자 (role: USER 이상)
- 입력: title(최대 200자), content(HTML, 최대 50,000자), boardType
- 갤러리 타입: image 파일 1~10개 필수 첨부
- 동영상 타입: video 파일 1개 필수 첨부
- 처리: content-filter 스킬로 금지어 검사
- 출력: { success: true, data: { postId, boardType, createdAt } }
- 오류: 400(유효성 실패), 401(비인증), 403(권한 없음)
```

에이전트가 이 PRD를 받으면 명확하게 구현할 수 있다.

### 1.2 에이전트 친화적 PRD의 5가지 특징

1. **기능 ID 체계**: 모든 기능에 FR-001, FR-002 형식의 고유 ID 부여
2. **입출력 명세**: 함수처럼 입력/출력/오류 코드가 명확
3. **수치화된 제약**: "많은 댓글" → "최대 1,000개/게시글"
4. **기술 스택 명시**: 에이전트가 추측하지 않아도 됨
5. **금지 사항 명시**: 절대 하지 말아야 할 것들

## 2. /ask로 아이디어 → PRD 구조화

### 2.1 단계별 브레인스토밍

아이디어가 있지만 PRD로 정리가 안 된 상태라면, /ask로 에이전트와 대화하며 구조화한다.

**Step 1: 아이디어 탐색**
```
/ask "커뮤니티 게시판 서비스를 만들려고 해.
      8가지 종류의 게시판(일반, 갤러리, 동영상, Q&A, 공지, FAQ, 비공개문의, 자유)을
      하나의 서비스에서 통합 관리하는 플랫폼이야.
      이 서비스의 핵심 가치 제안(Value Proposition)이 뭐가 좋을까?
      경쟁 서비스와 차별화 포인트도 분석해줘"
```

**Step 2: 사용자 역할 정의**
```
/ask "BoardHub 서비스의 사용자 역할을 정의해줘.
      각 역할의 권한 범위와 서로 다른 점을 테이블로 정리해줘"

에이전트 응답:
| 역할 | 가입 여부 | 글 작성 | 댓글 | 관리 기능 |
|------|---------|--------|------|---------|
| Guest | X | X | X | X |
| User | O | O | O | X |
| Moderator | O | O | O | 일부 |
| Admin | O | O | O | 전체 |
```

**Step 3: 기능 목록 추출**
```
/ask "BoardHub의 기능을 핵심/보조/선택적 기능으로 분류해서
      MoSCoW 방법론으로 우선순위를 정해줘
      (Must Have / Should Have / Could Have / Won't Have)"
```

**Step 4: 기술적 타당성 검토**
```
/ask "이 PRD에서 기술적으로 구현이 까다로운 부분은 어디야?
      SvelteKit + NestJS + PostgreSQL 스택에서 주의할 점을 알려줘"
```

## 3. PRD 필수 구성 요소

### 3.1 PRD 템플릿 구조

```markdown
# [서비스명] PRD v[버전]

## 1. 서비스 개요
  1.1 목적 및 배경
  1.2 핵심 가치 제안
  1.3 성공 지표 (KPI)

## 2. 범위 및 제외 항목
  2.1 포함 범위 (In-Scope)
  2.2 제외 항목 (Out-of-Scope)

## 3. 사용자 역할 및 권한
  (역할별 권한 테이블)

## 4. 기능 명세 (FR)
  4.x FR-xxx: 기능명 (기능별 상세 명세)

## 5. 비기능 요구사항 (NFR)
  5.1 성능
  5.2 보안
  5.3 가용성

## 6. 기술 스택
  (레이어별 기술 선택과 이유)

## 7. 금지 사항 (MUST NOT)
  (절대 해서는 안 되는 것들)

## 8. 용어 정의 (Glossary)
```

## 4. BoardHub 멀티 게시판 허브 전체 PRD

다음은 BoardHub 프로젝트의 완전한 PRD다:

```markdown
# BoardHub PRD v1.0
최종 수정: 2026-06-01

---

## 1. 서비스 개요

### 1.1 목적 및 배경
BoardHub는 대학 동아리, 커뮤니티, 소규모 기업이 다양한 용도의 게시판을 단일 플랫폼에서
통합 관리할 수 있는 서비스다. 기존에는 공지, 자료실, Q&A 등 용도마다 별도 솔루션을
사용하여 관리 비용이 높았다.

### 1.2 핵심 가치 제안
"하나의 플랫폼으로 모든 종류의 게시판을 통합 관리"

### 1.3 성공 지표 (KPI)
- 출시 3개월 내 회원 1,000명
- 일 게시글 200건 이상
- 월 활성 사용자 (MAU) 60% 이상
- 평균 응답 속도 200ms 이하

---

## 2. 범위

### 2.1 포함 범위
- 8종 게시판 운영 (일반, 갤러리, 동영상, Q&A, 공지, FAQ, 비공개문의, 자유)
- 회원 가입/로그인 (이메일 + 비밀번호)
- JWT 기반 인증 (Access + Refresh Token)
- 이미지 파일 업로드 (갤러리 게시판)
- 동영상 파일 업로드 (동영상 게시판)
- 댓글 및 대댓글
- 게시글 좋아요
- 관리자 대시보드

### 2.2 제외 항목
- SNS 소셜 로그인 (추후 v2.0에서 추가)
- 실시간 알림 (WebSocket) — v2.0
- 모바일 앱 — v2.0
- 다국어 지원 — v2.0

## 4. 기능 명세 (Functional Requirements)

### FR-001 회원 가입
- 대상: Guest
- 입력:
  - email: string (RFC 5321 형식, 최대 255자)
  - password: string (8~100자, 영문+숫자+특수문자 조합)
  - nickname: string (2~20자, 한글/영문/숫자)
- 처리:
  - 이메일 중복 확인
  - bcrypt rounds:12로 비밀번호 해싱
  - 가입 확인 이메일 발송 (기본 비활성)
- 출력: { success: true, data: { userId, email, nickname } }
- 오류:
  - 400: 유효성 검증 실패
  - 409: 이미 존재하는 이메일

### FR-002 로그인
- 대상: Guest
- 입력:
  - email: string
  - password: string
- 처리:
  - 비밀번호 bcrypt 검증
  - Access Token 발급 (유효기간: 15분)
  - Refresh Token 발급 (유효기간: 7일)
  - Refresh Token은 httpOnly 쿠키로 설정
- 출력: { success: true, data: { accessToken, user: UserDto } }
- 오류:
  - 401: 이메일 또는 비밀번호 불일치
  - 403: 비활성화된 계정

### FR-003 토큰 갱신 (Token Refresh)
- 대상: 인증된 사용자 (만료된 Access Token 포함)
- 입력: Refresh Token (쿠키에서 자동 추출)
- 처리:
  - Refresh Token 유효성 검증
  - 토큰 순환 갱신 (기존 Refresh Token 무효화 후 새 토큰 발급)
- 출력: { success: true, data: { accessToken } }
- 오류: 401 (Refresh Token 만료 또는 무효)

### FR-010 게시판 목록 조회
- 대상: 모든 사용자
- 입력: page(기본 1), limit(기본 20, 최대 100)
- 출력: { success: true, data: Board[], meta: PageMeta }
- Board 필드: id, name, type, description, postCount, isActive

### FR-011 게시글 목록 조회
- 대상: 모든 사용자 (비공개문의 제외)
- 입력:
  - boardId: number
  - page: number (기본 1)
  - limit: number (기본 20, 최대 100)
  - search: string (선택)
  - sort: 'latest'|'popular'|'views' (기본 'latest')
- 처리:
  - 삭제된 게시글(deletedAt IS NOT NULL) 제외
  - 비공개문의: 본인 글만 반환 (Admin은 전체)
- 출력: { success: true, data: PostSummary[], meta: PageMeta }

### FR-012 게시글 상세 조회
- 대상: 모든 사용자 (타입별 제한 적용)
- 입력: postId: number
- 처리:
  - 조회수(viewCount) 1 증가 (요청자 IP 기준 24시간 중복 방지)
  - 비공개문의: 작성자 또는 ADMIN만 접근
- 출력: { success: true, data: PostDetail }
- 오류: 403 (비공개문의 접근 권한 없음), 404 (게시글 없음)

### FR-020 게시글 작성
- 대상: USER 이상 (공지: MODERATOR 이상)
- 입력:
  - boardId: number
  - title: string (1~200자)
  - content: string (HTML, 최대 50,000자)
  - isAnonymous: boolean (자유 게시판만, 기본 false)
  - files: File[] (갤러리: 이미지 1~10개 필수, 동영상: 영상 1개 필수)
- 처리:
  - content-filter 스킬로 금지어 검사
  - 갤러리: image-optimizer 스킬로 WebP 변환 + 썸네일 생성
  - 동영상: video-thumbnailer 스킬로 썸네일 추출
  - 자유게시판 익명: authorId를 null로 저장
- 출력: { success: true, data: { postId } }
- 오류:
  - 400: 유효성 검증 실패 (파일 형식, 크기 제한 등)
  - 401: 비인증
  - 403: 권한 없음

### FR-021 게시글 수정
- 대상: 작성자 또는 MODERATOR 이상
- 입력: postId, title(선택), content(선택), files(선택)
- 처리: 수정 이력 updatedAt 갱신
- 오류: 403 (권한 없음), 404 (없음)

### FR-022 게시글 삭제
- 대상: 작성자 또는 MODERATOR 이상
- 처리: 소프트 딜리트 (deletedAt = NOW())
- 연쇄 처리: 하위 댓글도 소프트 딜리트

### FR-030 Q&A 답변 채택
- 대상: Q&A 게시글 작성자
- 입력: postId, answerId(comment의 id)
- 처리:
  - Post.acceptedAnswerId = answerId
  - Post.isAnswered = true
  - 채택된 댓글 작성자에게 포인트 +10

### FR-040 댓글 작성
- 대상: USER 이상
- 입력:
  - postId: number
  - content: string (1~2,000자)
  - parentId: number | null (대댓글 시 부모 댓글 ID)
- 처리:
  - content-filter 스킬 금지어 검사
  - 대댓글은 1단계까지만 허용 (대대댓글 금지)
  - Post.commentCount 1 증가
- 출력: { success: true, data: { commentId } }

### FR-050 파일 업로드
- 대상: USER 이상
- 입력:
  - file: File
  - postId: number
- 제한:
  - 이미지: JPEG, PNG, GIF, WebP (최대 5MB)
  - 동영상: MP4, MOV, AVI (최대 100MB)
- 처리 (갤러리 게시판):
  - image-optimizer로 WebP 변환 (품질: 85%)
  - 썸네일 3종 생성 (150x150, 640x480, 1280x960)
- 처리 (동영상 게시판):
  - video-thumbnailer로 썸네일 추출 (3초 지점)

## 5. 비기능 요구사항 (NFR)

### NFR-001 성능
- API 응답 시간: p95 기준 500ms 이하
- 동시 사용자 100명 처리
- 이미지 썸네일 생성: 10초 이하

### NFR-002 보안
- HTTPS 필수
- CORS: 허용 오리진 명시 (와일드카드 금지)
- Rate Limiting: API별 초당 최대 요청 수 제한
- 파일 업로드: 바이러스 스캔 (선택)

### NFR-003 가용성
- 목표 가동률: 99.5% (월 3.6시간 이하 다운타임)
- 백업: 일 1회 자동 DB 백업

## 7. 금지 사항 (MUST NOT)

- 직접 SQL 쿼리 사용 (Prisma ORM만 사용)
- 물리적 데이터 삭제 (소프트 딜리트 정책 준수)
- .env 파일을 Git에 커밋
- JWT를 localStorage에 저장 (httpOnly 쿠키 사용)
- 비밀번호를 평문으로 저장 또는 로그 출력
- 사용자 입력을 sanitize 없이 HTML로 렌더링 (XSS)
- CORS 허용 오리진에 와일드카드(*) 사용

## 8. 용어 정의

| 용어 | 정의 |
|------|------|
| 소프트 딜리트 | deleted_at 필드를 현재 시각으로 설정하여 논리적으로 삭제. 물리 삭제는 하지 않음 |
| Access Token | JWT 형식의 단기 인증 토큰 (15분) |
| Refresh Token | 장기 토큰 갱신용 토큰 (7일), httpOnly 쿠키 저장 |
| 비공개문의 | 작성자와 Admin만 열람 가능한 1:1 문의 게시판 |
| 자유 게시판 | 익명 작성 가능. 실명과 익명 선택 |
| BoardType | 게시판 유형 Enum: GENERAL, GALLERY, VIDEO, QNA, NOTICE, FAQ, PRIVATE, FREE |
```

## 5. PRD를 에이전트에게 전달하는 방법

PRD를 작성한 후 에이전트에게 전달하여 구현을 시작한다:

```bash
# PRD 파일로 저장
mkdir -p docs
# (위 PRD 내용을 docs/PRD.md로 저장)

# 에이전트에게 PRD 기반 구현 지시
agy agent run "다음 PRD를 완전히 이해하고,
              1단계로 prisma/schema.prisma를 모든 모델과 Enum을 포함하여 작성해줘.
              PRD의 FR 명세에서 필요한 모든 필드를 포함하고,
              관계(relation)를 올바르게 설정해줘" @docs/PRD.md
```

## 6. PRD 품질 자가 검증 체크리스트 20항목

PRD 완성 후 다음 20가지를 확인한다:

```
기본 요소 (1-5):
[ ] 1. 서비스 목적과 핵심 가치 제안이 1-2문장으로 명확히 기술됨
[ ] 2. 포함 범위와 제외 항목이 명시됨
[ ] 3. 성공 지표(KPI)가 수치로 정의됨
[ ] 4. 기술 스택이 레이어별로 명시됨
[ ] 5. 용어 정의(Glossary)가 포함됨

사용자 역할 (6-8):
[ ] 6. 모든 사용자 역할이 정의됨 (Guest, User, Moderator, Admin 등)
[ ] 7. 각 역할의 권한이 기능별로 테이블로 정리됨
[ ] 8. 역할 간 계층 관계가 명확함

기능 명세 (9-15):
[ ] 9. 모든 기능에 FR-xxx 형식의 고유 ID가 있음
[ ] 10. 각 기능의 대상 사용자 역할이 명시됨
[ ] 11. 각 기능의 입력 파라미터가 타입과 제약사항 포함하여 명시됨
[ ] 12. 각 기능의 출력 형식이 JSON으로 명시됨
[ ] 13. 각 기능의 오류 코드가 HTTP 상태 코드와 함께 명시됨
[ ] 14. 파일 업로드 기능의 크기/형식 제한이 명시됨
[ ] 15. 페이지네이션 방식이 명시됨 (오프셋/커서 중 선택)

비기능 요구사항 (16-18):
[ ] 16. 성능 요구사항이 수치로 명시됨 (응답 시간, 동시 사용자)
[ ] 17. 보안 요구사항이 명시됨 (HTTPS, CORS, Rate Limiting)
[ ] 18. 가용성 목표가 명시됨

안전장치 (19-20):
[ ] 19. 금지 사항(MUST NOT) 목록이 명시됨
[ ] 20. 에이전트가 오해할 수 있는 모호한 표현이 없음
```

## 7. PRD 버전 관리 전략

### 7.1 Git으로 PRD 버전 관리

PRD는 살아있는 문서다. 변경이 일어날 때마다 Git으로 추적한다:

```bash
# PRD 초기 커밋
git add docs/PRD.md
git commit -m "docs: PRD v1.0 초안 작성"

# 변경 발생 시 (예: 비공개 문의 기능 추가)
git add docs/PRD.md
git commit -m "docs: PRD v1.1 - 비공개 문의 게시판 기능 추가"

# PRD 이력 확인
git log --oneline docs/PRD.md
```

### 7.2 PRD 변경 영향 분석

PRD가 변경될 때 에이전트에게 영향 분석을 요청한다:

```
/ask "PRD에서 비공개 문의 게시판 기능이 새로 추가되었어.
      이미 구현된 코드에서 변경이 필요한 부분을 분석해줘:
      1. schema.prisma에서 수정할 부분
      2. PostsService에서 추가할 로직
      3. 새로 필요한 API 엔드포인트
      4. 프론트엔드에서 수정할 부분"
      @docs/PRD.md @src/
```

## 8. 역할별 PRD 협업 가이드

### 8.1 기획자 — PRD 초안 작성

```
기획자가 /ask로 브레인스토밍 후 초안 작성:

/ask "아이디어를 PRD로 구조화해줘:
      아이디어: 대학교 과 커뮤니티 사이트
      목적: 선후배 멘토링, 강의 정보 공유, 취업 정보
      대상: 대학생 (재학생, 졸업생)"

→ 에이전트가 PRD 초안 구조 제안
→ 기획자가 상세 내용 채우기
```

### 8.2 개발자 — 기술적 검토

```
개발자가 PRD 기술적 타당성 검토:

/ask "이 PRD에서 기술적으로 주의해야 할 부분은?
      SvelteKit + NestJS + PostgreSQL 스택에서
      각 기능의 구현 난이도를 상 중 하로 분류해줘"
      @docs/PRD.md
```

### 8.3 디자이너 — UI 요구사항 확인

```
디자이너가 PRD에서 UI 관련 내용 추출:

/ask "이 PRD에서 디자인이 필요한 화면 목록을 추출해줘.
      각 화면의 주요 UI 구성요소와 인터랙션도 정리해줘"
      @docs/PRD.md
```
