> **R6 수정**: @must/@avoid/@prefer 어노테이션 시스템 완전 삭제 (공식 문서 미확인 창작 오류). 일반 Markdown 규칙 문장 방식으로 완전 대체. AST 파싱/시맨틱 청킹 창작 설명 삭제. @include 지시어 삭제. 내용 실질적 가치 유지하며 공식 방식에 맞게 재작성.

# 04. GEMINI.md 작성 완벽 가이드 — 에이전트의 헌법 설계하기

> **학습 목표**
> - GEMINI.md의 역할과 에이전트 동작에 미치는 영향을 이해한다
> - 파일 위치와 우선순위 체계를 파악한다
> - 명확한 Markdown 규칙 문장으로 에이전트를 효과적으로 제어한다
> - 멀티 게시판 프로젝트용 완전한 GEMINI.md를 작성한다
> - 잘못 작성된 GEMINI.md와 올바른 GEMINI.md를 구별할 수 있다

## 1. GEMINI.md란 무엇인가

GEMINI.md는 Antigravity 에이전트가 프로젝트에서 작업할 때 따라야 할 규칙을 정의한 파일이다. Claude Code의 CLAUDE.md에 해당하는 개념으로, 에이전트의 "헌법" 또는 "시스템 프롬프트의 파일화"라고 이해하면 된다.

에이전트는 새로운 작업을 시작할 때마다 GEMINI.md를 먼저 읽고, 그 규칙들을 작업 전반에 적용한다. 개발자가 매번 "TypeScript strict 모드를 써줘", "Prisma ORM만 사용해줘" 같은 지시를 반복할 필요가 없다.

GEMINI.md는 **일반 Markdown 형식**으로 작성한다. 명확한 문장과 목록으로 규칙을 표현하면 에이전트가 이를 이해하고 따른다.

### 1.1 GEMINI.md가 없을 때의 문제

```
개발자: "users 모듈 CRUD 구현해줘"

에이전트 결과물 (GEMINI.md 없음):
- any 타입 사용 (TypeScript strict 무시)
- 직접 SQL 쿼리 사용 (Prisma 대신 pg 라이브러리)
- 영어 주석 (한국어 팀 프로젝트인데)
- 소프트 딜리트 미적용 (DB 설계 원칙 무시)
- camelCase 대신 snake_case 변수명
```

GEMINI.md를 잘 작성하면 에이전트가 처음부터 프로젝트 컨벤션에 맞는 코드를 생성한다.

### 2.1 위치 유형

2. 프로젝트 루트 GEMINI.md
   위치: {프로젝트루트}/GEMINI.md
   범위: 해당 프로젝트 전체
   용도: 프로젝트 컨벤션, 기술 스택 규칙

3. 하위 폴더 GEMINI.md
   위치: {프로젝트루트}/src/GEMINI.md

## 3. GEMINI.md 작성 원칙

### 3.1 명확한 규칙 문장으로 작성

GEMINI.md는 일반 Markdown으로 작성하며, 에이전트가 이해하기 쉬운 명확한 문장을 사용한다:

**좋은 예 — 구체적인 기술 규칙:**

- 모든 서비스 메서드에 한국어 JSDoc 주석을 작성한다

**나쁜 예 — 모호한 규칙:**
```markdown

```

## 5. 멀티 게시판 프로젝트 전체 GEMINI.md 예시

```markdown

# 최종 수정: 2026-06-01

## 프로젝트 개요

**서비스명**: BoardHub (멀티 게시판 허브)
**목적**: 8종 게시판(일반·갤러리·동영상·Q&A·공지·FAQ·비공개문의·자유)을 단일 서비스에서 통합 관리
**개발 언어**: 한국어 (주석·변수명 영어, 사용자 메시지 한국어)

### 기술 스택

| 레이어 | 기술 | 버전 |
|-------|------|-----|
| Frontend | SvelteKit | 2.x |
| Backend | NestJS | 11.x |
| Database | PostgreSQL | 16 |
| ORM | Prisma | v5 |
| Auth | JWT (Access + Refresh) | - |
| 패키지 관리 | pnpm workspaces | 9.x |
| 테스트 | Vitest | 1.x |

## 절대 금지 사항

- Prisma `$queryRaw`, `$executeRaw` 사용 금지 (SQL Injection 위험)
- `any` 타입 사용 금지 (unknown 또는 구체적 타입 사용)
- `DELETE FROM` 직접 실행 금지 (소프트 딜리트: `deletedAt` 필드 업데이트)
- `.env`, `.env.local` 파일을 Git에 커밋 금지
- 하드코딩된 설정값 금지 (URL, 포트, 비밀키 등은 환경변수로)
- `console.log` 사용 금지 (Logger 서비스의 `this.logger.log` 사용)
- 동기 파일 I/O 금지 (`fs.readFileSync` → `fs.readFile` 사용)

## 핵심 필수 규칙

### 코드 품질
- TypeScript strict 모드를 항상 사용한다 (`tsconfig.json`: `"strict": true`)
- 모든 DB 조작은 Prisma ORM을 통해서만 한다
- 환경 변수는 반드시 `ConfigService`를 통해 읽는다 (`process.env` 직접 접근 금지)
- 새로운 Prisma 모델 추가 시 반드시 migration 파일을 생성한다
- 모든 서비스 메서드에 한국어 JSDoc 주석을 작성한다
- 컨트롤러에서 비즈니스 로직을 작성하지 않는다 (서비스로 위임)
- 모든 API 엔드포인트에 `@ApiOperation`, `@ApiResponse` 데코레이터를 추가한다

### API 응답 형식
- 성공 응답: `{ "success": true, "data": T, "meta": PageMeta | null }`
- 에러 응답: `{ "success": false, "message": string, "code": string, "statusCode": number }`
- HTTP 상태 코드: 200(조회), 201(생성), 400(입력오류), 401(인증), 403(권한), 404(없음)
- 모든 날짜 필드는 UTC로 저장하고 ISO 8601 형식으로 반환한다
- 파일 업로드 크기 제한: 이미지 5MB, 동영상 100MB

### 인증/인가
- 인증이 필요한 API는 `JwtAuthGuard`를 적용한다
- 관리자 전용 API는 `RolesGuard + @Roles('ADMIN')`을 적용한다
- JWT 토큰은 `localStorage`가 아닌 `httpOnly` 쿠키에 저장한다

## 권장 패턴

- SvelteKit server-side load 함수를 클라이언트 fetch보다 우선 사용한다
- `class-validator + class-transformer`를 유효성 검증에 사용한다
- `date-fns`를 날짜 처리에 사용한다 (moment.js 사용 지양)
- 테스트 파일은 구현 파일 옆에 위치한다 (`posts.service.spec.ts`)
- 컴포넌트 파일명은 PascalCase를 사용한다 (`PostCard.svelte`)
- `index.ts` 배럴 파일로 모듈 공개 API를 관리한다
- 단일 파일은 300줄을 초과하지 않는다 (초과 시 파일 분리)

## DB 규칙

### 소프트 딜리트 정책

모든 주요 엔티티는 소프트 딜리트를 적용한다:

```prisma
model Post {
  id        Int       @id @default(autoincrement())
  deletedAt DateTime? @map("deleted_at")
}
```

Prisma v5 `$extends()` 패턴으로 자동 필터링:
```typescript
const prismaWithSoftDelete = prisma.$extends({
  query: {
    $allModels: {
      async findMany({ args, query }) {
        args.where = { ...args.where, deletedAt: null };
        return query(args);
      },
    },
  },
});
```

### 페이지네이션
```typescript
interface PaginationQuery {
  page?: number;    // 기본값: 1
  limit?: number;   // 기본값: 20, 최대: 100
}
```

## 7. 잘못 작성된 vs 올바른 GEMINI.md 비교

### 비교 1: 모호한 규칙 vs 구체적인 규칙

**나쁜 예:**
```markdown
- 코드를 잘 작성한다
- 보안에 신경쓴다

**좋은 예:**
```markdown

- 비밀번호는 bcrypt rounds: 12로 해싱한다
- 단위 테스트 커버리지 90% 이상을 유지한다
```

### 비교 2: 기술 스택 미명시 vs 명시

**나쁜 예:**
```markdown
# 프로젝트 규칙
- 좋은 코드를 작성한다
```

**좋은 예:**
```markdown
## 기술 스택
- Backend: NestJS 11.x + TypeScript 5.x
- ORM: Prisma v5 (직접 SQL 금지)
- 패키지 관리: pnpm 9.x (npm, yarn 사용 금지)
```

### 비교 3: 충돌하는 규칙 vs 일관된 규칙

**나쁜 예:**
```markdown
- 소프트 딜리트를 사용한다
- 너무 복잡한 Prisma 쿼리를 작성하지 않는다
→ 소프트 딜리트는 Prisma 미들웨어가 필요한데 이를 금지하면 충돌
```

**좋은 예:**
```markdown
- 소프트 딜리트를 사용한다 (deletedAt 필드)
- Prisma v5 $extends()로 삭제된 레코드를 자동 필터링한다
- 단일 파일 500줄 초과 금지 (기능별 분리)
```
