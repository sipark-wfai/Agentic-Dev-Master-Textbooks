# 08. 샌드박스 완벽 가이드 — 안전한 격리 실행 환경의 모든 것

> **학습 목표**
> - Secure Linux Sandbox의 필요성과 작동 원리를 이해한다
> - 샌드박스 생명주기(시작→작업→Proposal→종료)를 파악한다
> - 파일 시스템 격리와 네트워크 격리 설정 방법을 익힌다
> - 샌드박스 리소스 제한을 프로젝트에 맞게 튜닝한다
> - 병렬 샌드박스 충돌 방지와 초기화 문제를 해결한다

## 1. 샌드박스의 필요성 — 왜 에이전트를 격리 환경에서 실행하는가

### 1.1 샌드박스 없는 에이전트의 위험

에이전트가 격리 없이 직접 로컬 파일 시스템과 시스템 명령에 접근하면 어떤 위험이 있을까?

**위험 시나리오 1: 실수로 인한 파일 삭제**
```
에이전트 지시: "불필요한 node_modules 캐시를 정리해줘"

에이전트 실행 (격리 없음):
rm -rf /Users/developer/projects/boardhub/node_modules
# 의도한 동작

rm -rf /Users/developer/projects/  ← 경로 오해로 전체 프로젝트 삭제
# 복구 불가
```

**위험 시나리오 2: 비밀 파일 노출**
```
에이전트가 디버깅 목적으로:
cat .env >> debug.log
git add debug.log
git commit -m "debug: add log file"
git push origin main

→ .env 내용이 GitHub에 공개 업로드
```

**위험 시나리오 3: 시스템 명령 오용**
```
에이전트가 포트를 확인하려다:
kill -9 $(lsof -t -i:3000)
# 3000번 포트를 쓰는 다른 중요한 서비스 종료
```

### 1.2 샌드박스가 해결하는 문제

Secure Linux Sandbox는 에이전트의 모든 작업을 격리된 컨테이너 안에서 실행한다.

```
격리 전:
  에이전트 → 로컬 파일 시스템 (위험)
  에이전트 → 시스템 명령 (위험)
  에이전트 → 네트워크 (무제한 위험)

격리 후:
  에이전트 → 샌드박스 가상 파일 시스템 (안전)
             ↓ (Proposal Accept 시에만)
             로컬 파일 시스템 (인간이 최종 승인)
  에이전트 → 샌드박스 시스템 명령 (제한됨)
  에이전트 → 허용된 도메인만 접근 (화이트리스트)
```

## 2. Secure Linux Sandbox 아키텍처

### 2.1 기술 스택

```
Secure Linux Sandbox 내부 구조:
+----------------------------------------------+
| Alpine Linux 기반 컨테이너 *(버전 3.19는 공식 미확인)* <!-- R3 수정 -->                    |
|                                              |
| /workspace/                                  |
|   ├── (프로젝트 파일 스냅샷)                  |
|   └── (에이전트 작업 공간)                    |
|                                              |
| 런타임:                                       |
|   - Node.js 22 (프로젝트 실행)               |
|   - Python 3.12 (스크립트)                   |
|   - Go 1.22 (CLI 도구)                       |
|   - Git 2.45                                 |
|   - pnpm 9.x                                 |
|                                              |
| 격리 레이어:                                  |
|   - 네임스페이스 (PID, NET, MNT, UTS, IPC)   |
|   - cgroups v2 (CPU, Memory 제한)            |
|   - seccomp 필터 (허용된 시스템 콜만)         |
|   - AppArmor 프로파일 (파일 접근 제어)        |
+----------------------------------------------+
|            Docker 런타임 (호스트)              |
+----------------------------------------------+
|         Antigravity Desktop App               |
+----------------------------------------------+
|              macOS / Windows                  |
+----------------------------------------------+
```

### 2.2 샌드박스가 컨테이너 기반인 이유

가상 머신(VM) 대신 컨테이너를 사용하는 이유:
- **속도**: 컨테이너 시작 시간이 VM보다 10배 이상 빠름 (1-2초 vs 30-60초)
- **리소스**: 컨테이너는 VM보다 훨씬 적은 리소스 사용
- **격리**: seccomp + AppArmor로 충분한 보안 격리 제공

## 3. 샌드박스 생명주기

### 3.1 생명주기 단계

```
생명주기 흐름:

1. INIT (초기화)
   ├── Alpine Linux 컨테이너 시작
   ├── 프로젝트 파일 스냅샷 (현재 상태 복사)
   ├── Node.js, pnpm 등 런타임 준비
   └── MCP 서버 연결 확인

2. READY (준비)
   └── 에이전트 작업 대기

3. RUNNING (실행 중)
   ├── 에이전트가 파일 읽기/쓰기
   ├── 명령어 실행 (npm, git 등)
   ├── MCP 서버 호출
   └── 스킬 실행

4. PROPOSING (제안 중)
   ├── 작업 완료 감지
   ├── 변경된 파일 목록 수집
   └── Proposal 카드 생성

5. APPLYING (적용 중) — Proposal Accept 시
   ├── 변경 파일을 로컬 파일 시스템에 복사
   ├── 타임머신 스냅샷 저장
   └── 샌드박스 상태 갱신

6. IDLE / STOP
   └── 일정 시간 비활성 후 자동 정리
```

### 3.2 샌드박스 시작 과정 상세

```bash
agy sandbox start

# 내부 처리 과정 (agy daemon logs --follow로 확인 가능):
[sandbox] Pulling base image: gcr.io/antigravity-sandbox/alpine-base:2.0  # 주의: 이미지 경로 공식 미확인 <!-- R3 수정 --> (cached)
[sandbox] Creating container: boardhub-sandbox-001
[sandbox] Mounting workspace: /Users/dev/projects/boardhub → /workspace (read-only)
[sandbox] Initializing runtime: Node.js 22.x, pnpm 9.x
[sandbox] Running pnpm install (캐시 사용)
[sandbox] Connecting MCP servers: postgres-mcp, git-mcp
[sandbox] Sandbox ready in 2.1s
```

## 4. 파일 시스템 격리

### 4.1 격리 구조

```
호스트 파일 시스템 (로컬):            샌드박스 파일 시스템:
/Users/dev/projects/boardhub/        /workspace/
  ├── src/                              ├── src/ (읽기 전용 마운트)
  │   ├── users/ (현재 상태)            │   ├── users/ (복사본)
  │   └── posts/ (현재 상태)            │   └── posts/ (복사본)
  ├── prisma/                           ├── prisma/ (복사본)
  └── GEMINI.md                        ├── GEMINI.md (복사본)
                                        └── (에이전트 작업 임시 파일)
```

**중요한 격리 원칙:**
- 에이전트는 샌드박스의 `/workspace`에만 쓰기 가능
- 호스트 파일 시스템은 Proposal Accept 전까지 변경되지 않음
- 에이전트가 `rm -rf /workspace/node_modules`를 실행해도 호스트는 영향 없음

### 4.2 파일 동기화 타이밍

```
에이전트 작업 중:
  호스트 → 샌드박스: 작업 시작 시 스냅샷 한 번 (단방향)

Proposal Accept 후:
  샌드박스 → 호스트: 변경된 파일만 선택적 복사

명시적 동기화 (필요 시):
  agy sandbox sync  # 주의: agy sandbox sync 명령어 공식 미확인 <!-- R3 수정 -->   # 호스트의 최신 변경을 샌드박스에 반영
```

## 6. 네트워크 격리

### 6.1 네트워크 정책 모드

**Whitelist 모드 (권장):**
```json
{
  "networkPolicy": {
    "mode": "whitelist",
    "allowedDomains": [
      "registry.npmjs.org",
      "pypi.org"
    ]
  }
}
```
허용된 도메인만 접근 가능. 가장 안전한 방법.

**Blacklist 모드:**
```json
{
  "networkPolicy": {
    "mode": "blacklist",
    "blockedDomains": [
      "*.social-media.com",
      "*.tracker.com"
    ]
  }
}
```
차단된 도메인만 차단. 덜 안전하지만 유연함.

**Disabled 모드 (오프라인 개발):**
```json
{
  "networkPolicy": {
    "mode": "disabled"
  }
}
```
모든 외부 네트워크 차단. 완전 격리 개발 환경.

## 8. 파일 동기화 단절 문제와 해결법

### 8.1 문제 시나리오

에이전트 작업 중에 개발자가 직접 파일을 수정하면 동기화 문제가 발생할 수 있다.

```
상황:
1. 에이전트가 users.service.ts 작업 중
2. 개발자가 IDE에서 직접 users.service.ts를 수정
3. 에이전트가 작업 완료 후 Proposal 발행
4. Proposal의 변경 기반이 된 파일(샌드박스)과
   현재 호스트 파일이 달라짐 → 충돌 발생
```

### 8.2 해결 방법

```bash
# 방법 1: 에이전트 작업 중 직접 파일 수정 자제
# (에이전트 작업 완료 후 수동 수정)

# 방법 2: 동기화 강제 갱신
agy sandbox sync  # 주의: agy sandbox sync 명령어 공식 미확인 <!-- R3 수정 -->

# 방법 3: Proposal에서 충돌 파일을 Selective Reject
# Diff View에서 충돌 파일만 Reject하고 나머지 Accept

# 방법 4: Timemachine으로 안전한 상태로 복구
agy timemachine restore --snapshot [이전_스냅샷_ID]
```

## 9. 병렬 샌드박스 충돌 방지

여러 에이전트가 동시에 같은 파일을 수정하려 할 때 충돌이 발생한다.

### 9.1 Mutex 파일 잠금

```json
// .agents/config.json
{
  "multiAgentGate": {
    "enabled": true,
    "strategy": "mutex",
    "conflictPolicy": "queue"  // 주의: 설정 키 이름 공식 미확인 <!-- R3 수정 -->,
    "mutexFiles": [
      "prisma/schema.prisma",
      "package.json",
      "pnpm-lock.yaml",
      ".env"
    ]
  }
}
```

`mutexFiles`에 등록된 파일은 한 번에 하나의 에이전트만 수정할 수 있다. 나머지 에이전트는 큐에서 대기한다.

### 9.2 에이전트별 작업 영역 분리

```bash
# 에이전트 1: 백엔드만 담당
agy agent run "users 모듈 구현" --scope "apps/backend/src/users/"

# 에이전트 2: 프론트엔드만 담당
agy agent run "사용자 목록 페이지 구현" --scope "apps/frontend/src/routes/users/"
```

각 에이전트가 서로 다른 `--scope`를 갖도록 설정하면 파일 충돌이 원천 차단된다.


### 10.2 샌드박스 동작 확인 실습

```bash
# 1. 샌드박스 시작

# 3. 간단한 테스트 실행
agy sandbox exec "node --version"
agy sandbox exec "pnpm --version"
agy sandbox exec "ls /workspace/"

# 4. 에이전트 작업 실행

              installed 패키지 수, DB 연결 상태를 확인하고 보고해줘"

# 5. Proposal 확인 (보고서 파일 생성)
agy proposal list
agy proposal accept --all
```
