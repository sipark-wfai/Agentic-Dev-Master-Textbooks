## 1. 소프트웨어 개발의 패러다임 전환

### 1.1 코파일럿 시대 (2021–2024)

2021년 GitHub Copilot이 등장했을 때 개발자들은 환호했다. 자동완성이 단순한 키워드 수준을 넘어 함수 전체를 제안해 주었기 때문이다. 이후 수많은 코파일럿형 도구들이 쏟아졌다.

그러나 코파일럿 시대의 도구들은 본질적으로 **"매우 똑똑한 자동완성기"**에 불과했다. 개발자가 코드를 한 줄씩 입력하면, AI가 다음 줄을 제안하는 방식이다. 의사결정권은 언제나 인간에게 있었고, AI는 보조자 역할에 머물렀다.

```
코파일럿 패러다임:
  인간 → [코드 입력] → AI 제안 → 인간 수락/거부 → 반복
  (인간이 루프를 주도, AI는 한 줄씩 반응)
```

코파일럿 시대의 3가지 한계:
1. **컨텍스트 단절**: 파일 하나만 보고 제안하므로, 프로젝트 전체 구조를 이해하지 못한다
2. **실행 불가**: 코드를 제안할 뿐, 실제로 실행·테스트·배포하지 못한다
3. **기억 없음**: 세션이 끊기면 이전 대화와 결정을 기억하지 못한다

### 1.2 에이전트 시대 (2025–현재)

2025년을 기점으로 개발 도구의 패러다임이 근본적으로 바뀌었다. 단순히 "더 잘 제안하는" AI가 아니라, **"스스로 계획하고, 실행하고, 검증하는"** AI 에이전트가 등장한 것이다.

에이전트 패러다임에서 AI는:
- 사용자의 지시를 받아 **스스로 계획**을 수립한다
- 도구(파일 읽기·쓰기, 명령어 실행, API 호출 등)를 **자율적으로 사용**한다
- 실행 결과를 **관측하고 다음 행동을 수정**한다
- 목표를 달성할 때까지 **루프를 지속**한다

```
에이전트 패러다임:
  인간 → [목표 지시] → AI 계획 → AI 실행 → AI 관측 → AI 수정 → ... → 결과 보고
  (AI가 루프를 주도, 인간은 목표와 최종 승인만)
```

### 1.3 코파일럿 vs 에이전트 비교표

| 구분 | 코파일럿 (예: GitHub Copilot) | 에이전트 (예: Google Antigravity 2.0) |
|------|-------------------------------|--------------------------------------|
| 역할 | 스마트 자동완성기 | 자율 실행 파트너 |
| 컨텍스트 범위 | 현재 파일 + 열린 탭 | 전체 프로젝트 + 외부 시스템(DB, Git, API) |
| 실행 능력 | 없음 (제안만) | 있음 (파일 수정, 명령 실행, 테스트, 배포) |
| 계획 수립 | 없음 | 있음 (단계별 마일스톤 자동 분할) |
| 오류 처리 | 없음 | 있음 (오류 감지 → 자동 수정 → 재시도) |
| 메모리 | 없음 | 있음 (GEMINI.md로 규칙 영속화) |
| 비용 단위 | 토큰/월정액 | 월정액 플랜 기반 |
| 인간 개입 시점 | 매 줄마다 | 목표 설정 + 최종 Proposal 승인 |
| 안전장치 | 없음 | Proposal System + Sandbox 격리 |

## 2. Google Antigravity 2.0의 탄생

### 2.1 역사와 배경

**2024년 하반기**: Google DeepMind와 Google Labs의 공동 프로젝트로 "Project Liftoff" 시작. Gemini 모델을 로컬 개발 환경에 통합하는 연구가 진행되었다. <!-- R3 수정: 내부 프로젝트명 "Project Liftoff" 및 이 시기 세부 내용은 공식 미확인 — 창작 정보 포함 가능성 있음 -->

**2025년 11월**: Google Antigravity v1.0 비공개 베타 출시. 초기에는 Google 내부 개발자들만 사용했으며, VS Code 익스텐션 형태로 배포되었다. 이 버전에서는 기본적인 코드 생성과 파일 수정 기능만 제공되었다.

**2026년 1월**: 공개 베타 출시. 외부 개발자들의 피드백을 수집하면서 Proposal System의 초안이 개발되었다. 이 시기에 샌드박스 격리 실행의 필요성이 제기되었다. <!-- R3 수정: 2026년 1월 공개 베타 날짜 공식 미확인 — 공식 발표는 2026년 5월 19일 Google I/O -->

**2026년 5월 Google I/O**: **Google Antigravity 2.0** 정식 발표. 가장 큰 변화는 3-tier 아키텍처의 도입이었다. Desktop App(백엔드 엔진) + Antigravity IDE(프론트엔드 에디터) + CLI(`agy` 명령어)가 분리되어 독립적으로 동작하면서도 유기적으로 연결되는 구조가 탄생했다. 내부 AI 엔진도 Gemini 3.5로 업그레이드되었다.

### 2.2 왜 3-tier 구조인가?

기존 VS Code 익스텐션 방식(v1.0)의 문제점:
- IDE가 닫히면 에이전트 작업도 중단된다
- 에이전트가 IDE 프로세스와 같은 메모리 공간을 공유하여 격리가 불가능하다
- CI/CD 파이프라인에서 사용하려면 GUI가 필요하다

2.0의 해결책:
- **Desktop App**: 항상 백그라운드에서 실행되는 데몬 프로세스. IDE를 닫아도 에이전트 작업이 계속된다
- **IDE**: 에디터와 에이전트 관리를 하나의 화면에서 처리하는 전용 인터페이스
- **CLI**: GUI 없이 터미널과 CI/CD에서 에이전트를 제어할 수 있는 경량 도구

## 3. 3대 구성 요소 상세 개요

### 3.1 Antigravity 2.0 Desktop App (백엔드 엔진)

Desktop App은 Antigravity 에코시스템의 심장부다. 사용자가 직접 조작하는 UI는 없지만, 모든 지능적 처리가 여기서 이루어진다.

**주요 역할:**

1. **로컬 에이전트 데몬 (Local Agent Daemon) 실행**
   - 백그라운드에서 항상 실행되는 서비스 프로세스
   - Gemini 3.5 Flash API와의 통신을 담당
   - 에이전트 작업 큐(Task Queue) 관리

2. **보안 가상 리눅스 샌드박스 (Secure Linux Sandbox) 호스팅**
   - Alpine Linux 기반 컨테이너 환경
   - 에이전트가 실행하는 모든 코드는 이 안에서 격리 실행됨
   - 로컬 파일 시스템에 직접 접근 불가 → Proposal System을 통해서만 반영

3. **MCP 서버 관리**
   - Model Context Protocol 서버들의 생명주기 관리
   - PostgreSQL, Git, 파일 시스템, 웹 검색 등 외부 시스템 연동

4. **Agent Skills 관리**
   - 온디맨드 스킬 패키지 로딩/언로딩
   - 이미지 최적화, 동영상 처리, 클라우드 배포 등

5. **멀티에이전트 오케스트레이션**
   - 여러 에이전트를 병렬로 실행하고 결과를 통합
   - 파일 충돌 방지를 위한 Mutex 잠금 관리

### 3.2 Antigravity IDE (프론트엔드 에디터)

VS Code 아키텍처를 기반으로 한 포크(Fork)이지만, 에이전트 협업을 위해 근본적으로 재설계된 에디터다.

**핵심 기능:**

- **듀얼 엔진 뷰 (Dual-Engine View)**:
  - 좌측 패널: 고성능 코드 에디터 (VS Code 완전 호환)
  - 우측 패널: 에이전트 관리 패널 (채팅, 작업 현황, Proposal 카드)

- **에이전트 제안 시스템 (Proposal Interface)**:
  - 에이전트가 생성한 코드 변경사항을 "제안 카드"로 표시
  - Accept / Reject / Partial Accept / Diff View 선택 가능

- **타임머신 롤백 (Timemachine)** *(공식 문서 미확인 기능)*: <!-- R3 수정: Timemachine 공식 확인 불가 — 창작 가능성 있음 -->
  - 모든 파일 변경을 트랜잭션으로 기록
  - 원클릭으로 특정 시점의 상태로 완전 복구

- **실시간 비용 게이지**:
  - 현재 작업에 사용된 토큰 수와 예상 비용 실시간 표시

- **gRPC 양방향 스트리밍**:
  - Desktop App과 실시간으로 통신
  - 에이전트 작업 상황을 IDE에 즉시 반영

### 3.3 Antigravity CLI (`agy` 명령어)

Go 언어로 빌드된 초경량 CLI 도구. 터미널에서 Antigravity의 모든 기능을 제어할 수 있다.

```bash
# 자주 사용하는 agy 명령어  <!-- R3 수정: 코드블록 내 ag 주석 → agy 수정 -->
agy --version              # 버전 확인
agy status                 # 데몬 상태 확인
agy sandbox start          # 샌드박스 시작
agy sandbox stop           # 샌드박스 중지
agy agent run "지시사항"   # 에이전트 실행
agy agent list             # 실행 중인 에이전트 목록
agy agent stop [id]        # 특정 에이전트 중지
agy skill install [이름]   # 스킬 설치
agy skill list             # 설치된 스킬 목록
agy mcp add [설정]         # MCP 서버 추가
agy logs [에이전트-id]     # 에이전트 로그 확인
```

CI/CD 파이프라인 예시:
```yaml
# GitHub Actions에서 Antigravity 사용
- name: Run Antigravity Agent
  run: |
    agy agent run "테스트 코드가 실패하는 모듈을 찾아 수정하고, PR 설명을 업데이트하라"
    agy agent wait --timeout 300
```

## 5. 핵심 개념 심층 이해

### 5.1 ReAct 루프 — 에이전트의 사고 방식

Antigravity 에이전트는 **ReAct(Reason + Act)** 패턴으로 동작한다. 이는 인공지능 에이전트가 복잡한 문제를 해결하는 방법론으로, 추론(Reason)과 행동(Act)을 반복하여 목표에 도달한다.

```
ReAct 루프 (단일 사이클):

1. REASON (추론)
   "현재 상황을 파악한다. users 테이블이 없으므로
    먼저 Prisma 스키마를 확인해야 한다"
        ↓
2. ACT (행동)
   filesystem-mcp를 사용해 prisma/schema.prisma 읽기
        ↓
3. OBSERVE (관측)
   "User 모델이 정의되어 있지만 migration이
    실행되지 않았음을 확인"
        ↓
4. REASON (재추론)
   "npx prisma migrate dev를 실행해야 한다"
        ↓
5. ACT (행동)
   샌드박스에서 npx prisma migrate dev 실행
        ↓
6. OBSERVE (관측)
   "마이그레이션 성공. users 테이블 생성 완료"
        ↓
7. 목표 달성 → 결과 보고 (Proposal 카드 발행)
```

이 루프가 인간의 "코드 작성 → 실행 → 오류 확인 → 수정" 사이클과 동일하다는 점에 주목하자. 에이전트는 단순히 코드를 생성하는 것이 아니라, 인간 개발자처럼 반복적으로 시도하고 수정한다.

### 5.2 Artifacts 시스템 — 블랙박스 문제 해결

초기 AI 에이전트의 가장 큰 문제는 **블랙박스**였다. 에이전트가 무엇을 했는지 알 수 없었고, 결과물을 추적하기 어려웠다.

Antigravity 2.0의 Artifacts 시스템은 이 문제를 해결한다. 에이전트가 생성하는 모든 산출물이 시각적 카드로 추적된다:

| Artifact 유형 | 설명 | 예시 |
|--------------|------|------|
| CODE | 생성/수정된 코드 파일 | `src/users/users.service.ts` |
| SCHEMA | DB 스키마 변경 | `prisma/schema.prisma` |
| TEST | 테스트 코드 | `src/users/users.spec.ts` |
| SCREENSHOT | UI 스크린샷 | 컴포넌트 렌더링 결과 |
| LOG | 실행 로그 | 서버 시작 로그, 테스트 결과 |
| MIGRATION | DB 마이그레이션 파일 | `20260601_add_users_table.sql` |

IDE의 Artifacts 패널에서 에이전트 작업의 전체 타임라인을 볼 수 있다. 어느 시점에 어떤 파일이 변경되었는지 완전히 투명하게 추적된다.

### 5.3 Proposal System — 안전한 코드 적용 메커니즘 *(공식 문서 미확인 기능)* <!-- R3 수정: Proposal System 세부 동작 방식 공식 미확인 -->

Proposal System은 Antigravity 2.0의 핵심 안전장치로 알려진 개념이다.

**동작 원리:**
1. 에이전트가 코드를 생성하면 **즉시 파일에 반영되지 않는다**
2. 대신 샌드박스 안의 임시 공간에 저장된다
3. IDE에 "Proposal 카드"가 표시되며 인간의 검토를 기다린다
4. 인간이 Accept를 선택하면 비로소 실제 파일 시스템에 반영된다

```
Proposal 카드 구조:
┌─────────────────────────────────────────┐
│  📋 Proposal #23                         │
│  에이전트: Gemini-3.5 / 작업: DB 스키마  │
│─────────────────────────────────────────│
│  변경 파일: prisma/schema.prisma         │
│  추가: +45줄 / 삭제: -3줄 / 수정: 0줄   │
│─────────────────────────────────────────│
│  [✅ Accept] [❌ Reject] [🔀 Partial]    │
│  [🔍 Diff View] [🕐 History]             │
└─────────────────────────────────────────┘
```

이 시스템 덕분에 에이전트가 실수를 하더라도 실제 코드베이스에는 영향이 없다. 인간이 항상 최종 결정권을 갖는다.

### 5.4 GEMINI.md — 에이전트의 헌법

GEMINI.md는 프로젝트 루트에 위치하는 텍스트 파일로, 에이전트가 따라야 할 규칙을 정의한다. Claude Code의 CLAUDE.md에 해당하는 개념이다.

Antigravity의 GEMINI.md는 어노테이션 시스템을 지원한다 *(공식 문서에서 확인 필요)*: <!-- R3 수정: @must/@avoid/@prefer 어노테이션 공식 미확인 -->
- `@must`: 반드시 지켜야 할 강제 규칙
- `@avoid`: 절대 해서는 안 되는 것
- `@prefer`: 권장 패턴 (부드러운 제약)

```markdown
<!-- GEMINI.md 미리보기 -->
# 멀티 게시판 허브 — Gemini 규칙서

@must TypeScript strict 모드를 사용한다
@must 모든 DB 조작은 Prisma ORM을 통해서만 한다
@avoid 직접 SQL 쿼리 사용 (Prisma $queryRaw 금지)
@prefer SvelteKit의 server-side load 함수를 우선 사용한다
```

## 6. 예제 프로젝트 소개 — 멀티 게시판 허브

이 시리즈 전체에서 사용할 실습 프로젝트는 **멀티 게시판 허브**다. 현실적인 웹 서비스를 에이전트와 함께 처음부터 끝까지 구축하는 과정을 통해 Antigravity 2.0의 모든 기능을 실습한다.

### 6.1 프로젝트 개요

**서비스명**: BoardHub (보드허브)
**목적**: 여러 종류의 게시판을 하나의 서비스에서 통합 관리

**8종 게시판:**
| 유형 | 설명 | 특이사항 |
|------|------|---------|
| 일반 게시판 | 텍스트 중심 자유 게시판 | 기본형 |
| 갤러리 게시판 | 이미지 중심 게시판 | 썸네일 자동 생성 |
| 동영상 게시판 | 동영상 공유 게시판 | 동영상 썸네일 추출 |
| Q&A 게시판 | 질문/답변 구조 | 채택된 답변 표시 |
| 공지 게시판 | 운영진 공지사항 | 관리자 전용 작성 |
| FAQ 게시판 | 자주 묻는 질문 | 카테고리 분류 |
| 비공개 문의 | 1:1 문의 게시판 | 작성자+관리자만 열람 |
| 자유 게시판 | 제한 없는 자유 게시판 | 익명 작성 가능 |

### 6.2 기술 스택

```
Frontend:  SvelteKit 2.x (TypeScript)
Backend:   NestJS 11.x (TypeScript)
Database:  PostgreSQL 16 + Prisma v5
Auth:      JWT (Access Token + Refresh Token)
Storage:   로컬 파일 시스템 (추후 S3 연동)
Deploy:    Docker Compose (개발) → Vercel+Railway (배포)
```

### 6.3 시스템 아키텍처 개요


### 6.4 이 프로젝트를 선택한 이유

멀티 게시판 허브는 다음 요소들을 모두 포함하기 때문에 Antigravity 2.0 학습에 최적이다:

- **복잡한 DB 설계**: 8가지 게시판 유형이 공통 구조를 공유하면서도 각자의 특성을 가짐
- **인증/인가 시스템**: JWT, 역할 기반 권한 제어(RBAC)
- **파일 업로드**: 이미지, 동영상 파일 처리
- **API 설계**: RESTful API 명세 작성 실습
- **풀스택 구현**: 프론트엔드와 백엔드를 함께 다룸
- **에이전트 스킬 활용**: image-optimizer, video-thumbnailer 스킬 실습

## 7. 역할별 가치 — 누가 왜 Antigravity를 사용하는가

### 7.1 개발자 관점

```
기존 방식:
  기획서 읽기 → 설계 → 코드 작성 → 디버깅 → 테스트 → 반복
  (수 주 ~ 수 개월 소요)

Antigravity 방식:
  PRD 작성 → GEMINI.md 설정 → agy agent run → Proposal 검토 → 배포
  (수 일 ~ 수 주 소요)
```

개발자의 역할이 "코드를 직접 작성하는 사람"에서 "에이전트를 설계하고 검증하는 사람"으로 진화한다.

**핵심 이점:**
- 반복적인 보일러플레이트 코드 생성을 에이전트에게 위임
- 복잡한 버그의 원인 분석과 수정 자동화
- 테스트 코드 자동 생성 및 커버리지 향상
- 문서 자동화 (API 명세, 컴포넌트 문서)

### 7.2 기획자 관점

기획자가 Antigravity를 사용하면 PRD(제품 요구사항 문서)를 직접 에이전트에게 전달하여 프로토타입을 확인할 수 있다. 개발자에게 요청하고 기다리는 시간이 대폭 줄어든다.

```
/ask "이 PRD에서 기술적으로 구현이 어려운 부분이 있는가? 
      난이도별로 분류해서 알려줘"

/ask "비공개 문의 게시판의 권한 정책이 ERD와 충돌하지 않는가?"
```

### 7.3 디자이너 관점

디자이너는 UI/UX 명세를 에이전트에게 전달하여 컴포넌트 코드를 생성하고, 실제 렌더링 결과를 스크린샷 Artifact로 확인할 수 있다.

```
/code "이 Figma 디자인 시스템에 맞춰 PostCard 컴포넌트를 
       SvelteKit으로 구현해. 카드 크기는 320x200px이고
       다크모드도 지원해야 해"
```

## 9. 기존 개발 방식 vs Antigravity 방식 대비

### 9.1 게시판 CRUD API 구현 시나리오

**기존 방식 (Copilot + 수동 작업):**
```
1일차: NestJS 모듈 구조 설계, 디렉터리 생성
2일차: Prisma 스키마 작성, 마이그레이션
3일차: PostsController, PostsService 작성
4일차: DTO 클래스 작성, 유효성 검증
5일차: 단위 테스트 작성
6일차: 통합 테스트, 버그 수정
총 소요: 6일 (실력에 따라 다름)
```

**Antigravity 방식:**
```
1시간: PRD 작성 + GEMINI.md 설정 + MCP 연동
2시간: agy agent run "posts 모듈 구현" → Proposal 검토
1시간: 생성된 코드 검토 및 수정
총 소요: 반나절 ~ 하루
```

### 9.2 비용 관점

기존 방식에서 개발자 1일 인건비가 50만원이라면, 6일 작업 = 300만원.
Antigravity 방식에서 비용은 선택한 플랜(월정액)에 따라 달라진다.

물론 에이전트가 생성한 코드를 검토하고 수정하는 개발자의 시간이 필요하지만, 전체 공수는 70~80% 절감된다.

## 10. 16편 학습 로드맵

이 시리즈는 크게 4단계로 구성된다:

```
Stage 1 — 환경 설정 (1~3편)

  02편: 설치 및 초기 설정
  03편: IDE 완벽 가이드

Stage 2 — 에이전트 제어 마스터 (4~9편)
  04편: GEMINI.md 작성법
  05편: 명령어 & 슬래시 커맨드
  06편: MCP 완벽 가이드
  07편: Skills 완벽 가이드
  08편: 샌드박스 완벽 가이드
  09편: 멀티에이전트 오케스트레이션

Stage 3 — 실전 프로젝트 (10~14편)
  10편: PRD 작성 (아이디어 → 문서)
  11편: 분석/설계서 작성 (ERD, API 명세)
  12편: PRD → 코드 (자율 구현 워크플로우)

  15편: 하네스 엔지니어링 (안전한 제어)

```

- **완전 마스터**: 01부터 16까지 순서대로
