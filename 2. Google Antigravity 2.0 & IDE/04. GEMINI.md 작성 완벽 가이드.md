# 04. GEMINI.md 작성 완벽 가이드 — 에이전트의 헌법 설계하기

> **학습 목표**
> - GEMINI.md의 역할과 에이전트 동작에 미치는 영향을 이해한다
> - 파일 위치와 우선순위 체계를 파악한다
> - @must / @avoid / @prefer 어노테이션 시스템을 숙달한다
> - 멀티 게시판 프로젝트용 완전한 GEMINI.md를 작성한다
> - 잘못 작성된 GEMINI.md와 올바른 GEMINI.md를 구별할 수 있다

---

## 1. GEMINI.md란 무엇인가

GEMINI.md는 Antigravity 에이전트가 프로젝트에서 작업할 때 반드시 따라야 할 규칙을 정의한 파일이다. Claude Code의 CLAUDE.md에 해당하는 개념으로, 에이전트의 "헌법" 또는 "시스템 프롬프트의 파일화"라고 이해하면 된다.

에이전트는 새로운 작업을 시작할 때마다 GEMINI.md를 먼저 읽고, 그 규칙들을 작업 전반에 적용한다. 개발자가 매번 "TypeScript strict 모드를 써줘", "Prisma ORM만 사용해줘" 같은 지시를 반복할 필요가 없다.

### 1.1 GEMINI.md가 없을 때의 문제

GEMINI.md 없이 에이전트에게 작업을 지시하면:

```
개발자: "users 모듈 CRUD 구현해줘"

에이전트 결과물 (GEMINI.md 없음):
- any 타입 사용 (TypeScript strict 무시)
- 직접 SQL 쿼리 사용 (Prisma 대신 pg 라이브러리)
- 영어 주석 (한국어 팀 프로젝트인데)
- 소프트 딜리트 미적용 (DB 설계 원칙 무시)
- camelCase 대신 snake_case 변수명
```

GEMINI.md를 잘 작성하면 에이전트가 처음부터 프로젝트 컨벤션에 맞는 코드를 생성한다.

### 1.2 GEMINI.md의 처리 방식

Antigravity 에이전트는 GEMINI.md를 단순히 텍스트로 읽는 것이 아니다. **AST(추상 구문 트리) 파싱**과 **시맨틱 청킹**을 통해 구조화된 규칙 집합으로 변환한다.

```
GEMINI.md 처리 파이프라인:

마크다운 텍스트
    ↓
AST 파싱 (헤더, 목록, 코드블록 구조화)
    ↓
시맨틱 청킹 (섹션별 의미 단위 분리)
    ↓
어노테이션 추출 (@must/@avoid/@prefer)
    ↓
규칙 우선순위 정렬
    ↓
에이전트 시스템 프롬프트에 주입
```

## 2. 파일 위치와 우선순위

GEMINI.md는 여러 위치에 존재할 수 있으며, 더 구체적인 경로의 파일이 더 높은 우선순위를 가진다.

### 2.1 위치 유형

```
우선순위 (낮음 → 높음):

1. 글로벌 GEMINI.md
   위치: ~/.gemini/GEMINI.md
   범위: 모든 프로젝트에 공통 적용
   용도: 개인 코딩 스타일, 선호 언어 설정

2. 프로젝트 루트 GEMINI.md
   위치: {프로젝트루트}/GEMINI.md
   범위: 해당 프로젝트 전체
   용도: 프로젝트 컨벤션, 기술 스택 규칙

3. 하위 폴더 GEMINI.md
   위치: {프로젝트루트}/src/GEMINI.md
          {프로젝트루트}/frontend/GEMINI.md
   범위: 해당 폴더 내 작업에만 적용
   용도: 특정 모듈/레이어의 세부 규칙
```

### 2.2 규칙 병합 방식

상위 규칙과 하위 규칙이 충돌하면 하위 규칙이 우선한다:

```
글로벌: @prefer 영어 변수명을 사용한다
프로젝트: @must 모든 변수명은 camelCase를 사용한다
frontend/: @prefer 컴포넌트 props는 PascalCase로 명명한다

→ frontend/ 작업 시: camelCase (프로젝트) + PascalCase props (하위)
→ backend/ 작업 시: camelCase (프로젝트)
```

### 2.3 분리 전략 — db.md / style.md

프로젝트가 커지면 GEMINI.md를 주제별로 분리하는 것이 좋다:

```
프로젝트 루트/
├── GEMINI.md          (메인 — 다른 파일을 @include)
├── docs/
│   ├── db.md          (DB 관련 규칙)
│   ├── style.md       (코딩 스타일 규칙)
│   ├── api.md         (API 설계 규칙)
│   └── security.md    (보안 규칙)
```

메인 GEMINI.md에서 include:
```markdown
# BoardHub 메인 규칙서

@include docs/db.md
@include docs/style.md
@include docs/api.md
@include docs/security.md

## 프로젝트 개요
...
```

## 4. @must / @avoid / @prefer 어노테이션 시스템

Antigravity GEMINI.md의 가장 강력한 기능은 어노테이션 시스템이다. *(공식 문서에서 확인 필요)*

### 4.1 @must — 강제 규칙

`@must`로 시작하는 규칙은 에이전트가 반드시 따라야 한다. 위반 시 에이전트는 스스로 오류를 감지하고 수정한다.

```markdown
@must TypeScript strict 모드를 사용한다 (tsconfig.json의 "strict": true)
@must 모든 DB 조작은 Prisma ORM을 통해서만 한다
@must 모든 API 엔드포인트에 swagger 데코레이터를 추가한다
@must 환경 변수는 반드시 .env 파일에서 ConfigService를 통해 읽는다
@must 새로운 Prisma 모델을 추가할 때마다 migration을 생성한다
@must 모든 서비스 메서드에 JSDoc 주석을 작성한다 (한국어)
@must 컨트롤러에서 직접 비즈니스 로직을 작성하지 않는다
@must 에러 응답은 항상 { success: false, message: string, code: string } 형식
@must 성공 응답은 항상 { success: true, data: T } 형식
```

### 4.2 @avoid — 금지 사항

`@avoid`로 시작하는 규칙은 절대 해서는 안 되는 것들이다.

```markdown
@avoid Prisma $queryRaw 사용 (직접 SQL 쿼리 금지)
@avoid any 타입 사용 (unknown 또는 구체적 타입 사용)
@avoid console.log 사용 (Logger 서비스 사용)
@avoid 하드코딩된 설정값 (환경 변수 사용)
@avoid DELETE 쿼리 직접 실행 (소프트 딜리트 정책 준수)
@avoid .env 파일을 Git에 커밋
@avoid 순환 의존성 (Circular dependency) 생성
@avoid 동기 파일 읽기 (fs.readFileSync → fs.readFile 사용)
```

### 4.3 @prefer — 권장 패턴

`@prefer`는 소프트 제약이다. 더 나은 방법이 있으면 따르되, 특별한 이유가 있을 때는 예외가 허용된다.

```markdown
@prefer SvelteKit의 server-side load 함수를 클라이언트 fetch보다 우선 사용한다
@prefer 유효성 검증에는 class-validator를 사용한다
@prefer 날짜 처리에는 date-fns 라이브러리를 사용한다 (moment.js 지양)
@prefer 에러 처리에 try-catch 대신 Result 패턴을 사용한다
@prefer 컴포넌트 파일명은 PascalCase, 유틸 파일명은 camelCase
@prefer 테스트 파일은 구현 파일 옆에 위치 (*.spec.ts)
```

## 핵심 강제 규칙 (@must)

@must TypeScript strict 모드를 항상 사용한다
@must 모든 DB 조작은 Prisma ORM을 통해서만 한다
@must 모든 API 엔드포인트에 @ApiOperation, @ApiResponse 데코레이터를 추가한다
@must 환경 변수는 반드시 ConfigService를 통해 읽는다 (process.env 직접 접근 금지)
@must 새로운 Prisma 모델 추가 시 반드시 migration 파일을 생성한다
@must 모든 서비스 메서드에 한국어 JSDoc 주석을 작성한다
@must 컨트롤러에서 비즈니스 로직을 작성하지 않는다 (서비스로 위임)
@must 성공 응답: { success: true, data: T, meta?: PageMeta }
@must 에러 응답: { success: false, message: string, code: string, statusCode: number }
@must 모든 날짜 필드는 UTC로 저장하고 ISO 8601 형식으로 반환한다
@must 파일 업로드 크기 제한: 이미지 5MB, 동영상 100MB
@must 인증이 필요한 API는 JwtAuthGuard를 적용한다
@must 관리자 전용 API는 RolesGuard + @Roles('ADMIN')을 적용한다

---

## 금지 사항 (@avoid)

@avoid Prisma $queryRaw, $executeRaw 사용 (보안 취약점)
@avoid any, unknown 타입의 광범위한 사용
@avoid console.log 사용 (Logger 서비스 주입 후 this.logger.log 사용)
@avoid 하드코딩된 설정값 (URL, 포트, 비밀키 등)
@avoid DELETE FROM 직접 실행 (소프트 딜리트: deletedAt 필드 업데이트)
@avoid .env, .env.local 파일을 Git에 커밋
@avoid 순환 의존성 (forwardRef 사용 최소화)
@avoid 동기 파일 I/O (fs.readFileSync, fs.writeFileSync)
@avoid moment.js 사용 (date-fns 사용)
@avoid lodash 전체 import (필요한 함수만 import)
@avoid 중첩 콜백 (async/await 사용)
@avoid 단일 파일에 300줄 초과 (파일 분리)

---

## 권장 패턴 (@prefer)

@prefer SvelteKit server-side load 함수를 클라이언트 fetch보다 우선 사용
@prefer class-validator + class-transformer를 유효성 검증에 사용
@prefer date-fns를 날짜 처리에 사용
@prefer 테스트 파일은 구현 파일 옆에 위치 (posts.service.spec.ts)
@prefer 컴포넌트 파일명은 PascalCase (PostCard.svelte)
@prefer 유틸 함수 파일명은 camelCase (formatDate.ts)
@prefer 에러 처리에 NestJS ExceptionFilter 활용
@prefer index.ts 배럴 파일로 모듈 공개 API 관리

## DB 규칙

### 소프트 딜리트 정책

모든 주요 엔티티는 소프트 딜리트를 적용한다:

```prisma
model Post {
  id        Int       @id @default(autoincrement())
  ...
  deletedAt DateTime? @map("deleted_at")
}
```

Prisma 미들웨어로 자동 필터링:
```typescript
// deletedAt이 있는 레코드는 기본 조회에서 제외
// Prisma v5에서는 $extends() 패턴 사용
const prismaWithSoftDelete = prisma.$extends({
  query: {
    $allModels: {
      async findMany({ args, query }) {
        args.where = { ...args.where, deletedAt: null };
        return query(args);
      },
    },
  },
});
```

### 페이지네이션 규칙

모든 목록 API는 커서 기반 페이지네이션 또는 오프셋 페이지네이션을 일관되게 사용한다:

```typescript
// 쿼리 파라미터 표준
interface PaginationQuery {
  page?: number;    // 기본값: 1
  limit?: number;   // 기본값: 20, 최대: 100
}

// 응답 메타 표준
interface PageMeta {
  total: number;
  page: number;
  limit: number;
  totalPages: number;
  hasNext: boolean;
  hasPrev: boolean;
}
```

## API 규칙

```
GET    /api/boards              게시판 목록

### 게시판 유형별 특수 처리

```

QNA      → answered, acceptedAnswerId 필드 추가

FAQ      → category 필드 필수
PRIVATE  → 작성자 + ADMIN만 열람 가능
ANONYMOUS → authorId null 허용
```

## 보안 규칙

@must 비밀번호는 bcrypt (rounds: 12)로 해싱
@must SQL Injection 방지: 모든 값은 Prisma 파라미터로 전달
@must XSS 방지: 사용자 입력은 sanitize-html로 정제 후 저장
@must CORS: 허용 Origin을 명시적으로 지정 (*)는 금지
@avoid JWT 토큰을 localStorage에 저장 (httpOnly 쿠키 사용)

## 테스트 규칙

@must 새로운 서비스 메서드마다 단위 테스트 작성

@prefer 통합 테스트보다 단위 테스트를 우선 작성
@prefer 테스트 데이터는 factory 함수로 생성 (faker.js 활용)

이 GEMINI.md는 80줄 이상의 실제 규칙을 포함한다.

## 6. 잘못 작성된 vs 올바른 GEMINI.md 비교 5가지

### 비교 1: 모호한 규칙 vs 구체적인 규칙

**잘못된 예:**
```markdown
- 코드를 잘 작성한다
- 보안에 신경쓴다
- 테스트를 작성한다
```

**올바른 예:**
```markdown
@must TypeScript strict 모드를 사용한다 (tsconfig.json: "strict": true)
@must 비밀번호는 bcrypt rounds: 12로 해싱한다
@must 단위 테스트 커버리지 90% 이상을 유지한다
```

### 비교 2: 기술 스택 미명시 vs 명시

**잘못된 예:**
```markdown
# 프로젝트 규칙
- 좋은 코드를 작성한다
```

**올바른 예:**
```markdown
# 기술 스택
- Backend: NestJS 11.x + TypeScript 5.x
- ORM: Prisma v5 (직접 SQL 금지)
- 패키지 관리: pnpm 9.x (npm, yarn 사용 금지)
```

### 비교 3: 충돌하는 규칙 vs 일관된 규칙

**잘못된 예:**
```markdown
@must 소프트 딜리트를 사용한다
@avoid 너무 복잡한 Prisma 쿼리
→ 소프트 딜리트는 Prisma 미들웨어가 필요한데 이를 "복잡한 쿼리"로 금지하면 충돌
```

**올바른 예:**
```markdown
@must 소프트 딜리트를 사용한다 (deletedAt 필드)
@must Prisma 미들웨어로 삭제된 레코드를 자동 필터링한다
@avoid 500줄 이상의 서비스 파일 (기능별 분리)
```

### 비교 4: 응답 형식 미정의 vs 명확한 정의

**잘못된 예:**
```markdown
- API 응답을 일관되게 한다
```

**올바른 예:**
```markdown
@must 성공 응답 형식:
  { "success": true, "data": T, "meta": PageMeta | null }
@must 에러 응답 형식:
  { "success": false, "message": string, "code": string, "statusCode": number }
@must HTTP 상태 코드: 200(조회), 201(생성), 400(입력오류), 401(인증), 403(권한), 404(없음)
```

### 비교 5: 너무 긴 규칙 vs 적절한 분리

**잘못된 예:**
```markdown
# 규칙 (500줄의 단일 파일)
... (너무 길어서 에이전트가 핵심을 놓침)
```

**올바른 예:**
```markdown
# GEMINI.md (메인)
@include docs/db.md
@include docs/style.md
@include docs/api.md

# 핵심 규칙 (가장 중요한 것만)
@must ...
@avoid ...
```
