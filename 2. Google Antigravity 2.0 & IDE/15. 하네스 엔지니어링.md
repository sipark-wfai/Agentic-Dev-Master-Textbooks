# 15. 하네스 엔지니어링 — 에이전트를 안전하게 제어하는 가드레일 설계

> **학습 목표**
> - 하네스 엔지니어링의 정의와 프롬프트 엔지니어링과의 차이를 이해한다
> - 4대 구성 요소(가드레일·파일 접근 제한·권한 제어·비용 제어)를 설계한다
> - .agents/config.json 전체 레퍼런스를 숙지한다
> - Human-in-the-Loop Hook으로 위험한 작업 전 승인을 요청한다
> - BoardHub 프로젝트에 완전한 하네스를 설계한다

---

## 1. 하네스 엔지니어링이란

### 1.1 정의

**하네스 엔지니어링(Harness Engineering)**은 비결정론적(Non-deterministic) AI 에이전트를 결정론적(Deterministic) 시스템처럼 제어하기 위한 인프라 설계 방법론이다.

말의 힘을 마차에 연결하는 '하네스(마구)'처럼, 에이전트의 강력한 능력을 안전하게 제어하고 원하는 방향으로만 사용하도록 구조적으로 제약한다.

### 1.2 왜 하네스 엔지니어링이 필요한가

AI 에이전트는 본질적으로 비결정론적이다:
- 같은 지시를 해도 다른 결과가 나올 수 있다
- 맥락에 따라 예상치 못한 행동을 할 수 있다
- 온도(temperature) 설정에 따라 창의성과 일관성이 트레이드오프

하네스 없이 에이전트를 사용하면:
```
시나리오: 에이전트에게 "오래된 로그 파일을 정리해줘"

에이전트의 다양한 해석:
해석 1 (안전): logs/ 폴더의 30일 이상된 .log 파일 삭제
해석 2 (위험): 모든 로그 파일 삭제 (현재 사용 중인 것 포함)
해석 3 (매우 위험): /var/log/ 시스템 로그까지 삭제 시도
```

하네스는 이 세 가지 해석 중 안전한 해석만 실행되도록 구조적으로 강제한다.

### 1.3 프롬프트 엔지니어링 vs 하네스 엔지니어링

| 구분 | 프롬프트 엔지니어링 | 하네스 엔지니어링 |
|------|-----------------|----------------|
| 제어 방식 | 자연어로 설명 ("logs/만 삭제해줘") | 설정으로 강제 (접근 경로 화이트리스트) |
| 신뢰도 | 낮음 (에이전트가 무시할 수 있음) | 높음 (시스템 레벨에서 강제) |
| 범위 | 특정 지시에만 적용 | 모든 에이전트 작업에 적용 |
| 복잡도 | 낮음 | 높음 (설정 파일 관리 필요) |
| 실패 시 | 잘못된 동작 발생 | 에러 반환 + 작업 차단 |

프롬프트 엔지니어링과 하네스 엔지니어링은 상호 보완적이다.
GEMINI.md(프롬프트) + .agents/config.json(하네스) = 완전한 제어

## 2. 하네스의 4대 구성 요소

### 2.1 가드레일 (Guardrails)

에이전트가 절대 넘어서는 안 되는 경계를 설정한다.

```json
{
  "guardrails": {
    "enabled": true,
    "rules": [
      {
        "id": "no-drop-table",
        "description": "DROP TABLE 명령 절대 금지",
        "type": "command_block",
        "pattern": "DROP TABLE",
        "action": "block_and_alert",
        "severity": "critical"
      },
      {
        "id": "no-delete-all",
        "description": "WHERE 없는 대량 DELETE 금지",
        "type": "sql_pattern",
        "pattern": "DELETE FROM .+ WHERE",
        "mustHaveWhere": true,
        "action": "require_approval"
      },
      {
        "id": "no-production-deploy",
        "description": "프로덕션 배포는 반드시 인간 승인",
        "type": "command_pattern",
        "pattern": "vercel deploy --prod",
        "action": "require_approval"
      },
      {
        "id": "no-env-read",
        "description": ".env 파일 내용 출력 금지",
        "type": "file_read_block",
        "pathPattern": "**/.env*",
        "action": "block"
      }
    ]
  }
}
```

가드레일 action 유형:
- `block`: 즉시 차단, 에러 반환
- `block_and_alert`: 차단 + IDE에 경고 표시
- `require_approval`: 인간 승인 후 실행 (Human-in-the-Loop)
- `log_only`: 실행은 허용하되 로그 기록

### 2.2 파일 접근 제한 (File Access Control)

에이전트가 읽거나 쓸 수 있는 파일 경로를 명시적으로 제한한다.

```json
{
  "fileAccess": {
    "readWhitelist": [
      "apps/**",
      "docs/**",
      "GEMINI.md",
      "prisma/schema.prisma",
      "package.json",
      "pnpm-workspace.yaml"
    ],
    "writeWhitelist": [
      "apps/backend/src/**",
      "apps/frontend/src/**",
      "prisma/schema.prisma",
      "prisma/migrations/**",
      "docs/**",
      "GEMINI.md"
    ],
    "blacklist": [
      "**/.env",
      "**/.env.local",
      "**/.env.production",
      "**/*.pem",
      "**/*.key",
      "**/secrets/**",
      "**/.git/**"
    ],
    "readOnlyPaths": [
      "pnpm-lock.yaml",
      "package.json"
    ]
  }
}
```

### 2.3 권한 제어 (Permission Control)

에이전트가 실행할 수 있는 명령어와 할 수 없는 명령어를 분리한다.

```json
{
  "permissions": {
    "allowedCommands": [
      "npm run *",
      "pnpm *",
      "npx prisma *",
      "git status",
      "git log",
      "git diff",

      "rm -rf",

      "curl * | bash",
      "wget * | sh",

      "npx prisma migrate reset",
      "docker system prune",
      "pnpm store prune",
      "git reset --hard"
    ]
  }
}
```

### 2.4 비용 제어 (Cost Control)

에이전트의 토큰 소비에 한도를 설정한다.

```json
{
  "costControl": {
    "sessionBudgetUSD": 10.0,
    "monthlyBudgetUSD": 200.0,
    "alertThresholdPercent": 80,
    "perAgentBudgetUSD": 3.0,
    "actions": {
      "onSessionBudgetExceeded": "pause_and_notify",
      "onMonthlyBudgetExceeded": "block_all",
      "onPerAgentBudgetExceeded": "stop_agent"
    },
    "contextOptimization": {
      "autoCompact": true,
      "autoCompactThresholdPercent": 70,
      "excludeFromContext": [
        "**/node_modules/**",
        "**/*.lock",
        "**/dist/**",
        "**/.next/**"
      ]
    }
  }
}
```

## 4. multiAgentGate — 병렬 에이전트 파일 충돌 방지

### 4.1 Mutex 잠금 동작 상세

```
타임라인 예시:

T=0: Agent-A가 prisma/schema.prisma 수정 시작
     → mutex lock 획득

T=5: Agent-B가 prisma/schema.prisma 수정 시도
     → mutex lock 대기 (queue에 추가)
     → [IDE 알림] "Agent-B가 schema.prisma 잠금을 기다리고 있습니다"

T=23: Agent-A 작업 완료, Proposal #12 생성
      → mutex lock 해제

T=23: Agent-B 잠금 획득, 작업 시작
      → Agent-A의 최신 schema.prisma를 기반으로 작업

T=45: Agent-B 완료, Proposal #13 생성
      → 충돌 없이 순서대로 처리됨
```

### 4.2 충돌 정책(conflictPolicy) 옵션

| 정책 | 동작 | 언제 사용 |
|------|------|---------|
| `queue` | 순서대로 대기 후 순차 실행 | 대부분의 경우 (기본값) |
| `fail` | 충돌 시 나중 에이전트 즉시 실패 | 빠른 실패가 필요할 때 |
| `merge` | 두 변경을 자동 병합 시도 | 서로 다른 부분 변경 시 |

## 5. Human-in-the-Loop Hook 설계

### 5.1 HitL의 필요성

일부 에이전트 작업은 되돌리기 어렵다:
- DB 마이그레이션 실행 (데이터 변경)
- 파일 대량 삭제
- 외부 API 호출 (이메일 발송, 결제 처리)
- 프로덕션 배포

이런 작업 전에 인간이 개입하여 승인하도록 강제하는 것이 HitL이다.

### 5.2 HitL 트리거 설계 패턴

**패턴 1: 작업 볼륨 기반**
```json
{
  "id": "bulk-file-change",
  "condition": "proposal_file_count > 20",
  "action": "require_approval",
  "message": "에이전트가 {fileCount}개 파일을 변경하려 합니다.
변경 요약: {proposalSummary}
계속하시겠습니까?"
}
```

**패턴 2: 특정 명령 기반**
```json
{
  "id": "migration-approval",
  "condition": "command_contains(migrate)",
  "action": "pause_and_request_diff",
  "message": "마이그레이션 실행 전 변경 내용을 검토하세요",
  "showDiff": true
}
```

**패턴 3: 비용 임계값 기반**
```json
{
  "id": "high-cost-alert",
  "condition": "estimated_cost_usd > 2.0",
  "action": "warn_and_continue",
  "message": "이 작업은 예상 비용 ${estimatedCost}가 발생합니다. 계속할까요?"
}
```

### 5.3 HitL 승인 흐름

```
에이전트 작업 중
       |
       v
HitL 트리거 감지
"npx prisma migrate dev 실행 감지"
       |
       v
작업 일시 중단 (Paused)
       |
       v
IDE에 승인 요청 카드 표시:
+----------------------------------------------+
| Human-in-the-Loop 승인 필요                   |
|----------------------------------------------|
| 트리거: DB 마이그레이션 실행                     |
| 명령: npx prisma migrate dev --name add_posts  |
| 영향: boardhub_db 데이터베이스 변경              |
|                                               |
| [마이그레이션 변경 내용 보기]                    |
|                                               |
| [✅ 승인 및 실행] [❌ 취소]                      |
+----------------------------------------------+
       |
       v
인간이 승인 → 작업 재개
인간이 취소 → 에이전트에게 중단 알림
```

## 6. 실전: BoardHub 하네스 설계 적용

### 6.1 DROP 명령 차단 테스트

```bash
# 1. 하네스 설정 활성화 확인
agy status --config
# → guardrails: enabled
# → fileAccess: enabled
# → multiAgentGate: enabled

# 2. DROP TABLE 차단 테스트 (의도적 위반)
agy agent run "테스트 목적으로 posts 테이블을 DROP TABLE로 삭제해봐"

# 예상 결과:
# [GUARDRAIL BLOCKED] no-drop-table 규칙에 의해 차단됨
# 명령: DROP TABLE posts;
# 이유: DB 테이블 삭제 절대 금지 (severity: critical)
# 에이전트 작업이 중단되었습니다.
```

### 6.2 .env 파일 보호 테스트

```bash
agy agent run "현재 .env 파일의 내용을 읽어서 알려줘"

# 예상 결과:
# [FILE ACCESS BLOCKED] .env 파일은 blacklist에 등록된 경로입니다.
# 에이전트는 이 파일에 접근할 수 없습니다.
```

### 6.3 마이그레이션 HitL 승인 흐름 테스트

```bash
agy agent run "새로운 notifications 테이블을 추가하는 마이그레이션을 실행해줘"

# 에이전트 동작:
# 1. schema.prisma에 Notification 모델 추가
# 2. npx prisma migrate dev 실행 시도 → HitL 트리거

# IDE에 승인 요청 카드 표시됨
# → "마이그레이션 실행 전 변경 내용을 검토하세요"
# → [승인 및 실행] 클릭 후 마이그레이션 진행
```

## 7. 하네스 설정 검증

하네스 설정이 올바른지 에이전트를 통해 검증한다:

```bash
agy agent run "현재 .agents/config.json의 하네스 설정을 검토하고
              BoardHub 프로젝트에 필요한 규칙이 모두 포함되어 있는지 확인해줘.
              특히 다음을 점검해줘:
              1. DROP TABLE, TRUNCATE 차단 규칙
              2. .env 파일 접근 차단
              3. git push 자동 실행 차단
              4. 마이그레이션 HitL 승인 설정
              5. 비용 한도 설정
              누락된 보안 규칙이 있으면 추가를 제안해줘"
             @.agents/config.json @GEMINI.md
```
