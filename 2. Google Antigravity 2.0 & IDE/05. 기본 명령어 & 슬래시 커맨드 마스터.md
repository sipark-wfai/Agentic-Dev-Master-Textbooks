# 05. 기본 명령어 & 슬래시 커맨드 마스터 — Antigravity를 자유자재로 조종하는 법

> **학습 목표**
> - ag CLI 명령어 전체를 숙지하고 상황별로 올바른 명령어를 선택한다
> - IDE 채팅 슬래시 커맨드(/ask, /code, /review 등)를 자유자재로 사용한다
> - 컨텍스트 지시어(@파일경로)로 에이전트의 맥락을 정밀하게 제어한다
> - 실전 시나리오 10가지에서 최적의 명령어 조합을 적용한다
> - 비용을 최소화하는 명령어 전략을 익힌다

## 1. ag CLI 명령어 완전 정리

agy CLI는 Go 언어로 빌드된 초경량 도구로, 터미널과 CI/CD 파이프라인에서 Antigravity의 모든 기능을 제어한다.

### 1.1 시스템 상태 관련 명령어

```bash
# 버전 확인
agy --version
# → Antigravity CLI v2.0.4 (darwin/arm64)

# 전체 시스템 상태 확인
agy status
# → Daemon: Running | Sandbox: Ready | Gemini: Connected

# 상태 상세 출력
agy status --verbose
# → Daemon PID, 메모리 사용량, 실행 중인 에이전트 수, 비용 등

# 도움말
agy help
agy help agent    # 특정 명령어 도움말
agy help sandbox
```

### 1.2 데몬 관련 명령어

```bash
# 데몬 시작
agy daemon start

# 데몬 중지
agy daemon stop

# 데몬 재시작 (설정 변경 후 사용)
agy daemon restart

# 데몬 상태만 확인
agy daemon status

# 데몬 로그 실시간 스트리밍
agy daemon logs --follow

# 데몬 로그 (최근 100줄)
agy daemon logs --tail 100

# 데몬 설정 조회
agy daemon config
```

### 1.3 샌드박스 관련 명령어

```bash
# 샌드박스 시작
agy sandbox start

# 샌드박스 중지
agy sandbox stop

# 샌드박스 상태 확인
agy sandbox status

# 샌드박스 재초기화 (완전 초기화, 모든 임시 파일 삭제)
agy sandbox reset

# 샌드박스 내부 셸 직접 접근 (디버깅용)
agy sandbox shell

# 샌드박스 파일 목록
agy sandbox ls /workspace/

# 샌드박스에서 명령 직접 실행
agy sandbox exec "ls -la /workspace/"
agy sandbox exec "npm run test"

# 샌드박스 리소스 사용량 확인
agy sandbox resources
# → CPU: 23%, Memory: 1.2GB/4GB, Disk: 2.1GB/20GB
```

### 1.4 에이전트 실행 관련 명령어

```bash
# 에이전트 실행 (기본)
agy agent run "지시사항"

# 에이전트 실행 (특정 파일 첨부)
agy agent run "이 파일을 리뷰해줘" --file src/users/users.service.ts

# 에이전트 실행 (여러 파일 첨부)
agy agent run "이 두 파일의 의존성 문제를 해결해줘" \
  --file src/users/users.service.ts \
  --file src/auth/auth.service.ts

# 에이전트 실행 (비대화형 모드 — CI/CD용)
agy agent run "테스트 실패 원인을 찾아 수정해줘" --non-interactive

# 에이전트 실행 (타임아웃 설정)
agy agent run "전체 프로젝트 테스트 실행 및 수정" --timeout 600

# 실행 중인 에이전트 목록
agy agent list
# → [running] agent-abc123: "users 모듈 구현" (2m 34s)
# → [waiting] agent-xyz789: "posts 모듈 구현" (큐 대기)

# 특정 에이전트 상태 확인
agy agent status agent-abc123

# 에이전트 작업 완료 대기
agy agent wait agent-abc123
agy agent wait agent-abc123 --timeout 300

# 에이전트 강제 중지
agy agent stop agent-abc123

# 모든 에이전트 중지
agy agent stop --all

# 에이전트 실행 로그 확인
agy logs agent-abc123
agy logs agent-abc123 --follow    # 실시간 스트리밍
agy logs agent-abc123 --tail 50   # 최근 50줄
```

## 2. IDE 슬래시 커맨드 완전 정리

IDE 채팅창에서 사용하는 슬래시 커맨드는 에이전트와 상호작용하는 주요 수단이다.

### 2.1 질문/상담 명령어 — /ask

`/ask`는 파일을 수정하지 않고 순수하게 질문·상담할 때 사용한다. 토큰 소비가 적다.

```
# 기본 사용
/ask "이 프로젝트에서 순환 의존성이 발생할 수 있는 위험 요소는?"

# 파일 첨부
/ask "이 서비스의 성능 병목이 어디에 있는가?" @src/posts/posts.service.ts

# 복잡한 질문
/ask "PostgreSQL 16의 Row Level Security를 사용해서
      비공개 문의 게시판을 구현하는 게 나을까,
      아니면 애플리케이션 레벨에서 처리하는 게 나을까?
      BoardHub 프로젝트 맥락에서 장단점을 비교해줘"
```

### 2.2 코드 생성/수정 명령어 — /code

`/code`는 실제 코드를 생성하거나 수정할 때 사용한다. Proposal 카드가 발행된다.

```
# 파일 생성
/code "users 모듈의 UsersService를 구현해줘"

# 특정 파일 수정
/code "이 서비스에 findByEmail 메서드를 추가해줘" @src/users/users.service.ts

# 여러 파일에 걸친 변경
/code "모든 서비스 파일에 LoggingInterceptor를 적용해줘" @src/

# 조건부 구현
/code "갤러리 게시판일 때만 이미지 유효성 검증을 추가해줘.
       @prisma/schema.prisma 의 BoardType enum을 참고해"
```

### 2.3 코드 리뷰 명령어 — /review

`/review`는 코드의 품질, 버그, 보안 취약점을 검토한다. 파일을 수정하지 않는다.

```
# 현재 열린 파일 리뷰
/review

# 특정 파일 리뷰
/review @src/auth/auth.service.ts

# 리뷰 초점 지정
/review "보안 취약점 관점에서 리뷰해줘" @src/auth/

# 코드 리뷰 결과 예시
# → 1. [HIGH] JWT 토큰을 localStorage에 저장하고 있음 → httpOnly 쿠키로 변경 필요
# → 2. [MEDIUM] bcrypt rounds가 10임 → 12 이상 권장
# → 3. [LOW] refresh token 만료 처리 누락
```

### 2.4 테스트 생성 명령어 — /test

`/test`는 구현 파일에 대한 테스트 코드를 자동 생성한다.

```
# 현재 파일 테스트 생성
/test

# 특정 파일 테스트 생성
/test @src/users/users.service.ts

# 테스트 유형 지정
/test "단위 테스트와 통합 테스트를 모두 작성해줘" @src/posts/posts.service.ts

# 커버리지 목표 지정
/test "커버리지 95% 이상을 목표로 테스트 작성해줘" @src/auth/auth.service.ts
```

### 2.5 문서 생성 명령어 — /doc

`/doc`는 코드에서 문서를 자동 생성한다.

```
# JSDoc 주석 생성
/doc @src/users/users.service.ts

# API 문서 생성 (Swagger 기반)
/doc "이 컨트롤러에 Swagger 데코레이터를 추가해줘" @src/users/users.controller.ts

# README 생성
/doc "이 모듈의 README.md를 작성해줘" @src/users/
```

### 2.6 오류 수정 명령어 — /fix

`/fix`는 오류 메시지를 기반으로 자동 수정한다.

```
# 현재 에디터의 오류 수정
/fix

# 특정 오류 메시지 붙여넣기
/fix "Error: Cannot find module 'src/common/filters/http-exception.filter'"

# TypeScript 타입 오류 수정
/fix "Type 'string | undefined' is not assignable to type 'string'" @src/users/

# 빌드 오류 수정
/fix "빌드 오류를 모두 수정해줘. 아래는 에러 로그야:
      [오류 로그 붙여넣기]"
```

### 2.7 리팩터링 명령어 — /refactor

`/refactor`는 기존 코드의 구조를 개선한다.

```
# 일반 리팩터링
/refactor @src/posts/posts.service.ts

# 목적 지정
/refactor "이 함수를 SOLID 원칙에 맞게 분리해줘" @src/users/users.service.ts

# 패턴 적용
/refactor "Repository 패턴을 적용해줘" @src/posts/
```

### 2.8 설명 명령어 — /explain

`/explain`은 코드의 동작 방식을 설명한다. 파일을 수정하지 않는다.

```
# 코드 설명
/explain @src/auth/jwt.strategy.ts

# 특정 부분 집중 설명
/explain "이 Prisma 미들웨어가 어떻게 소프트 딜리트를 구현하는지 설명해줘"
          @src/prisma/prisma.service.ts

# 복잡한 로직 설명
/explain "JWT access token과 refresh token의 순환 갱신 로직을 설명해줘"
```

### 2.9 컨텍스트 초기화 명령어 — /compact

```
# 컨텍스트 윈도우 정리 (긴 세션 후 사용)
/compact
```

에이전트가 대화 이력을 요약하고 핵심 정보만 유지한다. 토큰 비용을 줄이는 데 효과적이다.

### 2.10 메모리 확인 명령어 — /memory

```
# 현재 GEMINI.md 규칙 확인
/memory

# 특정 규칙 검색
/memory "소프트 딜리트"
```

## 3. 컨텍스트 지시어 (@파일경로)

에이전트에게 특정 파일이나 폴더를 맥락으로 제공하는 방법이다.

### 3.1 단일 파일 지정

```
/review @src/auth/auth.service.ts

# 실제로 에이전트가 수행하는 작업:
# 1. filesystem-mcp로 해당 파일 내용 읽기
# 2. 컨텍스트에 파일 내용 포함
# 3. 리뷰 수행
```

### 3.2 여러 파일 지정

```
/ask "이 세 파일 사이의 의존성 관계를 다이어그램으로 설명해줘"
     @src/users/users.module.ts
     @src/auth/auth.module.ts
     @src/posts/posts.module.ts
```

### 3.3 폴더 전체 지정

```
/review "보안 취약점을 찾아줘" @src/auth/

# 주의: 폴더 내 파일이 많으면 토큰을 많이 사용함
# 필요한 파일만 명시적으로 지정하는 것이 효율적
```

### 3.4 URL 지정 (문서 참조)

```
/ask "이 공식 문서를 참고해서 NestJS Throttler를 설정해줘"
     @https://docs.nestjs.com/security/rate-limiting
```

### 3.5 Prisma 스키마 자동 참조

GEMINI.md에 설정하거나, 직접 명시:

```
/code "Post 모델 기반으로 PostsService를 구현해줘"
      @prisma/schema.prisma
```

## 4. 멀티라인 입력 방법

긴 지시사항은 멀티라인으로 입력하는 것이 좋다.

### IDE 채팅에서 멀티라인 입력

```
Shift+Enter   줄바꿈 (전송 안 됨)
Enter         전송
```

### 긴 지시사항 예시

```
/code "다음 명세에 따라 PostsService를 구현해줘:

1. findAll(boardId, page, limit): 특정 게시판의 게시글 목록 (커서 페이지네이션)
2. findOne(postId): 게시글 상세 (조회수 증가 포함)
3. create(boardId, createPostDto, authorId): 게시글 작성
4. update(postId, updatePostDto, requesterId): 게시글 수정 (작성자만)
5. remove(postId, requesterId): 소프트 딜리트 (작성자 또는 관리자)

조건:
- GALLERY 타입: 이미지 필수 첨부 검증
- PRIVATE 타입: 작성자와 ADMIN만 조회 가능
- VIDEO 타입: 동영상 필수 첨부 검증
- 모든 조회는 deletedAt이 null인 레코드만 반환

@prisma/schema.prisma 참고"
```

## 5. 실전 시나리오별 명령어 조합 10가지

### 시나리오 1: 새 모듈 시작

```bash
# CLI: 프로젝트 디렉터리 이동 후 에이전트 실행
cd ~/projects/boardhub

# IDE 채팅:
/ask "현재 프로젝트 구조를 파악하고 boards 모듈 구현 방법을 제안해줘"
/code "boards 모듈 기본 골격을 생성해줘 (모듈, 컨트롤러, 서비스)"
```

### 시나리오 2: 기존 코드 리팩터링

```
/review @src/posts/posts.service.ts
# → 리뷰 결과 확인

/ask "제안된 리팩터링 중 어떤 것을 우선 적용해야 할까?"
# → 우선순위 확인

/refactor "findAll 메서드를 Repository 패턴으로 분리해줘"
           @src/posts/posts.service.ts
```

### 시나리오 3: 버그 수정

```bash
# 1. 버그 재현 후 에러 로그 복사
# 2. IDE 채팅에서:
/fix "다음 오류를 수정해줘:
      TypeError: Cannot read properties of undefined (reading 'id')
      at PostsService.findOne (src/posts/posts.service.ts:45:23)"

# 3. Proposal 확인 후 Accept
```

### 시나리오 4: 테스트 작성

```
/test @src/users/users.service.ts
# → 기본 테스트 생성

/ask "생성된 테스트에서 갤러리 게시판의 이미지 필수 검증 테스트가 빠져 있다. 추가해줄 수 있나?"

/code "갤러리 게시판 이미지 필수 검증 테스트를 추가해줘"
      @src/posts/posts.service.spec.ts
      @src/posts/posts.service.ts
```

### 시나리오 5: API 문서화

```
/doc "Swagger 데코레이터를 추가해줘. 특히 응답 타입과 에러 케이스를 포함해줘"
     @src/posts/posts.controller.ts
```

### 시나리오 6: 성능 최적화

```
/ask "이 쿼리에서 N+1 문제가 발생할 수 있는 부분을 찾아줘"
     @src/posts/posts.service.ts

/code "N+1 문제를 Prisma include로 해결해줘"
      @src/posts/posts.service.ts
```

### 시나리오 7: 전체 빌드 오류 수정

```bash
# 터미널에서 빌드 실행
agy agent run "npm run build 명령을 실행하고 발생하는 모든 TypeScript 오류를 수정해줘"

# 완료 후 Proposal 확인
agy proposal list
agy proposal accept --all
```

### 시나리오 8: 코드 리뷰 자동화 (CI/CD)

```bash
# GitHub Actions에서 자동 코드 리뷰
agy agent run "변경된 파일들을 리뷰하고 문제점을 GitHub PR 코멘트로 작성해줘" \
  --non-interactive \
  --timeout 120
```

### 시나리오 9: 멀티에이전트 병렬 구현

```bash
# 에이전트 1: 백엔드 모듈
agy agent run "comments 모듈 (NestJS) 구현" &

# 에이전트 2: 프론트엔드 컴포넌트

```

/compact

# 핵심 맥락만 다시 제공:

## 6. 비용 절약을 위한 명령어 전략

### 6.1 /ask vs /code 선택 기준

| 상황 | 사용 명령어 | 이유 |
|------|-----------|------|
| 방향성 검토 | /ask | 코드 생성 없이 조언만 받음 |
| 구현 결정 후 | /code | 실제 코드 생성 |
| 오류 이해 | /ask | 수정 전 원인 파악 |
| 수정 실행 | /fix | 타겟 수정 |

### 6.2 컨텍스트 최소화 전략

```
# 비효율적: 큰 폴더 전체 포함
/review @src/

# 효율적: 필요한 파일만 지정
/review @src/posts/posts.service.ts @src/posts/posts.controller.ts
```

### 6.3 /compact 활용 타이밍

```
# 컨텍스트 사용량이 70% 이상일 때 /compact 실행
# IDE 비용 게이지에서 확인: 140,000/200,000 토큰 초과 시

/compact
```

### 6.4 작업 단위 분할

```
# 비효율적: 한 번에 모든 것을 요청
/code "전체 백엔드 API를 구현해줘"  # 토큰 폭발

# 효율적: 단계적으로 분할
/code "users 모듈만 구현해줘"
# → Accept 후
/code "boards 모듈 구현해줘"
# → Accept 후
/code "posts 모듈 구현해줘"
```
