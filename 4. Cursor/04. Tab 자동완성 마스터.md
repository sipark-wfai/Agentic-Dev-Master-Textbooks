## 1. Tab이란: 예측 편집 (Predictive Editing)

### 1.1 단순 자동완성과의 차이

기존 IDE의 자동완성(IntelliSense)은 현재 타이핑 중인 단어를 완성한다. `get`을 타이핑하면 `getUser`, `getPost` 같은 메서드명을 제안한다. 이것은 **단어 수준**의 완성이다.

Cursor Tab은 다르다. **다음에 올 코드 블록 전체**를 예측한다. 함수 시그니처를 작성하면 함수 구현체 전체를, 테스트 한 개를 작성하면 다음 테스트 케이스 전체를, DTO 필드 하나를 추가하면 연관된 모든 필드를 예측한다.

```typescript
// 개발자가 타이핑한 것 (2줄)
async function createPost(dto: CreatePostDto): Promise<Post> {
  // [여기서 Tab]

// Cursor Tab이 제안하는 것 (10줄+ 전체)
async function createPost(dto: CreatePostDto): Promise<Post> {
  const board = await this.prisma.board.findUnique({
    where: { id: dto.boardId },
  });
  if (!board) {
    throw new NotFoundException('게시판을 찾을 수 없습니다');
  }
  return this.prisma.post.create({
    data: {
      ...dto,
      authorId: dto.authorId,
    },
    include: { author: true, board: true },
  });
}
```

### 1.2 GitHub Copilot Tab과의 차이

| 항목 | GitHub Copilot Tab | Cursor Tab |
|------|-------------------|------------|
| 컨텍스트 | 열린 파일 위주 | 프로젝트 전체 인덱싱 |
| 제안 범위 | 현재 줄~몇 줄 | 멀티라인, 멀티블록 |
| Rules 반영 | 없음 | .cursor/rules 반영 |
| 최근 편집 반영 | 제한적 | 최근 편집 이력 학습 |
| 프로젝트 패턴 | 현재 파일 기반 | 프로젝트 전체 패턴 학습 |
| Fast Request 소비 | 별도 구독 | 소비 없음 (무제한) |

### 1.3 Tab 동작 원리

Cursor Tab이 제안을 생성할 때 다음 신호를 종합적으로 분석한다.

```
1. 커서 위치와 주변 코드 (현재 파일)
2. 최근 편집 이력 (방금 뭘 만들었는가?)
3. .cursor/rules (프로젝트 규칙)
4. 코드베이스 인덱스 (프로젝트 전체 패턴)
5. 열려 있는 다른 탭 파일
6. 파일 임포트 구조
```

이 신호들을 조합하여 "개발자가 다음에 하려는 것"을 예측한다.

## 2. Tab 수락 방법

### 2.1 세 가지 수락 방식

```
Tab         → 회색 제안 전체를 한 번에 수락
Opt+→ (macOS) / Ctrl+→ (Windows/Linux)  → 단어 하나씩 수락 <!-- R3 수정: macOS 우선 표기 -->
Esc         → 제안 거절 (현재 제안 무시)
```

### 2.2 실전 사용 패턴

```typescript
// 상황: prisma.post.findMany를 타이핑 중
// Cursor가 다음을 제안한다:
await prisma.post.findMany({
  where: {
    boardId: dto.boardId,
    deletedAt: null,
  },
  include: {
    author: { select: { id: true, name: true } },
    _count: { select: { comments: true } },
  },
  orderBy: { createdAt: 'desc' },
  skip: (page - 1) * limit,
  take: limit,
});

// 전체가 좋으면: Tab (한 번에 수락)
// "where"까지만 쓰고 싶으면:
//   "await prisma.post.findMany({"까지 제안 → Ctrl+→로 단어씩 수락
// 제안이 마음에 안 들면: Esc
```

### 2.3 부분 수락 전략

제안 전체를 수락하지 않고 원하는 부분까지만 수락하는 전략이다.

```typescript
// Cursor 제안:
const { data, meta } = await postService.findAll({
  boardId: params.boardId,
  page: searchParams.get('page') ?? '1',
  limit: searchParams.get('limit') ?? '20',
});

// "const { data, meta }"까지만 수락하고 싶다면:
// Ctrl+→를 반복하여 단어 단위로 수락
// 또는 Tab으로 전체 수락 후 불필요한 부분 삭제 (대부분의 경우 이게 더 빠름)
```

## 3. Tab이 잘 작동하는 10가지 패턴

### 패턴 1: 함수 시그니처 → 구현체

함수 시그니처를 완성하고 `{` 이후 Tab을 누르면 구현체를 제안한다.

```typescript
// NestJS 서비스 예시
async findPostsByBoard(
  boardId: string,
  paginationDto: PaginationDto
): Promise<PaginatedResult<Post>> {
  // [Tab] → 아래 전체 제안
  const { page = 1, limit = 20 } = paginationDto;
  const where = { boardId, deletedAt: null };
  
  const [data, total] = await this.prisma.$transaction([
    this.prisma.post.findMany({
      where,
      skip: (page - 1) * limit,
      take: limit,
      orderBy: { createdAt: 'desc' },
      include: { author: { select: { id: true, name: true } } },
    }),
    this.prisma.post.count({ where }),
  ]);

  return {
    data,
    meta: { page, limit, total, totalPages: Math.ceil(total / limit) },
  };
}
```

### 패턴 2: 비슷한 DTO 연속 생성

한 DTO를 만든 후, 다음 DTO를 만들 때 패턴을 학습하여 제안한다.

```typescript
// CreatePostDto를 작성한 후
export class CreatePostDto {
  @IsString()
  @MinLength(2)
  @MaxLength(100)
  title: string;

  @IsString()
  @MinLength(10)
  content: string;

  @IsUUID()
  boardId: string;
}

// UpdatePostDto 파일에서 "export class Update" 타이핑 후 Tab
export class UpdatePostDto {
  @IsString()
  @IsOptional()
  @MinLength(2)
  @MaxLength(100)
  title?: string;

  @IsString()
  @IsOptional()
  @MinLength(10)
  content?: string;
}
// ← CreatePostDto 패턴을 학습하여 Optional 필드로 제안
```

첫 번째 테스트를 작성하면 두 번째 테스트를 예측하여 제안한다.


### 패턴 4: Import 구문 자동 완성

사용하지 않은 클래스/함수를 코드에서 참조하면 import 구문을 제안한다.

```typescript
// 파일 상단에 import가 없는 상태에서
// "this.jwtService" 를 타이핑하면
// 파일 상단에 자동으로:

import { JwtService } from '@nestjs/jwt';
// ← Tab 한 번으로 import 구문 추가
```

### 패턴 5: 컨트롤러 엔드포인트 연속 생성

하나의 엔드포인트를 만들면 나머지 CRUD 엔드포인트를 패턴으로 제안한다.

```typescript
@Controller('posts')
@UseGuards(JwtAuthGuard)
export class PostController {
  constructor(private readonly postService: PostService) {}

  @Get()
  findAll(@Query() query: PaginationDto) {
    return this.postService.findAll(query);
  }

  // [Tab] → 아래 제안
  @Get(':id')
  findOne(@Param('id') id: string) {
    return this.postService.findOne(id);
  }

  // [Tab] → 또 제안
  @Post()
  create(@Body() createPostDto: CreatePostDto, @Request() req) {
    return this.postService.create(createPostDto, req.user.id);
  }

  // [Tab] → 계속 제안
  @Patch(':id')
  update(@Param('id') id: string, @Body() updatePostDto: UpdatePostDto) {
    return this.postService.update(id, updatePostDto);
  }

  @Delete(':id')
  remove(@Param('id') id: string) {
    return this.postService.remove(id);
  }
}
```

### 패턴 6: SvelteKit 컴포넌트 구조

```svelte
<!-- BoardCard.svelte 작성 시작 후 Tab -->
<script lang="ts">
  import type { Board } from '$lib/types';
  
  export let board: Board;
  // [Tab] → 나머지 props와 함수 제안
  export let onSelect: (board: Board) => void = () => {};
  
  function handleClick() {
    onSelect(board);
  }

<!-- [Tab] → 템플릿 전체 제안 -->
<div
  class="rounded-lg border border-gray-200 p-4 cursor-pointer hover:border-blue-500 transition"

  tabindex="0"

  <p class="text-sm text-gray-500 mt-1">{board.description}</p>
  <div class="flex items-center gap-2 mt-2 text-xs text-gray-400">
    <span>{board._count?.posts ?? 0}개 게시글</span>
  </div>
</div>
```

### 패턴 7: Prisma 스키마 모델 연속 생성

하나의 모델을 작성하면 다음 모델을 패턴으로 제안한다.

```prisma
model User {
  id        String    @id @default(cuid())
  email     String    @unique
  name      String
  role      Role      @default(USER)
  posts     Post[]
  comments  Comment[]
  createdAt DateTime  @default(now())
  updatedAt DateTime  @updatedAt
  deletedAt DateTime?
}

// [Tab] → 다음 모델 제안
model Post {
  id        String    @id @default(cuid())
  title     String
  content   String    @db.Text
  boardId   String
  authorId  String
  board     Board     @relation(fields: [boardId], references: [id])
  author    User      @relation(fields: [authorId], references: [id])
  comments  Comment[]
  createdAt DateTime  @default(now())
  updatedAt DateTime  @updatedAt
  deletedAt DateTime?
}
```

### 패턴 8: 환경변수 접근 패턴

`.env` 파일의 변수명을 기억하고 `process.env.` 이후를 제안한다.

```typescript
// .env 파일에 다음이 있는 경우:
// JWT_SECRET=...
// JWT_EXPIRES_IN=15m
// JWT_REFRESH_EXPIRES_IN=7d

// 코드에서 process.env. 타이핑 후 Tab
const secret = process.env.JWT_SECRET;  // ← Tab 제안

```

### 패턴 9: 타입 가드 함수

Union 타입을 사용할 때 타입 가드 함수를 제안한다.

```typescript
type BoardContent = TextPost | GalleryPost | PollPost;

// "function is" 타이핑 후 Tab
function isGalleryPost(post: BoardContent): post is GalleryPost {
  return post.type === 'GALLERY';
}

// [Tab] → 다음 타입 가드 제안
function isPollPost(post: BoardContent): post is PollPost {
  return post.type === 'POLL';
}
```

### 패턴 10: 에러 처리 일관성 적용

한 곳에서 에러 처리 패턴을 사용하면 다른 곳에서도 동일 패턴을 제안한다.

```typescript
// findPost에서 에러 처리를 이렇게 했다면
async findPost(id: string): Promise<Post> {
  const post = await this.prisma.post.findUnique({
    where: { id, deletedAt: null },
  });
  if (!post) {
    throw new NotFoundException(`게시글 ID ${id}를 찾을 수 없습니다`);
  }
  return post;
}

// findBoard에서 Tab → 동일 패턴으로 제안
async findBoard(id: string): Promise<Board> {
  const board = await this.prisma.board.findUnique({
    where: { id, deletedAt: null },
  });
  if (!board) {
    throw new NotFoundException(`게시판 ID ${id}를 찾을 수 없습니다`);
  }
  return board;
}
```

## 4. Tab을 더 잘 작동시키는 방법

### 4.1 Rules에 패턴 명시

```markdown
# .cursor/rules
## 코드 패턴
- 모든 서비스 메서드는 findById 헬퍼로 엔티티를 찾은 후 작업
- 페이지네이션은 항상 { data, meta } 구조로 반환
- NestJS 컨트롤러는 CRUD 순서로: findAll → findOne → create → update → remove
```

### 4.2 일관된 코딩 패턴 유지

비슷한 코드를 항상 같은 방식으로 작성하면 Tab이 그 패턴을 학습한다.

```typescript
// 항상 이 순서로 작성하면
// 1. where 조건
// 2. include 관계
// 3. orderBy
// 4. skip/take

// Tab이 다음번에 자동으로 이 순서로 제안한다
```

### 4.3 주석으로 의도 전달

코드 블록 위에 주석으로 의도를 설명하면 Tab이 더 정확한 제안을 한다.

```typescript

// 소프트 삭제된 게시글은 수정 불가

  // [Tab] → 위 주석을 반영한 정확한 구현체 제안
```

## 5. Tab 거절이 필요한 상황

### 5.1 제안이 잘못된 경우

```typescript
// 상황: findUser를 만들려고 함
// Cursor Tab이 잘못된 제안을 할 때

async findUser(id: string) {
  // Tab 제안:
  return this.prisma.post.findUnique({ where: { id } }); // ← 잘못된 테이블!
  
  // → Esc로 거절하고 직접 입력:
  return this.prisma.user.findUnique({ where: { id } });
}
```

### 5.2 패턴이 달라야 하는 경우

```typescript
// 대부분의 메서드는 소프트 삭제를 필터링하지만
// 관리자 조회는 모든 데이터를 봐야 하는 경우
async findAllForAdmin(id: string) {
  // Tab은 deletedAt: null 조건을 자동으로 넣지만
  // 이 메서드는 삭제된 데이터도 봐야 함
  // → Esc 후 직접 작성
  return this.prisma.post.findMany(); // 소프트 삭제 필터 없음
}
```

### 5.3 Tab 거절 판단 기준

```
✓ Tab 수락: 제안이 Rules와 일치하고 의도와 같을 때
✗ Tab 거절: 
  - 잘못된 테이블/필드 참조
  - 금지된 패턴 사용 (any, console.log)
  - 의도와 다른 로직
  - 과도하게 복잡한 제안 (간단한 코드가 적합할 때)
```

## 6. 비용: Tab은 Fast Request를 소비하지 않는다

### 6.1 중요한 사실

**Tab은 Fast Request 한도를 소비하지 않는다.** Pro 요금제에서 Tab을 하루에 수백 번 사용해도 Fast Request 500회 한도와 전혀 관계없다.

```
Fast Request 소비 여부:
- Tab: ✗ (소비 안 함, 무제한)
- Cmd+K (Inline Edit): 소량 소비
- Chat (Cmd+L): Fast Request 소비
- Agent (Composer): Fast Request 소비
```

### 6.2 비용 최적화 전략

이 사실을 활용하면 비용을 크게 절약할 수 있다.

```
전략 1: Tab을 최대한 활용
- 반복적인 코드 패턴은 무조건 Tab으로 생성
- 보일러플레이트 (DTO, Controller, Service 구조) = Tab

전략 2: 복잡한 로직만 Chat/Agent로
- 알고리즘, 비즈니스 로직 = Chat
- 멀티파일 기능 구현 = Agent

결과:
Tab 70% + Cmd+K 20% + Chat 10% 비율로 사용 시
Fast Request 사용량 대폭 감소
```
