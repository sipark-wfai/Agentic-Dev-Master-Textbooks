# 03. Cursor Rules 작성 완벽 가이드

> **학습 목표**
> - Cursor Rules의 역할과 적용 범위를 이해한다
> - Always On·Auto Attached·Manual 적용 방식의 차이를 구분한다
> - 멀티 게시판 프로젝트에 적합한 Rules를 직접 작성한다
> - 역할별 Rules 분리 전략과 Notepads 활용법을 익힌다

---

## 1. Cursor Rules란

### 1.1 정의

Cursor Rules는 AI에게 **프로젝트의 모든 것을 알려주는 설명서**다. AI는 Rules를 읽고 이 프로젝트에서 어떻게 코드를 작성해야 하는지, 어떤 기술 스택을 쓰는지, 어떤 규칙을 따라야 하는지를 항상 기억한다.

다른 AI 도구와 비교하면:
- Claude Code의 `CLAUDE.md`와 동일한 역할
- Gemini의 `GEMINI.md`와 동일한 역할
- GitHub Copilot의 `.github/copilot-instructions.md`와 동일한 역할

하지만 Cursor Rules는 파일 경로별로 적용 범위를 세밀하게 조정할 수 있어 더 강력하다.

### 1.2 Rules가 없는 Cursor vs Rules가 있는 Cursor

```
Rules 없는 경우:
개발자: "UserService에 findAll 메서드를 추가해줘"
AI: "알겠습니다! 어떤 라이브러리를 사용하나요? 
    TypeScript 쓰나요? 에러 처리는 어떻게 하나요?"
→ 매번 반복 설명 필요

Rules 있는 경우:
개발자: "UserService에 findAll 메서드를 추가해줘"
AI: "NestJS + Prisma v5 기반으로 findAll 메서드를 추가합니다.
    PaginationDto를 사용하고, SoftDelete 필터를 자동 적용합니다."
→ 프로젝트 컨텍스트 완벽 이해
```

## 2. 파일 위치와 적용 범위

### 2.1 파일 경로별 적용 범위

| 파일 경로 | 적용 범위 | 사용 시나리오 |
|-----------|-----------|---------------|
| `.cursor/rules/*.mdc` (alwaysApply: true) | 현재 프로젝트 전체 | 프로젝트 공통 규칙 | <!-- R3 수정: .mdc 확장자, alwaysApply frontmatter 사용 -->
| `.cursor/rules/backend.mdc` | 특정 패턴 파일에 자동 첨부 | 백엔드 전용 규칙 | <!-- R3 수정: .md → .mdc -->
| `.cursor/rules/frontend.mdc` | 특정 패턴 파일에 자동 첨부 | 프론트엔드 전용 규칙 | <!-- R3 수정: .md → .mdc -->
| `~/.cursor/rules/` (UI 설정 또는 파일) | 모든 프로젝트 (글로벌) | 개인 코딩 스타일 |

### 2.2 디렉토리 구조

```
multi-board-hub/
├── .cursor/
│   └── rules/
│       ├── project.mdc    ← 프로젝트 전체 규칙 (alwaysApply: true) <!-- R3 수정 -->
│       ├── backend.mdc    ← 백엔드 파일에만 적용 (.mdc 확장자) <!-- R3 수정 -->
│       ├── frontend.mdc   ← 프론트엔드 파일에만 적용 <!-- R3 수정 -->
│       └── database.mdc   ← Prisma 파일에만 적용 <!-- R3 수정 -->
└── ...
```

### 2.3 글로벌 Rules

개인 모든 프로젝트에 공통으로 적용하고 싶은 규칙은 글로벌 Rules에 작성한다.

```markdown
# ~/.cursor/rules (글로벌 - 모든 프로젝트에 적용)

## 내 코딩 스타일
- TypeScript strict 모드 항상 사용
- 함수형 프로그래밍 선호 (클래스보다 함수)
- 변수명: camelCase, 상수: UPPER_SNAKE_CASE
- 모든 public API에 JSDoc 필수
- 에러는 절대 무시하지 않음 (catch 후 throw 또는 로깅)

## 선호하는 패턴
- async/await (Promise.then 사용 안 함)
- 옵셔널 체이닝 (?.) 적극 사용
- 타입 단언(as) 대신 타입 가드 사용
```

## 3. Rules 적용 방식

### 3.1 Always On

<!-- R3 수정: Always On 방식은 .mdc 파일에 alwaysApply: true frontmatter로 설정 -->
`.cursor/rules/*.mdc` 파일에 `alwaysApply: true` frontmatter를 추가하면 항상 AI 컨텍스트에 포함된다. 모든 Chat, Inline Edit, Agent 실행 시 자동으로 읽힌다.

```markdown
---
alwaysApply: true
---
# project.mdc (항상 AI에게 제공)
# 이 파일은 항상 AI에게 제공된다
```

### 3.2 Auto Attached (파일 패턴 매칭)

<!-- R3 수정: .mdc 확장자 사용, alwaysApply 대신 globs frontmatter로 Auto Attached 설정 -->
`.cursor/rules/*.mdc` 파일은 글로브 패턴으로 특정 파일이 컨텍스트에 포함될 때 자동으로 첨부된다.

```markdown
# .cursor/rules/backend.mdc
# 파일 상단에 패턴 지정
---
globs: ["apps/backend/**/*.ts", "**/*.controller.ts", "**/*.service.ts"]
---

## 백엔드 규칙
NestJS 10.x 기반 백엔드 규칙...
```

### 3.3 Manual (@멘션으로 직접 참조)

`@Notepads`나 특정 Rules 파일을 Chat에서 직접 멘션하여 필요할 때만 사용한다.

```
Chat에서:
"@Notepads api-conventions 참조해서 새 엔드포인트 만들어줘"
```

## 4. Rules 작성 원칙

### 4.1 간결하고 측정 가능하게

```markdown
# 나쁜 예 (모호함)
- 코드를 깔끔하게 작성한다
- 좋은 에러 처리를 한다
- 성능을 고려한다

# 좋은 예 (구체적, 측정 가능)
- 함수당 최대 50줄 (초과 시 분리)
- 모든 async 함수에 try-catch 또는 NestJS ExceptionFilter 사용
- 배열 조회 시 인덱스 명시, N+1 쿼리 금지
```

### 4.2 AI가 실행할 수 있는 지시

```markdown
# 나쁜 예 (AI가 판단해야 함)
- 적절한 타입을 사용한다

# 좋은 예 (AI가 즉시 실행 가능)
- any 타입 사용 금지, unknown 또는 명시적 타입 사용
- API 응답 타입은 반드시 interface로 정의하고 dto/ 폴더에 저장
```

### 4.3 금지 사항은 명확하게

```markdown
## 금지 사항 (절대 위반 금지)
- console.log() 프로덕션 코드에 사용 금지 (Logger 서비스 사용)
- @ts-ignore, @ts-nocheck 사용 금지
- any 타입 사용 금지
- 하드코딩된 URL·비밀키·비밀번호 금지
- 동기 파일 I/O (fs.readFileSync 등) 금지
```

### 4.4 빌드·테스트 명령어 포함

```markdown
## 명령어
빌드: pnpm build
테스트: pnpm test
린트: pnpm lint
포맷: pnpm format
DB 마이그레이션: pnpm prisma migrate dev
DB 시드: pnpm prisma db seed
```

## 5. 멀티 게시판 프로젝트 전체 Rules 예시

### 5.1 메인 Rules 파일

```markdown
# .cursor/rules

## 프로젝트 개요
멀티 게시판 허브 - 8가지 유형의 게시판을 제공하는 풀스택 웹 애플리케이션

## 기술 스택
- 프론트엔드: SvelteKit 2.x + TypeScript + Tailwind CSS v3
- 백엔드: NestJS 10.x + TypeScript
- 데이터베이스: PostgreSQL 16 + Prisma v5
- 인증: JWT (Access Token 15분 + Refresh Token 7일)
- 파일 업로드: Multer + S3 호환 스토리지
- 패키지 매니저: pnpm (workspaces 모노레포)
- 컨테이너: Docker + Docker Compose

## 프로젝트 구조
```
multi-board-hub/
├── apps/
│   ├── frontend/          # SvelteKit 앱 (포트 5173)
│   └── backend/           # NestJS 앱 (포트 3000)
│       └── prisma/
│           └── schema.prisma
├── docs/
│   ├── prd.md
│   ├── erd.md
│   └── api.md
├── .cursor/rules          # 이 파일
└── docker-compose.yml
```

## 게시판 유형 (BoardType enum)
- NOTICE: 공지사항 (관리자만 작성)
- FREE: 자유게시판
- QNA: Q&A (채택 기능)
- GALLERY: 갤러리 (이미지 필수)
- FILE: 자료실 (파일 첨부 필수)
- NEWS: 뉴스 (외부 링크)
- POLL: 투표
- SECRET: 비밀게시판

## 사용자 역할 (Role enum)
- SUPER_ADMIN: 시스템 최고 관리자
- BOARD_ADMIN: 게시판 관리자
- USER: 일반 사용자
- GUEST: 비회원 (읽기 전용)

## TypeScript 규칙
- strict 모드 필수 (tsconfig.json strict: true)
- any 타입 절대 금지 → unknown 또는 명시적 타입 사용
- @ts-ignore, @ts-nocheck 절대 금지
- 타입 단언(as Type) 최소화, 타입 가드 함수 사용
- 모든 public 메서드에 JSDoc 주석 필수
- 인터페이스명: PascalCase + I 접두어 없음 (예: User, Post)
- DTO: {동작}{엔티티}Dto (예: CreatePostDto, UpdateBoardDto)

## 코딩 컨벤션
- 파일명: kebab-case (예: auth.service.ts, board-list.svelte)
- 함수명: camelCase (예: findAll, createPost)
- 클래스명: PascalCase (예: AuthService, BoardController)
- 상수: UPPER_SNAKE_CASE (예: JWT_SECRET, MAX_FILE_SIZE)
- 줄 길이: 최대 100자
- 들여쓰기: 2 spaces (탭 사용 안 함)
- 따옴표: 작은따옴표 (')
- 세미콜론: 사용
- trailing comma: es5

## 에러 처리
- NestJS: HttpException 또는 내장 Exception 클래스 사용
  - NotFoundException, BadRequestException, UnauthorizedException
- SvelteKit: error() 헬퍼 함수 사용
- 절대로 빈 catch 블록 금지 (최소한 Logger.error 호출)
- 사용자에게 노출되는 에러 메시지는 한국어로

## 금지 사항
- console.log() 프로덕션 코드 사용 금지 → NestJS Logger 또는 SvelteKit logger
- 하드코딩된 비밀키·URL·비밀번호 금지 → .env 파일 사용
- @ts-ignore, @ts-nocheck 사용 금지
- any 타입 사용 금지
- N+1 쿼리 금지 (Prisma include/select 사용)
- 동기 I/O 금지 (fs.readFileSync 등)
- 미완성 코드 커밋 금지 (TODO, FIXME 제거 후 커밋)

## Prisma 규칙
- 모든 테이블에 softDelete 적용 (deletedAt: DateTime?)
- 모든 테이블에 createdAt, updatedAt 자동 관리
- 관계 설정 시 cascade 옵션 명시
- 마이그레이션 명: 동사_명사 형식 (예: add_refresh_token)

## API 규칙
- REST API: /api/v1/{리소스} 형식
- 응답 형식:
  성공: { data: T, meta?: PaginationMeta }
  에러: { error: string, message: string, statusCode: number }
- HTTP 메서드: GET(조회), POST(생성), PATCH(수정), DELETE(삭제)
- 페이지네이션: ?page=1&limit=20 (기본값)

## 명령어
- 개발 서버 실행: pnpm dev
- 빌드: pnpm build
- 테스트: pnpm test
- 린트 + 포맷: pnpm lint && pnpm format
- DB 마이그레이션: cd apps/backend && pnpm prisma migrate dev
- DB 초기화: cd apps/backend && pnpm prisma db seed
- Docker 실행: docker-compose up -d
```

### 5.2 백엔드 전용 Rules

```markdown
# .cursor/rules/backend.md
---
globs: ["apps/backend/**/*.ts"]
---

## NestJS 아키텍처 패턴

### 모듈 구조
각 기능은 다음 파일로 구성:
- {기능}.module.ts
- {기능}.controller.ts
- {기능}.service.ts
- dto/create-{기능}.dto.ts
- dto/update-{기능}.dto.ts
- entities/{기능}.entity.ts (Prisma 타입 재사용 권장)

### 의존성 주입
- 서비스는 constructor 주입 사용
- circular dependency 금지

### 인증/인가
- @UseGuards(JwtAuthGuard): 로그인 필요 엔드포인트
- @UseGuards(JwtAuthGuard, RolesGuard): 역할 기반 접근
- @Roles(Role.BOARD_ADMIN): 역할 지정

### Prisma 사용법
- PrismaService를 통해서만 DB 접근
- 소프트 삭제 미들웨어 자동 적용 (where deletedAt is null)
- 트랜잭션: prisma.$transaction([...]) 사용

### DTO 유효성 검사
- class-validator 사용: @IsString(), @IsEmail(), @MinLength()
- class-transformer 사용: @Transform(), @Exclude()
- 모든 DTO 필드에 유효성 검사 데코레이터 필수
```

### 5.3 프론트엔드 전용 Rules

```markdown
# .cursor/rules/frontend.md
---
globs: ["apps/frontend/**/*.svelte", "apps/frontend/**/*.ts"]
---

## SvelteKit 패턴

### 라우팅
- 파일 기반 라우팅 (src/routes/)
- 동적 라우트: [board_id], [post_id]
- 레이아웃: +layout.svelte
- 서버 사이드: +page.server.ts (민감한 데이터)
- 클라이언트: +page.svelte

### 상태 관리
- Svelte 스토어 사용 (src/lib/stores/)
- 인증 상태: authStore (token, user)
- 전역 상태 최소화, 로컬 상태 우선

### API 호출
- src/lib/api/ 폴더의 함수 사용
- fetch 직접 사용 금지 → apiClient 래퍼 사용
- 에러는 error() 헬퍼로 처리

### 컴포넌트
- 파일명: PascalCase.svelte (예: BoardCard.svelte)
- Props는 명시적 타입 지정
- 이벤트: createEventDispatcher 사용
- Tailwind 클래스: 최대 10개, 초과 시 컴포넌트 분리
```

## 6. 잘못 작성된 vs 올바른 Rules 비교

### 비교 1: 기술 스택 명시

```markdown
# 나쁜 예
## 기술 스택
최신 기술을 사용한다.

# 좋은 예
## 기술 스택
- 프론트엔드: SvelteKit 2.x (TypeScript, Tailwind CSS v3)
- 백엔드: NestJS 10.x (TypeScript, class-validator)
- DB: PostgreSQL 16 + Prisma v5
- 인증: JWT (jsonwebtoken 9.x)
```

### 비교 2: 에러 처리 규칙

```markdown
# 나쁜 예
에러를 적절히 처리한다.

# 좋은 예
- NestJS에서는 반드시 HttpException 서브클래스 사용
  - 404: throw new NotFoundException('게시글을 찾을 수 없습니다')
  - 401: throw new UnauthorizedException('로그인이 필요합니다')
  - 400: throw new BadRequestException('잘못된 요청입니다')
- 빈 catch 블록 절대 금지
- 에러 메시지는 사용자 대상은 한국어, 로그는 영어
```

### 비교 3: 네이밍 컨벤션

```markdown
# 나쁜 예
변수명을 의미 있게 작성한다.

# 좋은 예
- 파일명: kebab-case (board-list.svelte, auth.service.ts)
- 변수/함수: camelCase (userId, findPostById)
- 클래스/인터페이스: PascalCase (UserService, CreatePostDto)
- 상수: UPPER_SNAKE_CASE (MAX_FILE_SIZE, JWT_EXPIRES_IN)
- Prisma 모델명: PascalCase (User, Post, Board)
- DB 컬럼명: snake_case (created_at, board_id, deleted_at)
```

### 비교 4: 금지 사항

```markdown
# 나쁜 예
나쁜 코드를 작성하지 않는다.

# 좋은 예
## 절대 금지
- any 타입: any 대신 unknown 또는 명시적 타입
- 하드코딩 비밀키: process.env.JWT_SECRET 사용
- console.log: Logger.log(), Logger.error() 사용
- @ts-ignore: 타입 오류는 타입 시스템으로 해결
- N+1 쿼리: 관계 데이터는 include로 한번에 조회
```

### 비교 5: 완료 기준

```markdown
# 나쁜 예
코드가 동작하도록 한다.

# 좋은 예
## 작업 완료 기준
1. pnpm build 에러 없음
2. TypeScript 타입 에러 없음
3. ESLint 경고 없음
4. 유닛 테스트 통과 (pnpm test)
5. API 엔드포인트는 Swagger에 자동 문서화됨
```

## 7. Notepads: 반복 컨텍스트 저장

### 7.1 Notepads란

Notepads는 자주 사용하는 컨텍스트를 저장해두고 `@Notepads`로 참조하는 기능이다. Rules는 항상 적용되지만, Notepads는 필요할 때만 선택적으로 포함한다.

### 7.2 Notepads 생성 방법

```
1. Cmd+Shift+P → "Cursor: Open Notepads"
2. 또는 Chat 패널 → Notepads 아이콘

## 8. Rules 품질 체크리스트

완성된 Rules를 다음 기준으로 검토한다.

```
필수 항목:
[ ] 프로젝트 이름과 목적이 한 줄로 설명되어 있다
[ ] 기술 스택이 버전 포함하여 명시되어 있다
[ ] 프로젝트 폴더 구조가 포함되어 있다
[ ] TypeScript 규칙이 구체적이다 (any 금지 등)
[ ] 금지 사항이 명확하다 (최소 5가지)
[ ] 에러 처리 방식이 명시되어 있다
[ ] 빌드/테스트 명령어가 있다

권장 항목:
[ ] 네이밍 컨벤션이 예시와 함께 있다
[ ] API 응답 형식이 명시되어 있다
[ ] DB 패턴이 명시되어 있다 (Prisma 사용법 등)
[ ] 완료 기준이 명시되어 있다

검증:
[ ] Rules를 읽은 후 AI가 올바른 기술 스택으로 코드를 생성하는가?
[ ] AI가 금지된 패턴(any, console.log)을 사용하지 않는가?
[ ] AI가 프로젝트 구조를 올바르게 이해하는가?
```

### 9.2 Rules 적용 확인

```
1. Cursor에서 Chat 열기 (Cmd+L)
2. 입력: "이 프로젝트의 기술 스택이 뭐야?"
3. AI가 Rules에서 읽은 정확한 기술 스택을 답해야 함

4. 입력: "User 서비스에 findAll 메서드를 추가해줘"
5. AI가 NestJS + Prisma v5 기반으로 올바른 코드를 생성해야 함
6. any 타입, console.log가 없는지 확인
```

### 9.3 Rules 업데이트 전략

Rules는 프로젝트 진행에 따라 업데이트한다.

```
초기 (개발 시작): 기본 스택, 컨벤션
중기 (기능 추가): 새로운 패턴, 발견된 금지 사항 추가
완성 (배포 준비): 배포 규칙, 성능 기준 추가

Git 커밋 메시지:
feat(rules): 게시판 CRUD 패턴 추가
fix(rules): 소프트 삭제 규칙 명확화
```
