## 1. Agent(Composer)란

### 1.1 Chat과 Agent의 근본적 차이

Chat(Cmd+L)은 AI와 대화하며 개발자가 Apply를 클릭해야 코드가 적용된다. 반면 Agent(Composer)는 **스스로 파일을 읽고, 계획을 세우고, 코드를 작성하고, 수정하는 자율 에이전트**다.

```
Chat 흐름:
개발자 → 지시 → AI 응답 → 개발자 Apply 클릭 → 코드 적용
(매 단계 개발자 개입 필요)

Agent 흐름:
개발자 → 목표 지정 → Agent 자율 실행 → 완료 후 검토 요청
(Agent가 여러 파일을 알아서 작업)
```

### 1.2 Agent가 할 수 있는 것

```
✓ 여러 파일을 동시에 읽고 이해
✓ 새 파일 생성
✓ 기존 파일 수정
✓ 파일 삭제 (승인 후)
✓ 터미널 명령어 실행 (설정 시)
✓ 에러 발생 시 자체 수정 시도
✓ 변경 파일 목록 제공
✓ 각 변경 사항에 대한 설명 제공
```

### 1.3 언제 Agent를 사용하는가

```
Agent 적합:
✓ 새로운 기능 전체 구현 (모듈 단위)
✓ 전체 리팩터링
✓ 여러 파일에 걸친 버그 수정
✓ 새 프로젝트 기본 구조 생성
✓ 테스트 코드 일괄 생성

Chat/Cmd+K 적합:
✓ 단일 파일 수정
✓ 짧은 코드 조각 생성
✓ 코드 설명 요청
✓ 빠른 질문/답변
```

## 2. Agent 실행 방법

### 2.1 Composer 탭 열기

```
방법 1: Cmd+I
방법 2: 에디터 우측 상단 [Composer] 아이콘 클릭
방법 3: View 메뉴 → Composer
방법 4: Cmd+L로 Chat 열기 → 상단 [Composer] 탭 선택
```

### 2.2 Agent 모드 vs Normal 모드

Composer에는 두 가지 모드가 있다.

```
Normal 모드: Chat과 유사, 파일 수정 제안만 함
Agent 모드: 자율적으로 파일을 읽고 수정

Agent 모드 활성화:
Composer 하단 → [Agent] 토글 클릭 (또는 기본값으로 설정)
```

## 3. Agent 작동 원리

### 3.1 4단계 실행 흐름

```
1단계: 파일 읽기
Agent가 @멘션된 파일, 관련 파일, .cursor/rules를 읽음
"이 프로젝트의 구조를 파악합니다..."

2단계: 계획 수립
변경할 파일 목록과 각 파일에서 할 작업을 계획
"다음 파일을 수정합니다:
- prisma/schema.prisma: User, Post, Board 모델 추가
- src/prisma/prisma.service.ts: 소프트 삭제 미들웨어
- src/app.module.ts: PrismaModule 등록"

3단계: 코드 작성
파일을 하나씩 수정하며 진행 상황을 실시간 표시

4단계: 검토 요청
"모든 변경을 완료했습니다. 검토해주세요."
변경 파일 목록과 각 파일의 diff 표시
```

### 3.2 변경 파일 목록 확인

Agent 완료 후 Composer 패널에서 변경된 모든 파일이 나열된다.

```
변경된 파일 (5개):
✓ prisma/schema.prisma          [+148줄]
✓ src/prisma/prisma.service.ts  [+45줄]
✓ src/app.module.ts             [+3줄]
✓ src/prisma/prisma.module.ts   [새 파일]
✓ .env.example                  [+8줄]
```

### 3.3 개별 수락/거절

```
각 파일 옆의 [✓] [✗] 아이콘:
✓ Accept: 해당 파일의 변경 수락
✗ Reject: 해당 파일의 변경 거절 (원래 상태로 되돌림)

[Accept All]: 모든 파일 변경 수락
[Reject All]: 모든 변경 취소

개별 파일 클릭 → diff 상세 보기 → 줄 단위 수락/거절
```

## 4. Background Agent

### 4.1 Background Agent란

일반 Agent는 Composer 패널이 열려 있는 동안 실행된다. Background Agent는 **백그라운드에서 독립적으로 실행**되어, 개발자가 다른 작업을 하는 동안 Agent가 큰 태스크를 처리한다.

```
Background Agent 활성화:
Cursor Settings → Features → Background Agent → Enable

실행 방법:
Composer에서 지시문 작성 후 [Run in Background] 버튼 클릭
또는 Composer → [⋮] 메뉴 → "Run in Background"

완료 시:
시스템 알림 또는 Cursor 알림으로 완료 통보
```

### 4.2 Background Agent 활용 시나리오

```
시나리오 1: 대규모 리팩터링
"전체 코드베이스에서 any 타입을 모두 찾아서 적절한 타입으로 교체해줘"
→ Background Agent로 실행
→ 개발자는 다른 기능 작업
→ 30분 후 완료 알림

시나리오 2: 테스트 코드 일괄 생성
"모든 서비스 파일에 대한 단위 테스트를 작성해줘"
→ Background Agent로 실행
→ 개발자는 프론트엔드 작업
→ 완료 후 검토
```

### 4.3 Background Agent + Computer Use 통합 (2026년 2월)

<!-- R4 수정: 2026년 2월 Background Agent에 Computer Use 통합 추가 -->

2026년 2월 업데이트로 Background Agent에 **Computer Use**가 통합되었다. Cloud Agent(오프머신 실행)가 브라우저·터미널·GUI 앱을 직접 조작할 수 있게 되었다.

```
Computer Use 통합 기능:
- 브라우저 자동 조작: 웹 앱 E2E 테스트 자동화
- 터미널 명령 실행: 빌드·배포·DB 마이그레이션
- GUI 앱 조작: 디자인 툴, 문서 편집 등

활용 예:
"로그인 페이지를 열고 회원가입 E2E 테스트를 실행한 뒤 스크린샷을 첨부해줘"
→ Background Agent가 브라우저를 열고 직접 테스트 수행
→ 결과 스크린샷 + 로그 자동 첨부
```

### 4.4 BugBot Autofix

<!-- R4 수정: BugBot Autofix 기능(해결률 ~80%) 추가 -->

Agent 모드와 연동되는 **BugBot Autofix**는 GitHub PR에서 발견된 이슈를 자동으로 수정하는 기능이다.

```
BugBot Autofix 동작 방식:
1. GitHub PR 생성 시 BugBot이 자동으로 코드 리뷰
2. 버그·보안 취약점·성능 이슈 감지
3. Autofix 버튼 클릭 → Agent가 자동으로 수정 PR 생성
4. 해결률 약 80% (경쟁 제품 대비 15%p 높음)

설정: Cursor Settings → Features → BugBot → Enable GitHub Integration
```

## 5. Agent 지시문 작성 패턴 10가지

### 패턴 1: 명확한 목표 설정

```
나쁜 지시문:
"인증 기능을 만들어줘"

좋은 지시문:
"JWT 기반 회원가입/로그인 기능을 구현해줘.
- 회원가입: 이메일, 비밀번호, 이름
- 로그인: 이메일+비밀번호 → accessToken(15분) + refreshToken(7일) 반환
- Access Token 재발급: refreshToken으로 새 accessToken 발급
- 로그아웃: refreshToken DB에서 삭제"
```

### 패턴 2: 범위 제한

```
"@Files apps/backend/src/auth/ 이 폴더 안에서만 작업해줘.
다른 모듈 파일은 수정하지 마.
AuthModule을 app.module.ts에 등록하는 것만 예외로 허용해."
```

### 패턴 3: 참조 파일 지정

```
"@Files docs/erd.md ERD를 참조해서
@Files apps/backend/prisma/schema.prisma Prisma 스키마를 작성해줘.
ERD에 있는 모든 엔티티와 관계를 정확히 반영해야 해."
```

### 패턴 4: 완료 기준 명시

```
"게시글 CRUD API를 구현해줘.
완료 기준:
1. pnpm build 에러 없음
2. 모든 엔드포인트에 @ApiOperation 데코레이터 있음
3. DTO에 class-validator 데코레이터 적용
4. TypeScript 타입 에러 없음
이 기준을 충족하지 못하면 스스로 수정해."
```

### 패턴 5: 기존 패턴 유지

```
"@Files apps/backend/src/board/board.service.ts
이 파일의 패턴과 스타일을 그대로 유지하면서
PostService를 비슷한 구조로 만들어줘.
새로 패턴을 만들지 말고 기존 패턴을 복제해."
```

### 패턴 6: 단계별 실행 지시

```
"다음 순서로 작업해줘:
1단계: Prisma 스키마에 Comment 모델 추가
2단계: prisma migrate dev 실행 (가능한 경우)
3단계: CommentService 생성 (PostService 패턴 참조)
4단계: CommentController 생성
5단계: CommentModule 생성 및 AppModule 등록

각 단계를 완료한 후 다음 단계로 넘어가."
```

### 패턴 7: 예외 케이스 명시

```
"게시판 타입별로 다른 업로드 처리 로직을 구현해줘.
- GALLERY: 이미지만 허용 (jpg, png, gif, webp), 최대 10MB
- FILE: 모든 파일 허용, 최대 50MB
- 그 외 게시판: 파일 업로드 불가 → BadRequestException

예외: SECRET 게시판은 파일 업로드 자체를 차단해야 해."
```

### 패턴 8: 기존 코드와 충돌 방지

```
"현재 구현된 내용을 먼저 확인하고,
@Files apps/backend/src/ 이미 구현된 기능과 중복되지 않게 해줘.
기존 코드를 삭제하거나 변경하지 말고, 추가만 해줘."
```

### 패턴 9: 성능 고려 사항 포함

```
"게시글 목록 API를 최적화해줘.
- 페이지당 20개, cursor-based pagination 사용
- 작성자 정보는 id, name만 select (전체 조회 금지)
- 댓글 수는 _count 사용 (댓글 전체 조회 금지)
- 자주 필터링되는 boardId, deletedAt에 인덱스 추가"
```

### 패턴 10: 테스트 포함 지시

```
"PostService를 구현하고, 동시에 테스트 코드도 작성해줘.
각 public 메서드마다:
1. 정상 동작 테스트
2. 존재하지 않는 ID로 조회 시 NotFoundException 테스트
3. 권한 없는 사용자의 수정 시도 ForbiddenException 테스트"
```

## 6. Agent를 멈춰야 할 때

### 6.1 중지 방법

```
방법 1: Esc 키
방법 2: Composer 패널의 [Stop] 버튼 클릭
방법 3: 실행 중인 Terminal 프로세스가 있으면 Ctrl+C
```

### 6.2 언제 멈춰야 하는가

```
중지 필요 상황:
- Agent가 잘못된 파일을 수정하기 시작했을 때
- 예상과 다른 방향으로 진행될 때
- Agent가 허가받지 않은 작업 (외부 API 호출 등)을 시도할 때
- 무한 루프에 빠진 것 같을 때 (10분 이상 진행 없음)
- 치명적인 파일 (schema.prisma 등)을 잘못 수정하려 할 때
```

### 6.3 중지 후 복구

```bash
# Agent가 잘못 수정한 경우 Git으로 복구
git diff  # 변경 내용 확인
git checkout -- .  # 모든 변경 취소
git checkout -- src/specific-file.ts  # 특정 파일만 복구
```

## 7. Agent 오류 발생 시 처리

### 7.1 빌드 오류 발생

```
Agent 완료 후 빌드 오류가 발생하면:
1. 오류 메시지를 복사
2. Composer에 붙여넣기: "빌드 오류가 발생했어. 수정해줘: [오류 메시지]"
3. Agent가 오류를 분석하고 자체 수정

또는 Agent 설정에서:
"완료 후 pnpm build를 실행하고 오류가 있으면 자체 수정해줘"
```

### 7.2 TypeScript 타입 오류

```
Agent가 생성한 코드에 타입 오류가 있는 경우:
"@Files [오류 발생 파일] TypeScript 타입 오류를 수정해줘.
오류 내용: [tsc 출력 붙여넣기]"
```

### 7.3 Agent가 무한 루프에 빠진 경우

```
같은 파일을 반복적으로 수정한다면:
1. Esc로 중지
2. 지시문을 더 명확하게 수정
3. 범위를 더 좁게 제한
4. 단계별로 분리하여 재실행
```

## 8. 실전 실습: 마일스톤 1 — DB 스키마 Agent로 구현

### 8.1 준비 상태 확인

```
실습 전 체크:
[ ] .cursor/rules 파일이 작성되어 있다
[ ] docs/erd.md 파일이 존재한다 (10편에서 작성)
[ ] Docker에서 PostgreSQL 16이 실행 중이다
[ ] .env 파일에 DATABASE_URL이 설정되어 있다
```

### 8.2 지시문

```
Cmd+I로 Composer 열기 → Agent 모드 활성화

지시문:
"@Files docs/erd.md ERD를 참조해서 Prisma 스키마를 작성해줘.

요구사항:
1. 모든 모델에 softDelete 적용 (deletedAt: DateTime?)
2. 모든 모델에 createdAt, updatedAt 자동 관리
3. User 모델: id(cuid), email(unique), name, role(enum), passwordHash
4. Board 모델: id(cuid), name, type(BoardType enum), description, isActive
5. Post 모델: id(cuid), title, content(Text), boardId, authorId, type
6. Comment 모델: id(cuid), content, postId, authorId, parentId(대댓글)
7. RefreshToken 모델: id, token(unique), userId, expiresAt
8. File 모델: id, filename, url, mimeType, size, postId

파일 위치: apps/backend/prisma/schema.prisma

완료 후 PrismaService도 생성해줘.
위치: apps/backend/src/prisma/prisma.service.ts
소프트 삭제 미들웨어를 포함해야 해."
```

### 8.3 예상 생성 결과

```prisma
// prisma/schema.prisma
generator client {
  provider = "prisma-client-js"
}

datasource db {
  provider = "postgresql"
  url      = env("DATABASE_URL")
}

enum Role {
  SUPER_ADMIN
  BOARD_ADMIN
  USER
  GUEST
}

enum BoardType {
  NOTICE
  FREE
  QNA
  GALLERY
  FILE
  NEWS
  POLL
  SECRET
}

model User {
  id           String         @id @default(cuid())
  email        String         @unique
  name         String
  role         Role           @default(USER)
  passwordHash String
  posts        Post[]
  comments     Comment[]
  refreshTokens RefreshToken[]
  createdAt    DateTime       @default(now())
  updatedAt    DateTime       @updatedAt
  deletedAt    DateTime?

  @@index([email])
  @@index([deletedAt])
}

model Board {
  id          String    @id @default(cuid())
  name        String
  type        BoardType
  description String?
  isActive    Boolean   @default(true)
  posts       Post[]
  createdAt   DateTime  @default(now())
  updatedAt   DateTime  @updatedAt
  deletedAt   DateTime?

  @@index([type])
  @@index([deletedAt])
}

model Post {
  id        String    @id @default(cuid())
  title     String
  content   String    @db.Text
  boardId   String
  authorId  String
  board     Board     @relation(fields: [boardId], references: [id])
  author    User      @relation(fields: [authorId], references: [id])
  comments  Comment[]
  files     File[]
  viewCount Int       @default(0)
  createdAt DateTime  @default(now())
  updatedAt DateTime  @updatedAt
  deletedAt DateTime?

  @@index([boardId])
  @@index([authorId])
  @@index([deletedAt])
  @@index([createdAt])
}

model Comment {
  id        String    @id @default(cuid())
  content   String
  postId    String
  authorId  String
  parentId  String?
```

### 8.4 PrismaService 생성 확인

```typescript
// apps/backend/src/prisma/prisma.service.ts
import { INestApplication, Injectable, OnModuleInit } from '@nestjs/common';
import { PrismaClient } from '@prisma/client';

@Injectable()
export class PrismaService extends PrismaClient implements OnModuleInit {
  constructor() {
    super({
      log: ['warn', 'error'],
    });
  }

  async onModuleInit() {
    await this.$connect();
  }

  getSoftDeleteClient() {
    // 소프트 삭제 미들웨어 ($extends - Prisma v5+)
    return this.$extends({
      query: {
        $allModels: {
          async $allOperations({ args, query, operation }) {
            if (operation === 'findMany' || operation === 'findFirst') {
              if (!args.where) args.where = {};
              if (args.where.deletedAt === undefined) {
                args.where.deletedAt = null;
              }
            }

            // <!-- R3 수정: $extends 내에서 this 대신 query/args 직접 조작 권장 -->
            if (operation === 'delete') {
              // soft delete: where 조건 유지하고 data를 삭제 대신 업데이트
              (args as any).data = { deletedAt: new Date() };
              return query({ ...args, data: { deletedAt: new Date() } });
            }

            if (operation === 'deleteMany') {
              // soft deleteMany: where 조건 유지하고 data 업데이트
              return query({ ...args, data: { deletedAt: new Date() } });
            }

            return query(args);
          },
        },
      },
    });
  }

  async enableShutdownHooks(app: INestApplication) {
    process.on('beforeExit', async () => {
      await app.close();
    });
  }
}
```

### 9.3 툴콜 제한 이해

<!-- R4 수정: Agent 표준 모드 25회, Max 모드 200회 툴콜 제한 명시 -->

Agent는 한 세션에서 실행할 수 있는 툴콜(파일 읽기·쓰기·터미널 실행 등) 횟수에 제한이 있다.

```
표준 Agent 모드: 최대 25회 툴콜
Max 모드:        최대 200회 툴콜 (Ultra 플랜 이상 또는 추가 비용)

툴콜 소진 시:
→ Agent가 작업을 완료하지 못하고 멈춤
→ "계속해줘" 또는 새 세션으로 나머지 작업 진행
→ 큰 작업은 여러 마일스톤으로 분할하여 각각 Agent 실행 권장
```

### 9.4 Agent Skills (오픈 표준)

<!-- R4 수정: Agent Skills 오픈 표준 설명 추가 -->

Cursor의 **Agent Skills**는 에이전트 기능을 확장하는 오픈 표준(open standard)으로 설계되어 있다. `SKILL.md` 파일과 `scripts/`, `references/`, `assets/` 디렉토리로 구성된 스킬 패키지를 `.cursor/skills/`에 배치하면 Agent가 자동으로 발견하여 활용한다.

```
.cursor/skills/
└── my-skill/
    ├── SKILL.md       ← 스킬 설명 (Agent가 읽는 파일)
    ├── scripts/       ← 실행 스크립트
    ├── references/    ← 참조 문서
    └── assets/        ← 이미지·설정 파일

커뮤니티 스킬:
https://github.com/spencerpauly/awesome-cursor-skills
```
