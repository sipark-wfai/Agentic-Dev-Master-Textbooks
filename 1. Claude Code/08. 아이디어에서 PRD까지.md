## 1. 전통적 PRD vs 에이전트 친화적 PRD

### 1.1 전통적 PRD의 한계

전통적인 PRD는 인간 개발자를 독자로 가정하여 작성된다. 그러다 보니 맥락 의존적이고, 암묵적인 전제가 많으며, 모호한 표현이 허용된다.

```
전통적 PRD 예시:
"게시글 작성 기능을 구현한다.
 사용자 경험을 고려하여 직관적인 UI를 제공한다.
 적절한 보안 처리를 한다."

문제점:
- "적절한 보안 처리"가 무엇인지 에이전트가 알 수 없다
- "직관적인 UI"는 정량적 기준이 없다
- 에러 케이스가 정의되지 않았다
```

### 1.2 에이전트 친화적 PRD의 특징

에이전트는 텍스트를 시맨틱하게 파싱한다. 즉, 구조화된 텍스트에서 다음을 추출한다.

- 명사(엔티티): User, Post, Board, Comment
- 동사(행동): create, update, delete, query
- 조건(제약): "로그인한 사용자만", "관리자 권한 필요"
- 성공 기준: "HTTP 200 응답", "DB에 저장됨"
- 예외 조건: "존재하지 않는 ID", "권한 없는 사용자"

이러한 구조를 명시적으로 작성하면 에이전트가 오해 없이 구현한다.

### 1.3 두 PRD 형식 비교

| 항목 | 전통적 PRD | 에이전트 친화적 PRD |
|------|-----------|---------------------|
| 기능 설명 | 산문형 설명 | 기능 ID + 구조화된 명세 |
| 성공 기준 | 없거나 모호 | 측정 가능한 구체적 조건 |
| 예외 처리 | 개발자가 판단 | 명시적으로 나열 |
| 비기능 요구사항 | 없거나 부족 | 성능, 보안, 접근성 수치 명시 |
| 기술 스택 | 언급 안함 | 명시적 제약 또는 권장사항 |
| 금지 사항 | 없음 | 명시적 금지 목록 |

## 2. 에이전트 친화적 PRD 필수 구성 요소

### 2.1 서비스 개요 및 핵심 목표

```markdown
## 서비스 개요

서비스명: 멀티 게시판 허브 (Board Hub)
버전: 1.0.0
작성일: 2026-06-04

### 한 줄 정의
하나의 플랫폼에서 8종의 게시판(일반, 갤러리, 동영상, Q&A, 공지, FAQ, 비공개문의, 자유)을
통합 관리하는 커뮤니티 서비스

### 핵심 목표 (3가지 이내)
1. 게시판 유형에 따른 맞춤형 UI/UX 제공
2. 파일 업로드 기반 미디어 공유 지원
3. 역할 기반 접근 제어(RBAC)로 안전한 커뮤니티 운영

### 성공 지표
- 게시글 작성 응답 시간: 1초 이내
- 파일 업로드 응답 시간: 이미지 5초, 동영상 60초 이내
- 동시 접속 사용자: 1,000명 처리 가능
```

### 2.2 사용자 역할 정의

```markdown
## 사용자 역할 정의

### ADMIN (관리자)
- 계정 생성 방법: 시스템 초기 설정 또는 기존 ADMIN이 부여
- 권한:
  - 모든 게시글 읽기/수정/삭제
  - 모든 댓글 삭제
  - 게시판 생성/수정/삭제/설정 변경
  - 회원 관리 (정지, 역할 변경)
  - 신고 처리
  - NOTICE 게시판 게시글 작성
  
### USER (일반 회원)
- 계정 생성 방법: 이메일 회원가입
- 권한:
  - 모든 게시판 읽기 (INQUIRY 제외: 자신이 작성한 것만)
  - 자신이 작성한 게시글 수정/삭제
  - 댓글 작성, 수정, 삭제 (자신의 것만)
  - 파일 업로드 (크기/형식 제한 내)
  - 게시글/댓글 좋아요, 신고
  - FAQ, NOTICE 게시판은 읽기만

### GUEST (비회원)
- 계정: 없음
- 권한:
  - 일부 공개 게시판 읽기 (INQUIRY 제외)
  - 댓글 작성 불가
  - 파일 업로드 불가
```

### 2.3 기능 명세 (기능 ID 형식)

```markdown
## 기능 명세

### [AUTH-001] 이메일 회원가입

**설명**: 이메일과 비밀번호로 새 계정을 생성한다.

**입력 데이터**:
- email: string, 이메일 형식 필수, 최대 255자
- password: string, 최소 8자, 영문+숫자+특수문자 포함
- nickname: string, 2~20자, 한글/영문/숫자 허용, 특수문자 금지

**처리 로직**:
1. email 중복 확인 (users 테이블)
2. nickname 중복 확인 (users 테이블)
3. password를 bcrypt로 해시 (salt rounds: 12)
4. users 테이블에 저장 (role: USER, isActive: true)
5. 환영 이메일 발송 (비동기, 실패해도 회원가입은 완료)

**성공 응답**: HTTP 201
```json
{
  "id": "uuid-v4",
  "email": "user@example.com",
  "nickname": "닉네임",
  "role": "USER",
  "createdAt": "2026-06-04T00:00:00.000Z"
}
```

**에러 응답**:
- 409: 이메일 중복 ("이미 사용 중인 이메일입니다")
- 409: 닉네임 중복 ("이미 사용 중인 닉네임입니다")
- 400: 유효성 검사 실패 (각 필드별 상세 메시지)

**금지 사항**:
- 비밀번호를 평문으로 DB에 저장하지 않는다
- 응답에 hashedPassword를 포함하지 않는다
```

```markdown

버전: 1.0.0  
작성일: 2026-06-04  
작성자: 기획팀  
상태: 확정

## 1. 서비스 개요

### 한 줄 정의
8종 게시판을 하나의 플랫폼에서 통합 관리하는 커뮤니티 서비스

### 배경 및 필요성
커뮤니티 운영자들은 일반 게시판, 갤러리, Q&A, 공지 등 여러 성격의 게시판이 필요하지만,
이를 통합 관리할 수 있는 솔루션이 부족하다.
멀티 게시판 허브는 하나의 플랫폼에서 모든 게시판 유형을 지원한다.

### 핵심 목표
1. 8종 게시판 유형별 맞춤형 UI/UX 제공
2. 이미지/동영상 미디어 공유 지원
3. 역할 기반 접근 제어로 안전한 운영

## 2. 사용자 역할

| 역할 | 설명 | 게시글 작성 | 게시글 관리 | 게시판 관리 |
|------|------|------------|------------|------------|
| ADMIN | 관리자 | 전체 게시판 | 전체 | 가능 |
| USER | 일반 회원 | NOTICE/FAQ 제외 | 자신의 것만 | 불가 |
| GUEST | 비회원 | 불가 | 불가 | 불가 |

## 3. 게시판 유형 명세

### [BOARD-GENERAL] 일반 게시판
- 게시글 형식: 제목 + 텍스트 본문 + 첨부파일(선택)
- 특수 기능: 없음
- 접근 제어: USER 이상 작성 가능, GUEST 읽기 가능

### [BOARD-GALLERY] 갤러리 게시판
- 게시글 형식: 제목 + 이미지(1개 이상 필수) + 설명 텍스트
- 특수 기능: 썸네일 자동 생성, 그리드 레이아웃
- 접근 제어: USER 이상 작성 가능
- 파일 제한: jpg/png/gif/webp, 개당 최대 10MB, 게시글당 최대 20개

### [BOARD-VIDEO] 동영상 게시판
- 게시글 형식: 제목 + (동영상 파일 OR YouTube URL) + 설명
- 특수 기능: YouTube 임베드, 동영상 플레이어
- 파일 제한: mp4/webm, 최대 500MB

### [BOARD-QNA] Q&A 게시판
- 게시글 형식: 질문 제목 + 상세 내용 + 태그(최대 5개)
- 특수 기능:
  - 답변 채택: 질문자가 답변 중 하나를 채택 가능
  - 채택된 답변은 상단 고정 표시
  - 미채택 질문 필터링 기능
- 접근 제어: USER 이상 질문/답변 가능

### [BOARD-NOTICE] 공지사항 게시판
- 게시글 형식: 제목 + 본문 + 첨부파일
- 특수 기능: 
  - 게시글 목록 상단 고정 옵션
  - 읽음 표시 (읽은 사용자 수 표시)
- 접근 제어: ADMIN만 작성 가능, 전체 읽기 가능

### [BOARD-FAQ] FAQ 게시판
- 게시글 형식: 질문(제목) + 답변(본문) + 카테고리
- 특수 기능:
  - 카테고리별 분류
  - 아코디언 UI (질문 클릭 시 답변 펼침/닫힘)
- 접근 제어: ADMIN만 작성 가능, 전체 읽기 가능

### [BOARD-INQUIRY] 비공개 문의
- 게시글 형식: 문의 제목 + 상세 내용 + 첨부파일
- 특수 기능:
  - 비공개: 작성자 본인과 ADMIN만 조회 가능
  - 답변 기능: ADMIN이 댓글로 답변
  - 답변 완료 상태 표시
- 접근 제어: USER 이상 작성, 작성자+ADMIN만 조회

### [BOARD-FREE] 자유 게시판
- 게시글 형식: 제목 + 본문 + 첨부파일
- 특수 기능:
  - 익명 작성 옵션 (작성 시 선택 가능)
  - 익명 게시글은 작성자명 대신 "익명" 표시
  - ADMIN은 익명 게시글의 실제 작성자 확인 가능

## 4. 핵심 기능 명세

### [AUTH-001] 이메일 회원가입
입력: email, password, nickname  
처리: 중복 확인 -> bcrypt 해시 -> DB 저장  
성공: HTTP 201 + UserResponseDto  
에러: 409(중복), 400(유효성 실패)

### [AUTH-002] 이메일 로그인
입력: email, password  
처리: 사용자 조회 -> bcrypt 비교 -> JWT 발급  
성공: HTTP 200 + { accessToken, refreshToken, user }  
에러: 401(인증 실패), 403(비활성 계정)  
토큰 만료: accessToken 1시간, refreshToken 30일

### [AUTH-003] 토큰 갱신
입력: refreshToken (쿠키)  
처리: 토큰 유효성 검증 -> 새 accessToken 발급  
성공: HTTP 200 + { accessToken }  
에러: 401(토큰 만료/무효)

### [POST-001] 게시글 작성
입력: boardId, title, content, boardType에 따른 추가 필드  
처리: 권한 확인 -> 게시판 유형별 유효성 검사 -> DB 저장 -> 파일 연결  
성공: HTTP 201 + PostResponseDto  
에러: 403(권한 없음), 404(게시판 없음), 400(유효성 실패)

### [POST-002] 게시글 목록 조회
입력: boardId, page(기본값 1), limit(기본값 20), sort(latest/popular), search  
처리: 권한 확인 -> 페이지네이션 쿼리 -> soft delete 제외  
성공: HTTP 200 + { items: PostListItemDto[], total, page, limit }  
에러: 404(게시판 없음)  
성능: 100ms 이내 응답

### [POST-003] 게시글 상세 조회
입력: boardId, postId  
처리: 권한 확인(INQUIRY 게시판은 작성자+ADMIN만) -> 조회수 +1 -> 조회  
성공: HTTP 200 + PostDetailDto  
에러: 403(권한 없음), 404(게시글 없음)

### [POST-004] 게시글 수정
입력: boardId, postId, 수정할 필드들  
처리: 본인 또는 ADMIN 확인 -> 수정 -> 파일 업데이트  
성공: HTTP 200 + PostResponseDto  
에러: 403(권한 없음), 404(없음)

### [POST-005] 게시글 삭제
처리: 본인 또는 ADMIN 확인 -> soft delete (deletedAt 설정)  
성공: HTTP 204  
에러: 403(권한 없음), 404(없음)

### [FILE-001] 파일 업로드
입력: file (multipart/form-data)  
처리: 파일 형식/크기 검증 -> 저장 경로 생성 (uploads/yyyy/mm/uuid.ext) -> 저장  
이미지: 썸네일 자동 생성 (200x200 crop)  
성공: HTTP 201 + { fileId, url, thumbnailUrl }  
에러: 400(형식 불가), 413(용량 초과)

### [COMMENT-001] 댓글 작성
입력: postId, content, parentId(대댓글 시)  
처리: 권한 확인 -> 계층 깊이 제한 (최대 2단계) -> DB 저장  
성공: HTTP 201 + CommentResponseDto  
에러: 403(권한 없음), 404(게시글 없음), 400(깊이 초과)

### [SEARCH-001] 게시글 검색
입력: q(검색어), boardId(선택), page, limit  
처리: PostgreSQL Full-text Search (tsvector) 사용  
검색 대상: 제목 + 본문  
성공: HTTP 200 + { items, total, page, limit }  
성능: 500ms 이내 응답

## 5. 비기능 요구사항

### 5.1 성능
- API 응답 시간: 일반 요청 200ms 이내, 파일 업로드 제외
- 페이지 로드: 초기 로드 3초 이내 (LCP 기준)
- DB 쿼리: 단일 쿼리 100ms 이내
- 동시 사용자: 1,000명 동시 접속 처리

### 5.2 보안
- 모든 API 통신: HTTPS 필수 (HTTP 자동 리다이렉트)
- 비밀번호: bcrypt (salt rounds 12) 해시 저장
- JWT: RS256 또는 HS256, 1시간 만료
- SQL Injection: Prisma ORM으로 방지 (Raw SQL 사용 금지)
- XSS: DOMPurify로 입력 sanitize, Content Security Policy 설정
- CSRF: SameSite=Strict 쿠키 설정
- Rate Limiting: 로그인 API 1분당 10회, 회원가입 1시간당 5회
- 파일 업로드: 형식 검증(MIME type + 매직 바이트), 바이러스 스캔(선택)

### 5.3 접근성
- WCAG 2.1 AA 기준 준수
- 키보드 네비게이션 지원

## 5. 기획자·디자이너·개발자의 PRD 협업 방법

### 5.1 PRD 협업 워크플로우

```
Step 1: 기획자가 PRD 초안 작성
        기능 ID, 입력/출력, 비즈니스 규칙에 집중

Step 2: 디자이너 검토
        - UI 컴포넌트 명세 추가 (어떤 컴포넌트 사용?)
        - 에러 상태 UI 정의
        - 빈 상태 UI 정의 (게시글 0개일 때)
        - 로딩 상태 UI 정의

Step 3: 개발자 검토
        - 기술적 실현 가능성 확인
        - 성능 목표 현실성 검토
        - DB 스키마 영향 분석
        - API 설계 검토

Step 4: PRD 확정 및 버전 태깅
        - docs/PRD-v1.0.md 로 저장
        - Git 태그: docs-v1.0

Step 5: Claude Code로 구현 시작
        - PRD.md를 @로 참조하며 구현
```

### 7.1 역할별 PRD 검토 포인트

PRD를 혼자 작성하고 에이전트에게 전달하면 중요한 관점이 빠질 수 있다.
아래 역할별 검토 포인트를 팀이 함께 확인한다.

| 역할 | 검토 포인트 |
|------|-------------|
| 기획자 | 기능 ID가 누락 없이 정의됐는가, 예외 흐름이 명시됐는가 |
| 디자이너 | UI 컴포넌트 명세와 반응형 기준이 포함됐는가 |
| 개발자 | 기술 스택 제약이 현실적인가, 성능 수치가 달성 가능한가 |

### 7.2 PRD 버전 관리

PRD는 Git으로 버전 관리한다. 에이전트가 어떤 버전 기준으로 구현했는지 추적 가능하다.

```bash
# PRD 초안 커밋
git add docs/PRD.md
git commit -m "docs: PRD 초안 작성 (AUTH, POST 기능 포함)"

# 리뷰 후 수정
git add docs/PRD.md
git commit -m "docs: PRD 수정 - 파일 업로드 크기 제한 추가"
