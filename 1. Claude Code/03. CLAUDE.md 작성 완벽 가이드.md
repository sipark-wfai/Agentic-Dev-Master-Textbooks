## 1. CLAUDE.md란 무엇인가

CLAUDE.md는 Claude Code 에이전트가 특정 프로젝트에서 작업할 때 반드시 읽고 따르는 규칙서다. 사람으로 비유하면 새로 합류한 개발자에게 주는 온보딩 문서이자, 팀의 코딩 컨벤션 가이드이자, 프로젝트의 헌법이다.

Claude Code는 세션을 시작할 때마다 CLAUDE.md를 자동으로 읽는다. CLAUDE.md에 정의된 내용은 에이전트의 모든 결정에 영향을 미친다.

### 1.1 CLAUDE.md가 없으면 어떤 일이 생기는가

CLAUDE.md 없이 Claude Code를 사용하면 에이전트는 기본 지식으로만 추론한다.

- 프로젝트가 어떤 패키지 매니저를 쓰는지 알 수 없다 (npm, yarn, pnpm 중 추측)
- 코딩 컨벤션을 알 수 없다 (탭 vs 스페이스, 세미콜론 여부 등 추측)
- 어떤 폴더에 어떤 역할이 있는지 알 수 없다 (구조를 직접 탐색해야 함)
- 금지된 패턴을 알 수 없다 (any 타입, console.log 등을 자유롭게 사용)
- 테스트 실행 명령을 알 수 없다 (추측으로 실행)

결과적으로 에이전트가 만들어내는 코드의 품질이 일관되지 않는다.

### 1.2 CLAUDE.md vs 시스템 프롬프트의 차이

| 구분 | CLAUDE.md | 시스템 프롬프트 |
|------|-----------|----------------|
| 위치 | 프로젝트 파일 시스템 | API 호출 매개변수 |
| 버전 관리 | Git으로 팀 공유 가능 | 코드에 하드코딩 |
| 수정 방법 | 일반 텍스트 편집기 | API 클라이언트 수정 |
| 계층 구조 | 폴더별 여러 파일 가능 | 단일 프롬프트 |
| 실시간 수정 | 에디터로 직접 수정 후 세션 재시작; `/memory`는 현재 로드된 메모리 조회 전용<!-- R3 수정: /memory 역할 명확화 --> | 세션 재시작 필요 |
| 용도 | 프로젝트 규칙, 컨텍스트 | AI 기본 동작 설정 |

## 2. Claude Code가 CLAUDE.md를 처리하는 내부 방식

### 2.1 파일 탐색 순서

Claude Code는 세션 시작 시 다음 순서로 CLAUDE.md를 탐색하여 컨텍스트를 구성한다.

```
1. 글로벌 CLAUDE.md 읽기
   경로: ~/.claude/CLAUDE.md
   역할: 모든 프로젝트에 공통으로 적용되는 전역 규칙

2. 프로젝트 루트 CLAUDE.md 읽기
   경로: {프로젝트 루트}/CLAUDE.md
   역할: 현재 프로젝트의 주요 규칙

3. 현재 작업 폴더 CLAUDE.md 읽기 (있으면)
   경로: {현재 폴더}/CLAUDE.md
   역할: 현재 폴더에만 적용되는 세부 규칙

4. 모든 CLAUDE.md를 컨텍스트에 통합
   우선순위: 하위 폴더 > 프로젝트 루트 > 글로벌
```

### 2.2 컨텍스트 통합 방식

여러 CLAUDE.md가 존재할 경우, Claude Code는 모든 내용을 통합하여 단일 컨텍스트로 만든다. 충돌이 있을 경우 더 구체적인 (하위 폴더의) 규칙이 우선한다.

예시:
- 글로벌 CLAUDE.md: "들여쓰기는 2 스페이스"
- 프로젝트 루트 CLAUDE.md: "TypeScript strict 모드 사용"
- `src/legacy/` CLAUDE.md: "이 폴더는 JavaScript 파일만 있음, TypeScript 규칙 미적용"

`src/legacy/` 폴더에서 작업할 때 에이전트는 세 파일을 모두 읽지만, TypeScript 규칙은 `src/legacy/CLAUDE.md`의 지시에 따라 적용하지 않는다.

## 3. 파일 위치와 우선순위

### 3.1 글로벌 CLAUDE.md

```
~/.claude/CLAUDE.md
```

모든 프로젝트에 공통으로 적용되는 개인 설정을 담는다.

```markdown
# 개인 글로벌 설정

## 나의 기본 선호 설정
- 모든 코드는 TypeScript로 작성한다
- 패키지 매니저는 pnpm을 우선 사용한다
- 코드 스타일: Prettier 기본값 따름
- 커밋 메시지: Conventional Commits 형식 사용

## 절대 하지 않는 것
- 프로덕션 코드에 any 타입 사용하지 않는다
- 비밀키를 코드에 직접 넣지 않는다
- 테스트 없이 기능을 완료로 표시하지 않는다
```

### 3.2 프로젝트 루트 CLAUDE.md

```
{프로젝트 루트}/CLAUDE.md
```

현재 프로젝트의 핵심 규칙을 담는다. 가장 많이 사용하는 위치다.

### 3.3 하위 폴더 CLAUDE.md

```
{프로젝트 루트}/src/CLAUDE.md
{프로젝트 루트}/packages/frontend/CLAUDE.md
{프로젝트 루트}/packages/backend/CLAUDE.md
```

특정 서브 시스템에만 적용되는 세부 규칙을 담는다. 모노레포에서 특히 유용하다.

## 4. CLAUDE.md 필수 섹션 구성

효과적인 CLAUDE.md는 다음 섹션들로 구성된다.

### 4.1 프로젝트 개요 섹션

```markdown
# 프로젝트명

## 프로젝트 개요
이 프로젝트는 [무엇을 하는 서비스]다.
주요 사용자: [누가 사용하는가]
핵심 목표: [이 서비스가 달성하려는 것]
```

### 4.2 기술 스택 섹션

```markdown
## 기술 스택

### 프론트엔드
- SvelteKit 2.x (TypeScript)
- TailwindCSS 3.x
- shadcn-svelte 최신 버전

### 백엔드
- NestJS 10.x (TypeScript)
- Passport.js (JWT 인증)
- Multer (파일 업로드)

### 데이터베이스
- PostgreSQL 16
- Prisma v5 ORM

### 패키지 매니저
- pnpm 8.x (npm/yarn 사용 금지)
```

### 4.3 아키텍처 규칙 섹션

```markdown
## 아키텍처 규칙

### 모노레포 구조
- apps/frontend/: SvelteKit 앱
- apps/backend/: NestJS 앱
- packages/shared/: 공유 타입 및 유틸리티
- prisma/: DB 스키마 및 마이그레이션

### 레이어 규칙
- Controller: HTTP 요청/응답 처리만 담당
- Service: 비즈니스 로직 처리
- Repository(Prisma): DB 접근만 담당
- DTO: 요청/응답 데이터 유효성 검사

### 인증 규칙
- 모든 API는 기본적으로 JWT 인증 필요
- 공개 API에는 @Public() 데코레이터 명시
```

### 4.4 코딩 컨벤션 섹션

```markdown
## 코딩 컨벤션

### TypeScript
- strict 모드 활성화 (tsconfig.json의 strict: true)
- any 타입 사용 금지
- 인터페이스 이름: I 접두사 없음 (User, not IUser)
- 타입 이름: T 접두사 없음 (UserType, not TUserType)
- enum 대신 const enum 또는 as const 사용

### 파일 명명 규칙
- NestJS 파일: kebab-case (user.service.ts)
- SvelteKit 컴포넌트: PascalCase (UserCard.svelte)
- 유틸리티 함수: camelCase (formatDate.ts)

### 들여쓰기 및 포맷
- 들여쓰기: 2 스페이스
- 따옴표: 작은따옴표 (')
- 세미콜론: 사용
- 한 줄 최대 길이: 100자

### 임포트 순서
1. Node.js 내장 모듈
2. 외부 패키지 (node_modules)
3. 내부 모듈 (@/)
4. 상대 경로 (./)
```

### 4.5 금지 사항 섹션

```markdown
## 절대 금지 사항

### 코드 품질
- any 타입 절대 사용 금지
- console.log 프로덕션 코드에 사용 금지 (logger 모듈 사용)
- TODO 주석을 코드에 남기지 않음 (이슈 트래커 사용)
- 하드코딩된 상수 값 금지 (constants 파일 사용)

### 보안
- 비밀키, API 키, 비밀번호를 코드에 직접 작성 금지
- .env 파일을 Git에 커밋 금지
- SQL Injection 취약한 Raw SQL 사용 금지 (Prisma ORM 사용)
- XSS 취약한 innerHTML 직접 조작 금지

### 데이터베이스
- 마이그레이션 파일 직접 수정 금지 (새 마이그레이션 생성)
- 프로덕션 DB에서 DROP TABLE 직접 실행 금지
- ORM 없이 직접 쿼리 작성 금지 (성능 최적화 목적 제외)
```

### 4.6 빌드·테스트 명령어 섹션

```markdown
## 명령어

### 개발 서버 시작
- 전체: pnpm dev (루트에서)
- 프론트엔드만: cd apps/frontend && pnpm dev
- 백엔드만: cd apps/backend && pnpm start:dev

### 빌드
- 전체 빌드: pnpm build
- 프론트엔드 빌드: pnpm --filter frontend build
- 백엔드 빌드: pnpm --filter backend build

### 테스트
- 전체 테스트: pnpm test
- 백엔드 단위 테스트: pnpm --filter backend test
- 백엔드 통합 테스트: pnpm --filter backend test:e2e

### 데이터베이스
- 마이그레이션 생성: npx prisma migrate dev --name 마이그레이션명
- 마이그레이션 실행: npx prisma migrate deploy
- Prisma Studio 실행: npx prisma studio
- DB 초기화: npx prisma db push --force-reset (개발 환경만)

### 코드 품질
- 린팅: pnpm lint
- 포맷팅: pnpm format
- 타입 검사: pnpm typecheck
```

## 5. 멀티 게시판 허브 CLAUDE.md 전체 예시

다음은 이 시리즈의 예제 프로젝트인 멀티 게시판 허브의 실제 CLAUDE.md다.

```markdown
# 멀티 게시판 허브 (Board Hub)

## 프로젝트 개요
멀티 게시판 허브는 8종의 게시판(일반, 갤러리, 동영상, Q&A, 공지, FAQ, 비공개문의, 자유)을
하나의 플랫폼에서 통합 관리하는 커뮤니티 서비스다.

주요 사용자:
- 일반 회원: 게시글 작성, 댓글, 파일 업로드
- 관리자: 게시판 관리, 회원 관리, 신고 처리

## 기술 스택

### 프론트엔드
- SvelteKit 2.x (TypeScript, strict 모드)
- TailwindCSS 3.x
- shadcn-svelte (UI 컴포넌트)
- Lucide Icons (아이콘)

### 백엔드
- NestJS 10.x (TypeScript, strict 모드)
- JWT + Passport.js (인증)
- Multer (파일 업로드)
- class-validator, class-transformer (DTO 검증)

### 데이터베이스
- PostgreSQL 16
- Prisma v5 ORM
- UUID v4 (PK 전략)

### 인프라
- Docker Compose (로컬 개발)
- pnpm 모노레포

## 프로젝트 구조

```
board-hub/
+-- apps/
|   +-- frontend/       SvelteKit
|   +-- backend/        NestJS
+-- packages/
|   +-- shared/         공유 타입 및 상수
+-- prisma/
|   +-- schema.prisma
|   +-- migrations/
+-- docker-compose.yml
+-- CLAUDE.md
```

## 아키텍처 규칙

### 백엔드 레이어
- Controller: HTTP 요청/응답만 처리, 비즈니스 로직 없음
- Service: 모든 비즈니스 로직 처리
- Prisma Service: DB 접근 담당, Service에서만 호출
- Guard: 인증/인가 처리
- DTO: 입력 데이터 유효성 검사 (class-validator)

### 게시판 분기 처리
- 게시판 유형(BoardType enum)에 따라 서비스 레이어에서 분기
- 각 게시판 유형별 추가 필드는 Post.metadata (JSONB) 필드 활용
- 공통 CRUD는 PostService에서 처리, 유형별 특수 처리는 별도 메서드

### 프론트엔드 라우팅
- /board/[board_id]/           게시판 목록
- /board/[board_id]/[post_id]  게시글 상세
- /board/[board_id]/write      게시글 작성
- /(auth)/login                로그인
- /(auth)/register             회원가입
- /admin/                      관리자 영역

## 코딩 컨벤션

### 공통
- 들여쓰기: 2 스페이스
- 따옴표: 작은따옴표
- 세미콜론: 사용
- 최대 줄 길이: 100자
- 파일 인코딩: UTF-8

### TypeScript
- strict: true 필수
- any 타입 절대 금지
- unknown + type guard 패턴 사용
- 인터페이스는 동사 없이 명사로 (User, not IUser)
- 제네릭 타입 파라미터: T, K, V 등 의미 있는 단문자

### NestJS 백엔드
- 파일명: kebab-case (user.service.ts)
- 클래스명: PascalCase (UserService)
- 메서드명: camelCase (findUserById)
- DTO 클래스: 동사+명사+Dto (CreatePostDto, UpdatePostDto)
- Guard: 인증은 JwtAuthGuard, 인가는 RolesGuard 사용
- 응답은 항상 DTO 또는 타입 정의된 객체 반환

### SvelteKit 프론트엔드
- 컴포넌트 파일: PascalCase (PostCard.svelte)
- 페이지 파일: +page.svelte (SvelteKit 컨벤션)
- 스토어: camelCase 함수명 (createAuthStore)
- API 호출: src/lib/api/ 폴더에서 함수로 분리
- 상태 관리: Svelte stores 사용 (외부 상태 라이브러리 금지)

### Prisma 스키마
- 모델명: PascalCase 단수형 (User, Post, Comment)
- 필드명: camelCase (createdAt, boardId)
- 관계 필드명: 모델명 camelCase (author, board)
- enum명: PascalCase (BoardType, PostStatus)

## 절대 금지 사항

### 코드 품질
- any 타입 사용 금지 (unknown + 타입 가드 사용)
- console.log 금지 (NestJS Logger 또는 pino 사용)
- @ts-ignore / @ts-expect-error 금지 (타입 오류는 올바르게 해결)
- 사용하지 않는 임포트 금지
- 매직 넘버 금지 (constants.ts에 상수로 정의)

### 보안
- API 키, 비밀번호, JWT_SECRET 등 코드에 직접 작성 금지
- .env 파일 Git 커밋 금지 (.env.example은 허용)
- Raw SQL에서 사용자 입력 직접 삽입 금지 (Prisma parameterized query 사용)
- 비밀번호를 평문으로 DB에 저장 금지 (bcrypt 해시 필수)

### 데이터베이스
- 기존 마이그레이션 파일 수정 금지 (새 마이그레이션 생성)
- schema.prisma 변경 후 migrate dev 없이 코드 작성 금지
- 개발 환경 외에서 db push --force-reset 금지

### 게시판 로직
- 비공개 문의(PRIVATE_INQUIRY) 게시판의 게시글은 작성자와 관리자만 조회 가능
- 공지(NOTICE) 게시판은 ADMIN 역할만 작성 가능
- 삭제된 게시글은 DB에서 물리적으로 삭제하지 않음 (deletedAt soft delete)

## 7. 잘못 쓴 CLAUDE.md vs 잘 쓴 CLAUDE.md 비교 5가지

### 비교 1: 기술 스택 명시

**잘못된 예**:
```markdown
## 기술 스택
웹 개발에 필요한 최신 기술을 사용한다.
```

**잘 쓴 예**:
```markdown
## 기술 스택
- 프론트엔드: SvelteKit 2.x, TypeScript, TailwindCSS 3.x
- 백엔드: NestJS 10.x, TypeScript
- 데이터베이스: PostgreSQL 16, Prisma v5
- 패키지 매니저: pnpm 8.x (npm, yarn 사용 금지)
- Node.js: 20.x LTS
```

이유: 에이전트는 "최신 기술"이 무엇인지 스스로 판단해야 한다. 구체적인 버전과 패키지명을 명시해야 일관된 코드가 생성된다.

### 비교 2: 금지 사항 명시

**잘못된 예**:
```markdown
## 규칙
좋은 코드를 작성한다.
```

**잘 쓴 예**:
```markdown
## 절대 금지
- TypeScript any 타입 사용 금지 (unknown + 타입 가드 사용)
- 프로덕션 코드에 console.log 금지 (Logger 클래스 사용)
- 하드코딩된 비밀키, 연결 문자열 금지
- 테스트 없이 기능 완료 처리 금지
```

이유: "좋은 코드"는 주관적이다. 에이전트에게는 구체적이고 검증 가능한 규칙이 필요하다.

### 비교 3: 명령어 제공

**잘못된 예**:
```markdown
## 빌드
표준 방식으로 빌드한다.
```

**잘 쓴 예**:
```markdown
## 명령어
- 개발 서버: pnpm dev
- 빌드: pnpm build
- 테스트: pnpm test
- 린팅: pnpm lint
- 마이그레이션: npx prisma migrate dev --name {name}
```

이유: 에이전트가 명령어를 추측하면 잘못된 명령어를 실행할 수 있다.

### 비교 4: 폴더 구조 설명

**잘못된 예**:
```markdown
## 구조
MVC 패턴을 따른다.
```

**잘 쓴 예**:
```markdown
## 폴더 구조

### 백엔드 (apps/backend/src/)
- auth/          인증 모듈 (로그인, 회원가입, JWT)
- users/         사용자 관리 모듈
- boards/        게시판 설정 모듈
- posts/         게시글 CRUD 모듈
- comments/      댓글 모듈
- files/         파일 업로드 모듈
- common/        공통 유틸, 데코레이터, 가드
- prisma/        Prisma Service (DB 연결)
```

이유: 에이전트가 어느 폴더에 코드를 작성해야 하는지 정확히 알 수 있다.

### 비교 5: 비즈니스 규칙 명시

**잘못된 예**:
```markdown
## 게시판
게시판 기능을 구현한다.
```

**잘 쓴 예**:
```markdown
## 비즈니스 규칙

### 게시판 접근 제어
- NOTICE 게시판: ADMIN 역할만 게시글 작성 가능
- INQUIRY 게시판: 작성자 본인과 ADMIN만 게시글 조회 가능
- FAQ 게시판: 모든 사용자 조회 가능, ADMIN만 작성

### Soft Delete
- Post, Comment, User는 삭제 시 deletedAt 필드 업데이트
- DB에서 물리적으로 삭제하지 않음

### 파일 업로드 제한
- 이미지: jpg, png, gif, webp만 허용, 최대 10MB
- 동영상: mp4, webm만 허용, 최대 500MB
- 업로드 경로: uploads/{year}/{month}/{uuid}.{ext}
```

이유: 비즈니스 규칙이 없으면 에이전트가 일반적인 구현을 선택하여 실제 요구사항과 다른 코드가 생성된다.
