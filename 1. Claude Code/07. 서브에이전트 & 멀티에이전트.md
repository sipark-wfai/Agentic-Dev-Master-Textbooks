## 1. 서브에이전트 개념: 오케스트레이터-워커 패턴

혼자서 모든 것을 처리하는 에이전트 하나보다, 역할이 분명한 에이전트 팀이 훨씬 효과적이다. 이것이 오케스트레이터-워커 패턴의 핵심이다.

### 1.1 단일 에이전트의 한계

```
[단일 에이전트가 8종 게시판을 순차적으로 구현하는 경우]

에이전트
  |
  +-- 일반 게시판 API 구현 (30분)
  |     완료 후...
  +-- 갤러리 게시판 API 구현 (35분)
  |     완료 후...
  +-- 동영상 게시판 API 구현 (40분)
  |     완료 후...
  +-- (5개 더...)

총 소요 시간: 약 4~5시간 (순차 실행)
```

### 1.2 멀티에이전트의 강점

```
[오케스트레이터 + 워커 에이전트들이 병렬로 구현하는 경우]

[오케스트레이터 에이전트]
  |
  +--병렬 시작--> [워커 1] 일반 + 자유 게시판
  +--병렬 시작--> [워커 2] 갤러리 + 동영상 게시판
  +--병렬 시작--> [워커 3] Q&A + 공지 게시판
  +--병렬 시작--> [워커 4] FAQ + 비공개문의 게시판

총 소요 시간: 약 40분 (병렬 실행, 4배 빠름)
```

### 1.3 오케스트레이터의 역할

오케스트레이터는 전체 작업을 계획하고, 워커에게 적절한 태스크를 배분하며, 결과를 통합한다.

오케스트레이터가 수행하는 것:
- 전체 작업 분석 및 태스크 분할
- 각 워커의 작업 범위와 제약 정의
- 워커 간 의존성 파악 (순서 관리)
- 완료된 워커 결과물 검토 및 통합

오케스트레이터가 직접 하지 않는 것:
- 구체적인 코드 작성
- 파일 생성 및 수정
- 명령어 직접 실행

## 3. 직렬 vs 병렬 에이전트 실행

### 3.1 직렬 실행을 선택해야 할 때

```
케이스 1: 단계 간 강한 의존성
   DB 스키마 생성 -> 마이그레이션 -> 코드 생성
   (앞 단계가 끝나야 다음 단계 가능)

케이스 2: 동일 파일을 수정하는 작업
   auth.service.ts에 login 메서드 추가
   auth.service.ts에 logout 메서드 추가
   (같은 파일 -> 충돌 방지를 위해 순차 실행)

케이스 3: 컨텍스트 공유가 필요한 작업
   "프론트엔드 컴포넌트가 완성된 후 백엔드 응답 형식을 맞춰야 할 때"
```

### 3.2 병렬 실행을 선택해야 할 때

```
케이스 1: 독립적인 모듈 구현
   - Auth 모듈 구현 (독립)
   - File 업로드 모듈 구현 (독립)
   - 알림 모듈 구현 (독립)
   -> 세 모듈이 서로 다른 파일을 수정 = 병렬 OK

케이스 2: 여러 테스트 파일 작성
   - auth.service.spec.ts 작성
   - posts.service.spec.ts 작성
   - comments.service.spec.ts 작성
   -> 독립 파일 = 병렬 OK

케이스 3: 게시판 유형별 독립 구현
   - GENERAL 게시판 전용 로직
   - QNA 게시판 전용 로직
   -> 분리된 서비스 메서드 = 병렬 OK
```

### 3.3 선택 기준 체크리스트

병렬 실행 전 다음을 확인한다:

- [ ] 각 에이전트가 서로 다른 파일을 수정하는가?
- [ ] 에이전트 A의 결과물을 에이전트 B가 필요로 하지 않는가?
- [ ] 공유 상태(DB 마이그레이션, package.json)가 없는가?
- [ ] 모든 에이전트가 동일한 브랜치에서 작업하는가? (Git 충돌 확인)

## 4. 병렬 실행 시 주의사항: Race Condition 방지

### 4.1 Race Condition이란

여러 에이전트가 동시에 같은 파일을 수정하려 할 때 발생하는 충돌이다.

```
시나리오: 두 에이전트가 동시에 package.json을 수정하는 경우

에이전트 A: package.json 읽기
에이전트 B: package.json 읽기
에이전트 A: express 추가 후 저장
에이전트 B: multer 추가 후 저장 (에이전트 A의 변경사항 덮어씌움!)

결과: express가 package.json에서 사라짐
```

### 4.2 Race Condition 방지 패턴

**패턴 1: 파일 소유권 할당**

각 에이전트에게 명확한 파일 소유권을 부여한다.

```
오케스트레이터 지시사항:

에이전트 1이 소유하는 파일:
- apps/backend/src/posts/posts.module.ts
- apps/backend/src/posts/posts.controller.ts
- apps/backend/src/posts/posts.service.ts

에이전트 2가 소유하는 파일:
- apps/backend/src/comments/comments.module.ts
- apps/backend/src/comments/comments.controller.ts
- apps/backend/src/comments/comments.service.ts

규칙: 자신이 소유하지 않은 파일은 절대 수정하지 않는다.
```

**패턴 2: 공유 파일 사전 처리**

병렬 실행 전에 공유 파일을 미리 처리한다.

```bash
# Phase 1: 오케스트레이터가 직접 처리 (순차)
# - package.json 의존성 설치
# - prisma/schema.prisma 전체 스키마 확정
# - app.module.ts 모듈 임포트 추가

# Phase 2: 워커들이 병렬 실행
# - 각 모듈의 독립 파일만 수정
```

**패턴 3: 브랜치 분리**

각 에이전트가 별도 Git 브랜치에서 작업하고 최종에 병합한다.

```bash
# 오케스트레이터가 브랜치 생성
git checkout -b feature/posts-module
git checkout -b feature/comments-module
git checkout -b feature/files-module

# 각 에이전트가 해당 브랜치에서 작업
# 완료 후 main에 병합 (충돌 수동 해결)
```

## 7. 멀티 게시판 8종 게시판 병렬 구현 실습

### 7.1 사전 준비 (순차 실행, 오케스트레이터 직접 처리)

## 8. 서브에이전트 결과물 통합 전략

### 8.1 결과물 검토 체크리스트

모든 워커가 완료되면 오케스트레이터가 다음을 검토한다.

```
> 모든 서브에이전트가 완료됐다. 다음을 순서대로 검토해줘:

1. TypeScript 타입 오류 확인
   cd apps/backend && npx tsc --noEmit
   
2. 모듈 임포트 누락 확인
   app.module.ts에 모든 모듈이 등록됐는지 확인
   
3. API 엔드포인트 통일성 확인
   컨트롤러들의 경로 패턴이 /boards/:boardId/posts 형식인지 확인
   
4. 전체 테스트 실행
   pnpm test
   
문제가 있으면 해당 파일을 직접 수정해줘.
```

### 8.2 통합 충돌 해결

```bash
# TypeScript 오류가 여러 파일에 있는 경우
claude "apps/backend에서 TypeScript 타입 오류를 모두 찾아서 수정해줘.
       npx tsc --noEmit 결과를 기반으로 하나씩 수정해줘."

# 임포트 누락 정리
claude "app.module.ts를 열고 
       src/ 폴더에 있는 모든 모듈을 임포트해줘.
       순환 의존성이 생기지 않도록 주의해줘."
```

## 9. 멀티에이전트 비용 관리

### 9.1 비용 발생 구조

```
단일 에이전트:
  - 입력: 전체 컨텍스트 × 1 = X 토큰

멀티에이전트 (4개 병렬):
  - 입력: 각 에이전트의 컨텍스트 × 4 = 4X 토큰
  (속도는 4배 빠르지만 비용도 증가)
```

### 9.2 비용 최적화 전략

**전략 1: 컨텍스트 최소화**

```
나쁜 예: 서브에이전트에게 전체 프로젝트 컨텍스트 전달
좋은 예: 서브에이전트에게 해당 작업에 필요한 파일만 전달

예: Posts 모듈 구현 에이전트에게는
  - @prisma/schema.prisma (필수)
  - @CLAUDE.md (필수)  
  - @apps/backend/src/auth/auth.guard.ts (JWT 가드 참조용)
  만 전달, 나머지 파일은 전달하지 않음
```

**전략 2: 모델 선택 최적화**

| 작업 유형 | 추천 모델 | 이유 |
|-----------|-----------|------|
| 단순 CRUD 구현 | claude-haiku-4-5 | 빠르고 저렴 |
| 복잡한 비즈니스 로직 | claude-sonnet-4-5 | 균형 |
| 아키텍처 설계, 디버깅 | claude-opus-4-5 | 최고 품질 |

**전략 3: 재사용 가능한 출력 캐싱**

```bash
# 생성된 코드를 파일로 저장하고 재사용
claude --print "DTO 기본 구조를 생성해줘" > base-dto.txt
# 여러 에이전트가 이 파일을 참조하여 반복 생성 방지
```

**전략 4: 작업 완료 후 /compact 활용**

```
오케스트레이터 세션에서 주기적으로 /compact를 실행하여
누적된 대화 히스토리의 토큰을 절약한다.
```

## 10. 정리 및 체크리스트

### 이 편에서 배운 내용

- 오케스트레이터-워커 패턴: 전체 지휘 에이전트 + 독립 실행 워커
- 직렬 vs 병렬: 의존성이 없고 파일이 분리된 작업만 병렬로
- Race Condition 방지: 파일 소유권 할당, 공유 파일 사전 처리, 브랜치 분리
- 오케스트레이터 프롬프트: 범위, 금지사항, 공통 규칙, 완료 기준 포함
- 비용 관리: 컨텍스트 최소화, 모델 선택, /compact 활용
