# 06. 비동기 멀티태스킹 — 여러 작업을 병렬로 실행하고 관리하기

> **학습 목표**
> - 비동기 실행이 개발자 생산성에 미치는 영향을 이해한다
> - 태스크 큐 관리와 상태 모니터링 방법을 익힌다
> - 독립적 태스크와 의존성 있는 태스크를 구분하여 전략을 세운다
> - 태스크 우선순위 설정과 비용 관리 방법을 배운다
> - 멀티 게시판 8종 게시판 API를 병렬 태스크로 분산 구현한다

---

## 1. 비동기 실행의 핵심 가치

Claude Code나 로컬 터미널 에이전트는 **동기적**으로 작동한다. 개발자가 화면 앞에 앉아서 에이전트가 파일을 수정하는 것을 실시간으로 지켜봐야 한다. 30분짜리 작업이면 30분을 기다려야 한다.

ChatGPT Codex는 **비동기적**으로 작동한다. 태스크를 큐에 넣고 자리를 떠나면 된다. 에이전트가 클라우드에서 작업하는 동안 개발자는 미팅을 하거나 다른 코드를 작성하거나 점심을 먹을 수 있다.

```
[동기 방식 — Claude Code]
개발자 → 태스크 입력 → 기다림(30분) → 결과 확인 → 다음 작업

[비동기 방식 — ChatGPT Codex]
개발자 → 태스크 A 입력 →
         태스크 B 입력 →     ← 30초 만에 모두 큐에 등록
         태스크 C 입력 →
                  [다른 일 하는 중]
         ← 30분 후 → A, B, C 모두 완료 알림
```

세 개의 태스크가 동시에 실행되므로, 각각 30분씩 걸리더라도 총 30분이면 세 개가 모두 완료된다.

## 2. 태스크 큐 관리

### 2.1 태스크 상태

```
┌──────────────────────────────────────────────────────────┐
│                   태스크 상태 흐름                          │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  입력                                                     │
│    ↓                                                     │
│  QUEUED (대기)                                           │
│    ↓ 샌드박스 사용 가능 시                                │
│  RUNNING (실행 중)                                       │
│    ↓                                                     │
│  ┌──────┬──────────────┐                                │
│  ↓      ↓              ↓                                │
│ DONE  FAILED       CANCELLED                            │
│ (완료) (실패)        (취소됨)                             │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

**QUEUED**: 태스크가 입력되어 실행을 기다리는 상태. 샌드박스가 모두 사용 중이면 대기한다.

**RUNNING**: 샌드박스에서 코드를 실행 중인 상태. 레포 클론 → 코드 수정 → 빌드/테스트 → PR 생성 과정을 거친다.

**DONE**: 작업이 완료되어 PR이 생성된 상태.

**FAILED**: 빌드 실패, 테스트 실패, 타임아웃 등으로 작업이 실패한 상태.

**CANCELLED**: 개발자가 직접 취소한 상태.

### 2.2 Codex 대시보드에서 큐 모니터링

```
┌─────────────────────────────────────────────────────┐
│  Codex 태스크 대시보드                                │
├────────────────────────────────────────────────────┤
│  ⟳ RUNNING (2)                                     │
│    ● feat: 댓글 API 구현                    14:32~  │
│    ● feat: 파일 업로드 모듈                 14:33~  │
│                                                    │
│  ○ QUEUED (3)                                      │
│    ○ feat: Q&A 채택 기능             → 다음 실행     │
│    ○ feat: 공지 고정 기능            → 대기 중       │
│    ○ feat: 비공개문의 접근제어       → 대기 중       │
│                                                    │
│  ✓ DONE (2)                                        │
│    ✓ feat: 인증 모듈         PR #1 생성  13:45~14:10│
│    ✓ feat: 게시판 CRUD       PR #2 생성  13:46~14:15│
│                                                    │
│  ✗ FAILED (0)                                      │
└────────────────────────────────────────────────────┘
```

## 3. 독립적 태스크 병렬화 전략

### 3.1 의존성 분석

태스크를 병렬로 실행하려면 먼저 태스크 간 의존성을 분석해야 한다.

```
의존성 있음 (순차 실행 필요):
  - 인증 모듈 → 게시판 API (게시판 API가 JwtGuard를 사용)
  - 게시판 API → 게시물 API (게시물 API가 boardId를 필요로 함)
  - Prisma 스키마 → 모든 서비스 (스키마가 먼저 확정되어야 함)

의존성 없음 (병렬 실행 가능):
  - 댓글 API ↔ 파일 업로드 (서로 독립적)
  - Q&A 채택 ↔ 공지 고정 ↔ 비공개 접근제어 (서로 독립적)
  - 프론트엔드 컴포넌트 A ↔ 프론트엔드 컴포넌트 B
```

### 3.2 의존성 그래프 작성

```
board-hub 구현 의존성 그래프:

[1] Prisma 스키마 확정
        │
        ├──→ [2] 인증 모듈 (auth)
        │           │
        │           ├──→ [3] 게시판 CRUD (board)
        │           │           │
        │           │           ├──→ [4A] 게시물 CRUD (post)
        │           │           │           │
        │           │           │           ├──→ [5A] 댓글 (comment)
        │           │           │           ├──→ [5B] 파일 업로드 (file)
        │           │           │           ├──→ [5C] Q&A 채택
        │           │           │           └──→ [5D] 공지 고정
        │           │           │
        │           │           └──→ [4B] SvelteKit 게시판 목록 페이지
        │           │
        │           └──→ [4C] SvelteKit 로그인/회원가입 페이지
        │
        └──→ 기타 (병렬 가능)

[1]만 완료하면 [2]와 [4B], [4C]는 동시에 시작 가능
[2]와 [3]이 완료되면 [4A], [4B], [4C]를 동시에 시작 가능
[4A]가 완료되면 [5A], [5B], [5C], [5D]를 동시에 시작 가능
```

### 3.3 병렬 실행 타이밍

```
시간: 0분
  태스크 1: Prisma 스키마 작성 → 시작

시간: 15분 (스키마 완료 후)
  태스크 2: 인증 모듈 → 시작
  태스크 3: SvelteKit 로그인 페이지 → 동시 시작 (백엔드 API 없어도 UI 구현 가능)

시간: 45분 (인증 모듈 완료 후)
  태스크 4: 게시판 CRUD API → 시작

시간: 70분 (게시판 CRUD 완료 후)
  태스크 5: 게시물 CRUD API → 시작
  태스크 6: SvelteKit 게시판 목록 → 동시 시작

시간: 100분 (게시물 CRUD 완료 후)
  태스크 7: 댓글 API → 동시 시작
  태스크 8: 파일 업로드 → 동시 시작
  태스크 9: Q&A 채택 → 동시 시작
  태스크 10: 공지 고정 → 동시 시작

시간: 130분
  모든 기능 구현 완료 (PR 10개 리뷰)
```

순차 실행하면 10개 태스크 × 30분 = 300분이지만, 병렬 실행하면 약 130분으로 단축된다.

## 4. 의존성 있는 태스크 순서 관리

### 4.1 태스크 완료 대기 전략

Codex 대시보드에서 이전 태스크의 PR이 완료되었는지 확인한 후 다음 태스크를 시작한다.

```
절차:
1. 태스크 1 실행
2. 태스크 1의 PR 확인 (Files changed 탭)
3. PR 승인 및 머지
4. 태스크 2 실행 (이제 태스크 1의 코드가 레포에 존재)
```

### 4.2 PR 머지 전 다음 태스크 실행하기

PR이 아직 머지되지 않았어도, 브랜치를 지정하여 다음 태스크를 실행할 수 있다.

```
Codex 태스크 입력:

"apps/backend/src/board/ 모듈을 구현해줘.
이 태스크는 codex/feat-auth 브랜치를 기반으로 실행해줘.
(아직 develop에 머지되지 않았으므로 해당 브랜치 기준으로 작업)"
```

이렇게 하면 이전 PR이 머지되기 전에 다음 태스크를 시작할 수 있다.

### 4.3 태스크 설명에 의존성 명시

```
"[의존성 주의]
이 태스크는 다음이 완료된 상태를 가정한다:
- apps/backend/src/auth/ 모듈 존재 (JwtGuard, JwtStrategy 포함)
- User 모델이 prisma/schema.prisma에 정의됨

위 조건이 충족된 상태에서 board 모듈을 구현해줘."
```

## 5. 태스크 우선순위 설정

### 5.1 우선순위 기준

```
P0 (긴급): 프로덕션 버그, 보안 취약점
P1 (높음): 핵심 기능, 사용자에게 직접 영향
P2 (보통): 기능 개선, 성능 최적화
P3 (낮음): 문서화, 리팩터링, 기술 부채
```

### 5.2 태스크에 우선순위 반영

```
Codex 태스크 입력 (P0 긴급):
"[긴급] 프로덕션 버그를 수정해줘.
비밀번호 해싱 없이 평문 저장되는 보안 취약점.
file: apps/backend/src/auth/auth.service.ts의 register()
다른 모든 작업을 중단하고 이것을 먼저 처리해줘."
```

Plus 플랜에서는 동시 실행 태스크 수에 제한이 있으므로, P0 태스크를 먼저 실행하고 나머지를 큐에 넣는다.

## 6. 태스크 완료 알림 설정

### 6.1 GitHub 알림 활용

PR이 생성되면 GitHub 알림이 발송된다. 이메일 알림을 설정하면 태스크 완료 시 즉시 알 수 있다.

```
GitHub → Settings → Notifications
→ Email: 활성화
→ Pull Request: 활성화

이메일 필터 (Gmail 예시):
조건: from:notifications@github.com AND subject:[board-hub] codex/
레이블: "Codex PR"
```

### 6.2 ChatGPT 앱 알림

모바일 ChatGPT 앱을 사용하면 태스크 완료 시 푸시 알림을 받을 수 있다.

```
iPhone: 설정 → ChatGPT → 알림 → 허용
Android: 앱 설정 → 알림 → 허용
```

### 6.3 Slack 봇 연동

팀이 Slack을 사용한다면 GitHub-Slack 연동으로 PR 알림을 채널에서 받는다.

```
/github subscribe [owner]/board-hub pulls

이후 codex/ 브랜치의 PR이 생성될 때마다 Slack 알림
```

## 7. 장시간 실행 태스크 모니터링

### 7.1 타임아웃 예방 전략

Codex 태스크에는 실행 시간 제한이 있다. 너무 큰 태스크는 타임아웃으로 실패할 수 있다.

**위험한 태스크 (타임아웃 가능성)**:
```
❌ "board-hub 프로젝트 전체를 처음부터 구현해줘"
❌ "백엔드와 프론트엔드 전부를 한 번에 만들어줘"
```

**안전한 태스크 (적절한 크기)**:
```
✅ "apps/backend/src/auth/ 모듈 하나만 구현해줘"
✅ "apps/frontend/src/routes/auth/login/ 페이지만 구현해줘"
```

### 7.2 태스크 분할 기준

```
태스크 하나의 적정 크기:
- 파일 수: 5~10개 이내 수정
- 추정 실행 시간: 20~30분 이내
- 기능 단위: NestJS 모듈 하나, SvelteKit 라우트 하나

너무 크면:
- 기능별로 분할
- 백엔드와 프론트엔드 분리
- API 구현과 테스트 분리
```

### 7.3 실행 중인 태스크 확인

```
Codex 대시보드 → RUNNING 탭 → 태스크 클릭
→ 실행 로그 확인:
  ✓ 레포 클론 완료
  ✓ AGENTS.md 로드
  ⟳ 파일 수정 중: apps/backend/src/auth/auth.service.ts
  ⟳ 빌드 실행 중...

로그가 5분 이상 멈춰 있으면:
→ 태스크 취소 후 범위를 줄여서 재실행
```

## 8. 태스크 취소 및 재시작

### 8.1 태스크 취소하기

```
Codex 대시보드 → RUNNING 태스크 → "취소" 버튼 클릭
→ 확인 다이얼로그: "실행 중인 태스크를 취소하시겠습니까?"
→ "취소" 확인
→ 상태: CANCELLED
```

태스크를 취소하면 진행 중인 코드 변경이 저장되지 않는다. 처음부터 다시 시작해야 한다.

### 8.2 실패한 태스크 재시작

```
Codex 대시보드 → FAILED 태스크 → 태스크 클릭
→ 실패 원인 확인 (에러 로그)
→ 지시문 수정
→ "재시작" 버튼 클릭
```

실패 원인이 지시문에 있는 경우:
```
원래 지시문:
"인증 모듈을 구현해줘"

수정된 지시문:
"인증 모듈을 구현해줘. 
주의: jwt 패키지는 @nestjs/jwt 를 사용. 
pnpm add @nestjs/jwt @nestjs/passport passport passport-jwt
를 먼저 실행해줘."
```

## 9. 비용 관리 전략

### 9.1 모델별 비용 이해

Codex는 내부적으로 OpenAI 언어 모델을 사용하며, 모델 선택이 비용과 품질에 영향을 미친다.

```
┌────────────────┬──────────────┬──────────────────────────────┐
│     모델        │     비용     │          적합한 태스크        │
├────────────────┼──────────────┼──────────────────────────────┤
│ o4-mini        │ 낮음         │ 단순 CRUD, 테스트 작성        │
│ o3             │ 높음         │ 복잡한 로직, 아키텍처 설계    │
└────────────────┴──────────────┴──────────────────────────────┘
```

**o4-mini 적합**:
- CRUD API 구현 (반복적인 패턴)
- 테스트 코드 작성
- 문서 업데이트
- 단순 버그 수정

**o3 적합**:
- 복잡한 비즈니스 로직
- 보안 취약점 분석
- 아키텍처 리팩터링
- 성능 최적화

### 9.2 비용 절감 전략

**전략 1: 태스크 범위 최소화**

```
❌ 한 태스크에 모든 것:
"인증, 게시판, 게시물, 댓글 전부 만들어줘"
→ 실패 가능성 높고 비용 낭비

✅ 최소 단위로 분할:
"인증 모듈의 register 기능만 구현해줘"
→ 성공률 높고 비용 효율적
```

**전략 2: 명확한 지시문으로 재실행 방지**

```
지시문이 모호하면 실패 → 재실행 비용 발생
지시문이 명확하면 첫 번에 성공 → 비용 절약
```

**전략 3: 테스트 범위 조정**

```
단순 기능: 핵심 테스트 3~5개
복잡한 기능: 전체 시나리오 테스트
```

**전략 4: Plus 플랜 한도 내에서 효율적 사용**

```
Plus 플랜 월 한도를 효율적으로 사용하려면:
- 우선순위 높은 태스크부터 실행
- 실험적 태스크는 작게 시작
- 성공 패턴을 발견하면 복제하여 사용
```

## 11. 멀티태스킹 실수와 방지 방법

### 실수 1: 같은 파일을 수정하는 태스크 동시 실행

```
❌ 위험:
태스크 A: post.service.ts에 GALLERY 기능 추가
태스크 B: post.service.ts에 PRIVATE 접근제어 추가
→ 두 PR이 같은 파일의 같은 부분을 수정 → 충돌

✅ 안전:
태스크 A 머지 후 태스크 B 실행
또는
태스크 A와 B가 서로 다른 파일을 수정하도록 분할
```

### 실수 2: 의존하는 PR이 머지되기 전에 다음 태스크 실행

```
❌ 위험:
태스크 A: JwtGuard 구현 (PR #3 — 아직 미머지)
태스크 B: JwtGuard를 사용하는 Board API 구현 시작
→ 태스크 B가 JwtGuard를 찾지 못해 실패

✅ 안전:
태스크 A PR 머지 완료 후 태스크 B 시작
또는 태스크 B에 "codex/feat-auth 브랜치 기반으로 작업" 명시
```

### 실수 3: 스키마 변경 태스크 병렬 실행

```
❌ 위험:
태스크 A: Post 모델에 isPinned 컬럼 추가
태스크 B: Post 모델에 isAnonymous 컬럼 추가
→ 두 마이그레이션이 같은 테이블 수정 → 충돌

✅ 안전:
스키마 변경은 한 번에 모아서 처리
하나의 태스크: "Post 모델에 isPinned, isAnonymous 모두 추가"
```
