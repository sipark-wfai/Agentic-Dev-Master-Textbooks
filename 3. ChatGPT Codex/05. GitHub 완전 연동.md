# 05. GitHub 완전 연동 — 이슈·PR·브랜치를 Codex로 자동화하는 법

> **학습 목표**
> - GitHub와 Codex 사이의 연동 아키텍처를 이해한다
> - GitHub Issue를 Codex 태스크로 직접 전환하는 방법을 익힌다
> - 브랜치 자동 생성, PR 생성, 코드 리뷰 프로세스를 자동화한다
> - 브랜치 보호 규칙을 설정하여 안전한 협업 환경을 만든다
> - 멀티 게시판 GitHub 이슈 목록을 Codex로 자동 해결하는 워크플로우를 구축한다

---

## 1. GitHub ↔ Codex 연동 아키텍처

```

├─────────────────────────────────────────────────────────────────┤

│    │                                                            │
│    ├── GitHub Issue 생성                                         │
│    │     │                                                      │
│    │     ▼                                                      │
│    │   GitHub Issues (이슈 목록)                                 │
│    │     │                                                      │
│    │     │ (Codex가 직접 읽거나 개발자가 태스크에 이슈 번호 명시)  │
│    │     ▼                                                      │
│    └── Codex 태스크 입력                                          │
│              │                                                  │
│              ▼                                                  │
│         OpenAI Codex                                            │
│              │                                                  │
│    ┌─────────┴──────────┐                                       │

│    ▼                    ▼                                       │

│    │                    │                                       │
│    └─────────┬──────────┘                                       │
│              │                                                  │
│              ▼                                                  │
│         코드 수정 (샌드박스)                                      │
```

## 2. GitHub Issue 효과적으로 작성하기

Codex가 이슈를 읽고 정확한 작업을 수행하려면, 이슈 자체가 명확해야 한다.

### 2.1 이슈 템플릿 설정

레포지토리에 이슈 템플릿을 추가하면 팀원들이 일관된 형식으로 이슈를 작성한다.

```bash
mkdir -p .github/ISSUE_TEMPLATE
```

**버그 리포트 템플릿** (`.github/ISSUE_TEMPLATE/bug_report.md`):

```markdown

name: 버그 리포트
about: 버그를 신고합니다
title: 'fix: [간단한 버그 설명]'
labels: bug
assignees: ''
---

## 버그 설명
[버그를 명확하게 설명해주세요]

## 재현 방법
1. [단계 1]
2. [단계 2]
3. [오류 발생]

## 예상 동작
[정상적으로 동작해야 하는 결과]

## 실제 동작
```

### 2.2 Codex에 최적화된 이슈 작성 예시

**Issue #42 — 갤러리 게시판 썸네일 미생성 버그**

```markdown
## 버그 설명
갤러리 게시판에 이미지를 업로드하면 thumbnailUrl이 항상 null로 저장됩니다.
게시판 목록에서 이미지 미리보기가 표시되지 않습니다.

## 재현 방법
1. POST /auth/login으로 로그인
2. POST /posts에 multipart/form-data로 이미지 업로드
   body: { boardId: 2, title: "테스트", content: "테스트" }
   file: 이미지 파일 첨부
3. 응답의 thumbnailUrl이 null

## 예상 동작
thumbnailUrl: "/uploads/thumbs/[파일명]" 형태의 경로가 반환되어야 함

## 실제 동작
thumbnailUrl: null

## 영향 범위
- 발생 위치: POST /posts
- 관련 모듈: apps/backend/src/file/file.service.ts

## 관련 파일
- apps/backend/src/file/file.service.ts (generateThumbnail 함수)
- apps/backend/src/post/post.service.ts (create 메서드)
- prisma/schema.prisma (Post 모델의 thumbnailUrl 필드)

## Codex 지시 힌트
sharp 라이브러리가 설치되어 있음 (package.json 확인).
generateThumbnail 함수가 await 없이 호출되는 것으로 의심됨.
```

## 3. GitHub Issue를 Codex 태스크로 전환하기

### 3.1 직접 이슈 번호 참조

```
Codex 태스크 입력:

"GitHub Issue #42를 해결해줘.

이슈를 직접 읽어서 버그 내용을 파악하고,
apps/backend/src/file/file.service.ts의 썸네일 생성 로직을 수정해줘.

성공 기준:
- POST /posts에 이미지 업로드 시 thumbnailUrl이 null이 아닌 경로를 반환
- 회귀 테스트 추가
- 빌드 + 테스트 통과"
```

### 3.2 이슈 내용을 직접 붙여넣기

이슈 내용이 길거나 Codex가 이슈를 읽지 못하는 경우:

```
Codex 태스크 입력:

"다음 버그를 수정해줘 (Issue #42):

[버그]
갤러리 게시판 이미지 업로드 시 thumbnailUrl이 null로 저장됨

[원인 추정]
file.service.ts의 generateThumbnail()이 async 함수인데
post.service.ts에서 await 없이 호출됨

[수정 위치]
apps/backend/src/post/post.service.ts의 create() 메서드

[수정 후]
await this.fileService.generateThumbnail(fileId) 로 변경

[성공 기준]
이미지 업로드 후 thumbnailUrl에 값이 저장되는 테스트 추가
PR에 'Closes #42' 포함"
```

### 3.3 레이블로 이슈 분류하기

GitHub 레이블을 활용하면 이슈를 체계적으로 관리할 수 있다.

```
레이블 구성:
- codex-ready: Codex로 처리할 준비가 된 이슈
- in-progress: Codex가 처리 중인 이슈
- needs-review: PR 리뷰 대기 중
- blocked: 의존성이 있어 현재 처리 불가
- priority-high: 먼저 처리해야 하는 이슈
- priority-low: 나중에 처리해도 되는 이슈
```

## 4. 브랜치 자동 생성 패턴

Codex는 태스크를 실행할 때 자동으로 브랜치를 생성한다.

### 4.1 Codex 브랜치 명명 패턴

```
codex/[type]-[brief-description]
codex/fix-issue-42-thumbnail-null
codex/feat-comment-module
codex/refactor-user-service
codex/test-auth-module
codex/docs-api-swagger
```

AGENTS.md에서 브랜치 명명 규칙을 지정하면 Codex가 따른다:

```markdown
## 브랜치 전략 (AGENTS.md에서)

Codex는 다음 형식으로 브랜치를 생성한다:
- 버그 수정: codex/fix-issue-[번호]-[설명]
- 기능 개발: codex/feat-[기능명]
- 리팩터링: codex/refactor-[설명]
- 테스트: codex/test-[모듈명]

PR 대상 브랜치: develop (main이 아님)
```

### 4.2 브랜치 보호 규칙 설정

```
GitHub → board-hub → Settings → Branches → Add branch protection rule

Pattern: main
Rules:
  ✅ Require a pull request before merging
    Required approvals: 1
    ✅ Dismiss stale pull request approvals when new commits are pushed
    ✅ Require review from Code Owners
  ✅ Require status checks to pass before merging
    Required status checks: build, test
  ✅ Require branches to be up to date before merging
  ✅ Do not allow bypassing the above settings

Pattern: develop
Rules:
  ✅ Require a pull request before merging
    Required approvals: 1
```

이 설정으로 Codex가 올린 PR도 반드시 1명 이상의 리뷰어 승인이 필요하다.

## 5. PR 자동 생성 및 설명서 작성

### 5.1 Codex PR의 구조

Codex가 생성하는 PR에는 다음 내용이 포함된다:

```markdown
## PR 제목
feat: 갤러리 게시판 썸네일 자동 생성 기능 추가

## PR 설명 (Codex 자동 생성)

### 변경 요약
- file.service.ts에 generateThumbnail() 메서드 추가
- post.service.ts에서 이미지 업로드 시 썸네일 생성 호출
- Post 모델에 thumbnailUrl 필드 추가

### 변경 이유
이슈 #42: 갤러리 게시판에서 이미지 업로드 시 썸네일이 생성되지 않는 버그 수정

### 테스트 결과
- pnpm build: ✅ 성공
- pnpm test: ✅ 47/47 통과
- 새 테스트: 이미지 업로드 후 thumbnailUrl 검증 (2개 추가)

### 변경된 파일
- apps/backend/src/file/file.service.ts (수정)
- apps/backend/src/post/post.service.ts (수정)
- prisma/schema.prisma (수정)
- prisma/migrations/... (추가)
- apps/backend/src/file/file.spec.ts (수정)

Closes #42
```

### 5.2 PR 설명 품질 향상 지시

태스크 지시문에 PR 설명 요건을 추가하면 더 상세한 PR이 생성된다:

```
"PR 생성 시 다음을 반드시 포함해줘:
1. 변경 이유 (이슈 번호 포함)
2. 변경된 파일 목록과 각 파일의 변경 요약
3. 빌드 + 테스트 결과
4. 로컬 테스트 방법 (curl 명령어 예시 포함)
5. 관련 이슈: 'Closes #[번호]' 형식"
```

## 6. 코드 리뷰 프로세스

### 6.1 Codex PR 리뷰 표준 프로세스

```
1단계: 자동 체크 확인 (CI)
  - GitHub Actions 빌드 통과 여부
  - 테스트 통과 여부
  - 린트 오류 여부

2단계: 변경 파일 스캔
  - PR의 Files changed 탭에서 전체 파일 목록 확인
  - 예상치 못한 파일 변경 여부 확인

3단계: 핵심 로직 리뷰
  - Service 레이어의 비즈니스 로직 검토
  - 보안 취약점 확인 (인증/인가, SQL 인젝션, XSS)
  - 에러 처리 확인

4단계: 테스트 리뷰
  - 테스트 케이스가 실제 시나리오를 커버하는지 확인
  - trivial 테스트 (의미 없는 커버리지 채우기) 여부 확인

5단계: 승인 또는 재요청
  - 승인: "Approve" → "Merge pull request"
  - 재요청: 구체적인 수정 요청 코멘트 → Codex 재태스크
```

### 6.2 CODEOWNERS 설정

특정 파일이 변경될 때 자동으로 리뷰어를 지정한다.

```bash
# .github/CODEOWNERS
# 전체 코드: team-lead 리뷰 필요
* @team-lead

# Prisma 스키마 변경: DBA 추가 리뷰
/prisma/schema.prisma @team-lead @dba-reviewer

# 보안 관련 파일
/apps/backend/src/auth/** @team-lead @security-reviewer

# 프론트엔드
/apps/frontend/** @team-lead @frontend-reviewer
```

## 7. GitHub Actions와 Codex 연동

### 7.1 PR 생성 시 자동 테스트 설정

`.github/workflows/ci.yml`:

```yaml
name: CI

on:
  pull_request:
    branches: [ main, develop ]

jobs:
  test:
    runs-on: ubuntu-latest
    
    services:
      postgres:
        image: postgres:16
        env:
          POSTGRES_PASSWORD: postgres
          POSTGRES_DB: board_hub_test
        options: >-
          --health-cmd pg_isready
          --health-interval 10s
          --health-timeout 5s
          --health-retries 5
        ports:
          - 5432:5432

    steps:
      - uses: actions/checkout@v4
      
      - uses: pnpm/action-setup@v3
        with:
          version: 9
      
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'pnpm'
      
      - name: Install dependencies
        run: pnpm install
      
      - name: Type check
        run: pnpm -r exec tsc --noEmit
      
      - name: Lint
        run: pnpm lint
      
      - name: Build
        run: pnpm build
      
      - name: Run tests
        run: pnpm test
        env:
          DATABASE_URL: postgresql://postgres:postgres@localhost:5432/board_hub_test
          JWT_SECRET: test-secret-key
      
      - name: Upload coverage
        uses: codecov/codecov-action@v3
        with:
          files: ./apps/backend/coverage/lcov.info
```

## 8. 멀티 레포(Monorepo) 환경에서의 GitHub 연동

board-hub는 모노레포이므로 특별한 고려가 필요하다.

### 8.1 Codex의 모노레포 인식

AGENTS.md에 모노레포 구조를 명확히 설명하면 Codex가 올바른 경로에서 작업한다:

```markdown
## 모노레포 구조 (AGENTS.md)

이 레포지토리는 pnpm workspace 모노레포다.

패키지 경로:
- apps/frontend: SvelteKit 프론트엔드
- apps/backend: NestJS 백엔드
- packages/shared: 공유 타입·유틸

각 패키지의 scripts:
- apps/backend: 자체 package.json의 스크립트 사용
- apps/frontend: 자체 package.json의 스크립트 사용
- 루트: pnpm -r [command]로 모든 패키지에 실행

중요: 백엔드 작업은 apps/backend에서,
      프론트엔드 작업은 apps/frontend에서 수행.
      루트 package.json은 workspace 설정만 담당.
```

### 8.2 path-filter로 변경된 패키지만 CI 실행

대형 모노레포에서 변경이 없는 패키지의 CI를 건너뛸 수 있다:

```yaml
name: CI (Monorepo)

on:
  pull_request:
    branches: [ main, develop ]

jobs:
  detect-changes:
    runs-on: ubuntu-latest
    outputs:
      backend: ${{ steps.filter.outputs.backend }}
      frontend: ${{ steps.filter.outputs.frontend }}
    steps:
      - uses: actions/checkout@v4
      - uses: dorny/paths-filter@v3
        id: filter
        with:
          filters: |
            backend:
              - 'apps/backend/**'
              - 'packages/shared/**'
              - 'prisma/**'
            frontend:
              - 'apps/frontend/**'
              - 'packages/shared/**'

  test-backend:
    needs: detect-changes
    if: needs.detect-changes.outputs.backend == 'true'
    runs-on: ubuntu-latest
    steps:
      - name: Test Backend
        run: cd apps/backend && pnpm test

  test-frontend:
    needs: detect-changes
    if: needs.detect-changes.outputs.frontend == 'true'
    runs-on: ubuntu-latest
    steps:
      - name: Test Frontend
        run: cd apps/frontend && pnpm build
```

## 9. 실전: 멀티 게시판 GitHub 이슈 목록 자동 해결 워크플로우

### 9.1 이슈 목록 생성

board-hub 레포지토리에 다음 이슈들을 생성한다:

```
Issue #1: feat: 사용자 인증 모듈 구현 (JWT 로그인/회원가입)
Issue #2: feat: 게시판 관리 API (8종 게시판 CRUD)
Issue #3: feat: 게시물 CRUD API (기본 게시물 작성·수정·삭제)
Issue #4: feat: 댓글 API (게시물별 댓글 작성·삭제)
Issue #5: feat: 파일 업로드 모듈 (이미지·동영상, 썸네일)
Issue #6: feat: Q&A 게시판 답변 채택 기능
Issue #7: feat: 공지 게시판 상단 고정 기능
Issue #8: feat: 비공개문의 게시판 접근 제어
```

### 9.2 이슈 처리 우선순위 설정

```
의존성 그래프:
#1 (인증) → #2 (게시판) → #3 (게시물) → #4 (댓글)
                              └→ #5 (파일 업로드)
                              └→ #6 (Q&A 채택)
                              └→ #7 (공지 고정)
                              └→ #8 (비공개 접근제어)

순서:
1단계: #1 (인증) 먼저 완료
2단계: #2 (게시판) 완료
3단계: #3, #5 병렬 실행 가능
4단계: #4, #6, #7, #8 병렬 실행 가능 (각자 독립적)
```

### 9.3 Codex 태스크 순서 실행

**1단계 태스크 (Issue #1)**:
```
"GitHub Issue #1을 해결해줘.
JWT 기반 인증 모듈을 apps/backend/src/auth/에 구현해줘.
POST /auth/register, POST /auth/login, POST /auth/logout, GET /auth/me
Closes #1"
```

**2단계 태스크 (Issue #2)** — #1 머지 후:
```
"GitHub Issue #2를 해결해줘.
게시판 관리 API를 apps/backend/src/board/에 구현해줘.
인증은 Issue #1에서 구현된 JwtGuard를 사용.
Closes #2"
```

**3단계 병렬 태스크** — #2 머지 후 동시 실행:
```
태스크 A: "GitHub Issue #3을 해결해줘. 게시물 CRUD API 구현. Closes #3"
태스크 B: "GitHub Issue #5를 해결해줘. 파일 업로드 모듈 구현. Closes #5"
```

### 9.4 이슈 자동 Close 설정

PR 설명에 `Closes #[번호]`를 포함하면 PR이 머지될 때 이슈가 자동으로 닫힌다.

```
PR 설명 예시:
"feat: 사용자 인증 모듈 구현

...변경 내용...

Closes #1"
```

Codex에 이 패턴을 명시적으로 지시한다:

```
AGENTS.md에 추가:
## PR 규칙
- 이슈를 해결하는 PR은 반드시 'Closes #[이슈번호]'를 PR 본문에 포함한다
- 여러 이슈를 해결하는 경우: 'Closes #1, Closes #2'
```

## 10. 고급 GitHub 연동 전략

### 10.1 GitHub Projects와 연동

GitHub Projects (칸반 보드)를 사용하면 이슈와 PR 진행 상황을 시각적으로 관리할 수 있다.

```
GitHub Projects 보드 구성:
┌──────────┬──────────┬──────────┬──────────┬──────────┐
│  Backlog  │ Codex 대기│ Codex 진행│ 리뷰 대기 │  완료    │
├──────────┼──────────┼──────────┼──────────┼──────────┤
│ Issue #6  │ Issue #3  │ Issue #5  │ PR #12   │ Issue #1 │
│ Issue #7  │ Issue #4  │           │           │ Issue #2 │
│ Issue #8  │           │           │           │           │
└──────────┴──────────┴──────────┴──────────┴──────────┘
```

자동화 설정:
- 이슈 생성 → Backlog로 자동 이동
- Codex 태스크 시작 → "Codex 진행"으로 이동
- PR 생성 → "리뷰 대기"로 이동
- PR 머지 → "완료"로 이동

### 10.2 Codex PR에 자동 리뷰어 지정

```yaml
# .github/workflows/auto-assign-reviewer.yml
name: Auto Assign Reviewer

on:
  pull_request:
    types: [opened]
    branches: [ develop, main ]

jobs:
  assign:
    runs-on: ubuntu-latest
    if: startsWith(github.head_ref, 'codex/')
    steps:
      - uses: actions/github-script@v7
        with:
          script: |
            await github.rest.pulls.requestReviewers({
              owner: context.repo.owner,
              repo: context.repo.repo,
              pull_number: context.issue.number,
              reviewers: ['team-lead']
            });
            await github.rest.issues.addLabels({
              owner: context.repo.owner,
              repo: context.repo.repo,
              issue_number: context.issue.number,
              labels: ['codex', 'needs-review']
            });
```

### 10.3 PR 크기 제한

Codex가 너무 큰 PR을 올리지 못하도록 크기를 제한하는 규칙을 추가한다.

```yaml
# .github/workflows/pr-size-check.yml
name: PR Size Check

on:
  pull_request:
    types: [opened, synchronize]

jobs:
  size-check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/github-script@v7
        with:
          script: |
            const pr = await github.rest.pulls.get({
              owner: context.repo.owner,
              repo: context.repo.repo,
              pull_number: context.issue.number
            });
            
            const additions = pr.data.additions;
            const deletions = pr.data.deletions;
            const total = additions + deletions;
            
            if (total > 500) {
              await github.rest.issues.createComment({
                owner: context.repo.owner,
                repo: context.repo.repo,
                issue_number: context.issue.number,
                body: `⚠️ 이 PR은 ${total}줄을 변경합니다. 500줄 이하로 분할을 권장합니다.`
              });
            }
```

### 12.1 목표

1. GitHub Issue 생성

**Step 1**: 이슈 템플릿 Push

```bash
mkdir -p .github/ISSUE_TEMPLATE .github/workflows
# 위의 템플릿 파일들을 생성
git add .github/
git commit -m "ci: add issue templates and GitHub Actions"
git push origin main
```

**Step 2**: 이슈 생성 및 레이블 설정

GitHub에서 Issue #1을 작성한다. 레이블: `enhancement`, `codex-ready`

```
"GitHub Issue #1을 해결해줘.

PR에 'Closes #1' 포함.
```

**Step 4**: CI 자동 실행 확인

**Step 5**: 리뷰 및 머지
