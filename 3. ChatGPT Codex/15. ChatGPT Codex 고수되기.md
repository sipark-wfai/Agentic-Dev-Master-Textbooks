## 1. 고수의 태스크 설계 루틴

### 1.1 초보와 고수의 차이

```
[초보의 태스크 설계]
"로그인 기능 만들어줘"
→ 결과: 불완전한 구현, 재실행 필요

[고수의 태스크 설계]
PRD 확인 → 범위 정의 → 의존성 파악 → 성공 기준 수립 → 태스크 작성
→ 결과: 첫 번에 완성도 높은 구현
```

### 1.2 고수의 태스크 설계 5단계

**1단계: PRD 기능 ID 확인**
```
구현할 기능의 PRD 기능 ID를 먼저 확인한다.
AUTH-002, POST-003 등 명확한 ID로 범위를 정한다.
```

**2단계: 의존성 파악**
```
이 태스크가 성공하려면 무엇이 먼저 있어야 하는가?
- AUTH-002 로그인 → JwtStrategy, PrismaService, UserModule이 있어야 함
```

**3단계: 파일 수 예측**
```
이 태스크에서 생성·수정될 파일이 10개 이하인가?
10개 초과라면 분할한다.
```

**4단계: 테스트 케이스 미리 작성**
```
PRD의 성공 기준을 테스트 케이스로 변환해둔다.
이를 태스크 지시문에 포함한다.
```

**5단계: 재사용 가능한 지시문 저장**
```
성공한 태스크 지시문을 템플릿으로 저장한다.
비슷한 태스크에서 재사용한다.
```

### 1.3 고수의 일일 루틴

```
09:00 오전 태스크 큐 설정
  - 밤 사이 완료된 PR 확인
  - 오늘 실행할 태스크 3~5개 준비
  - 우선순위 결정 (P0 → P1 → P2)

09:30 병렬 태스크 실행 (3개)
  - 의존성 없는 태스크 동시 실행
  - 큐에 넣고 다른 업무 시작

12:00 점심 전 PR 리뷰
  - 오전 태스크 완료 PR 확인
  - CI 통과 여부 확인
  - 문제없으면 Approve

13:00 오후 태스크 큐 설정
  - 오전 PR 머지 후 의존성 해제된 태스크 실행
  - 추가 병렬 태스크 3개 실행

17:00 저녁 PR 리뷰
  - 오후 태스크 완료 PR 확인
  - 내일을 위한 태스크 큐 준비

다음날 09:00: 반복
```

이 루틴으로 하루에 6~10개의 태스크를 처리할 수 있다.

## 2. 비용 최소화 전략

### 2.1 모델 선택 최적화

```
┌─────────────────────────────────────────────────────┐
│             모델별 최적 사용 시나리오                  │
├──────────────────┬──────────────────────────────────┤
│    o4-mini       │    o3                             │
│    (비용 낮음)    │    (비용 높음)                    │
├──────────────────┼──────────────────────────────────┤
│ CRUD API 구현    │ 복잡한 알고리즘                   │
│ 테스트 작성      │ 보안 취약점 분석                  │
│ 문서 생성        │ 아키텍처 설계 검토                 │
│ 단순 버그 수정   │ 성능 최적화 전략                  │
│ DTO 작성         │ 레거시 코드 분석                  │
│ 스타일 수정      │ 복잡한 리팩터링                   │

80%의 태스크는 o4-mini로 처리 가능하다.
o3는 복잡한 판단이 필요한 20%에만 사용한다.
```

### 2.2 태스크 효율화 전략

**전략 1: AGENTS.md로 재실행 방지**

명확한 AGENTS.md가 있으면 첫 번에 올바른 코드가 생성된다.
재실행은 비용의 2배를 쓰는 것과 같다.

**전략 2: 지시문 템플릿 라이브러리 구축**

성공한 태스크 지시문을 팀 문서에 저장한다.

```markdown
# 태스크 지시문 라이브러리 (team-wiki/codex-templates.md)

## NestJS 모듈 생성 템플릿
[모듈명] 모듈을 apps/backend/src/[module]/에 생성해줘.
docs/API.md의 [섹션명] 스펙을 기반으로...

## SvelteKit 페이지 생성 템플릿
apps/frontend의 [경로] 페이지를 생성해줘.
+page.svelte와 +page.server.ts를 함께 작성...

## 테스트 추가 템플릿
[서비스파일]의 단위 테스트를 완성해줘.
Jest + @nestjs/testing 사용...
```

**전략 3: 배치 태스크**

여러 작은 작업을 하나의 태스크로 묶는다.

```
❌ 비효율:
태스크 1: "UserService에 JSDoc 추가"
태스크 2: "PostService에 JSDoc 추가"
태스크 3: "CommentService에 JSDoc 추가"

✅ 효율적:
태스크 1: "apps/backend/src/ 의 모든 Service 파일에 JSDoc 주석을 추가해줘.
           각 public 메서드에 @param, @returns, @throws 포함"
```

**전략 4: 재사용 가능한 AGENTS.md 패턴**

회사·팀별 공통 AGENTS.md 패턴을 만들어 새 프로젝트에 재사용한다.

```markdown

## 새 프로젝트 시작 시:
1. 패턴 라이브러리에서 복사
2. 프로젝트별 커스터마이징
3. 팀과 공유하여 검토
```

## 3. 팀 협업에서 Codex 활용

### 3.1 팀 도입 단계

```
1단계: 파일럿 (1명)
  - 개인 프로젝트에서 먼저 학습
  - 성공 패턴과 실패 패턴 파악
  - 팀 내 Codex 가이드 작성

2단계: 소규모 도입 (2~3명)
  - 새 기능 개발에 Codex 적용
  - 팀 공유 AGENTS.md 작성
  - PR 리뷰 문화 정립 (Codex PR도 동일하게 리뷰)

3단계: 전체 팀 도입
  - 모든 이슈에 codex-ready 레이블 체계 적용
  - 태스크 분배 회의 (주간)
  - Codex PR 리뷰 담당자 로테이션

4단계: 프로세스 최적화
  - 태스크 지시문 라이브러리 구축
  - AGENTS.md 정기 업데이트 (월간)
  - 비용 모니터링 및 최적화
```

### 3.2 팀 공유 AGENTS.md 관리

```markdown
# 팀 AGENTS.md 관리 정책

## 소유권
AGENTS.md는 팀 전체의 합의로 변경한다.
개인이 임의로 수정하면 다른 팀원의 태스크에 영향을 줄 수 있다.

## 변경 절차
1. AGENTS.md 변경 PR 생성
2. 팀 리뷰 (최소 2명 Approve)
3. 다음 주 월요일에 머지 (주간 일정에 맞춤)
4. 변경 내용을 팀 Slack에 공유

## 정기 검토
- 월간: AGENTS.md 전체 내용 검토
  - 더 이상 유효하지 않은 규칙 제거
  - 새로운 패턴 추가
  - 기술 스택 버전 업데이트
```

### 3.3 역할별 태스크 분배

```
기획자/PM 역할:
- GitHub Issue 작성 (버그 리포트, 기능 요청)
- PRD 관리 및 업데이트
- Codex 태스크 결과 검토 (기능 동작 확인)

개발 리드 역할:
- AGENTS.md 설계 및 관리
- 복잡한 태스크 지시문 작성
- PR 최종 리뷰 및 머지 승인
- 아키텍처 결정

주니어 개발자 역할:
- 간단한 버그 수정 태스크 실행
- 테스트 작성 태스크 실행
- Codex PR 1차 리뷰
- 태스크 결과 문서화

QA 엔지니어 역할:
- E2E 테스트 시나리오 작성 (Playwright)
- 버그 이슈 상세 작성 (재현 방법 포함)
- 릴리즈 전 Codex PR 전체 검증
```

### 3.4 Codex PR 코드 리뷰 문화

Codex가 올린 PR을 잘못 다루면 문제가 발생한다.

```
잘못된 문화 ❌:
"Codex가 올린 거니까 믿고 그냥 머지"
→ 보안 취약점, 버그, PRD 불일치가 통과됨

올바른 문화 ✅:
"Codex PR도 사람 PR과 동일한 기준으로 리뷰"
→ CI 통과 확인
→ 코드 로직 검토
→ 테스트 의미 있는지 확인
→ 보안 취약점 없는지 확인
→ PRD 기능 ID와 일치하는지 확인
```

### 4.2 Vercel 프론트엔드 자동 배포

```yaml
# .github/workflows/deploy-frontend.yml
name: Deploy Frontend to Vercel

on:
  push:
    branches: [ main ]
    paths: [ 'apps/frontend/**' ]

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production
    
    steps:
      - uses: actions/checkout@v4
      
      - uses: pnpm/action-setup@v3
        with:
          version: 9
      
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'pnpm'
      
      - run: pnpm install --frozen-lockfile
      - run: pnpm --filter frontend build
      
      - name: Deploy to Vercel
        uses: amondnet/vercel-action@v25
        with:
          vercel-token: ${{ secrets.VERCEL_TOKEN }}
          vercel-org-id: ${{ secrets.VERCEL_ORG_ID }}
          vercel-project-id: ${{ secrets.VERCEL_PROJECT_ID_FRONTEND }}
          working-directory: apps/frontend
          vercel-args: '--prod'
```

## 5. ChatGPT Codex vs Claude Code 선택 기준

15편 시리즈의 마지막으로, 두 에이전트 도구의 선택 기준을 정리한다.

```
┌─────────────────────────────────────────────────────┐
│           Codex vs Claude Code 선택 기준             │
├───────────────────────┬─────────────────────────────┤
│    Codex 선택          │    Claude Code 선택          │
├───────────────────────┼─────────────────────────────┤
│ 비동기 실행이 중요할 때 │ 실시간 피드백이 필요할 때   │
│ 장시간 작업 (>10분)    │ 단시간 반복 작업 (<5분)     │
│ 여러 작업 병렬화 필요  │ 하나씩 순서대로 처리        │
│ GitHub 중심 워크플로우 │ 로컬 파일 직접 편집         │
│ 팀 협업, PR 기반 개발  │ 개인 프로젝트, 즉각 반영    │
│ 환경 독립성 필요       │ 로컬 환경에서 바로 테스트   │
│ 기획자·디자이너도 사용 │ 개발자 중심 사용            │
└───────────────────────┴─────────────────────────────┘

혼합 전략 (권장):
- 대형 기능 구현: Codex (비동기, 병렬)
- 세밀한 조정: Claude Code (실시간)
- 빠른 버그 수정: Claude Code
- 테스트 자동화: Codex (배치)
```

### 6.2 OpenAI Assistants API

Codex처럼 파일을 읽고 코드를 실행하는 에이전트를 직접 만드는 API다.

```python
# Assistants API 예시
assistant = client.beta.assistants.create(

    tools=[{"type": "code_interpreter"}, {"type": "file_search"}],
    model="gpt-4o",

thread = client.beta.threads.create()
message = client.beta.threads.messages.create(
    thread_id=thread.id,
    role="user",
    content="Review this NestJS service file",

run = client.beta.threads.runs.create_and_poll(
```

### 6.3 LangChain·LangGraph 에이전트

더 복잡한 에이전트 워크플로우를 코드로 구성하는 프레임워크다.

```python
# LangGraph 에이전트 예시
from langgraph.graph import StateGraph, END
from langchain_openai import ChatOpenAI

# 상태 정의
class AgentState(TypedDict):
    task: str
    code: str
    test_result: str
    needs_revision: bool

# 노드 정의
def write_code(state: AgentState) -> AgentState:
    llm = ChatOpenAI(model="gpt-4o")
    code = llm.invoke(f"Write code for: {state['task']}")
    return {**state, "code": code.content}

def run_tests(state: AgentState) -> AgentState:
    # 테스트 실행 로직
    result = subprocess.run(["pytest", "-v"], capture_output=True, text=True)
    return {**state, "test_result": result.stdout, "needs_revision": result.returncode != 0}

# 그래프 구성
graph = StateGraph(AgentState)
graph.add_node("write_code", write_code)
graph.add_node("run_tests", run_tests)
graph.add_edge("write_code", "run_tests")
graph.add_conditional_edges("run_tests", lambda s: "write_code" if s["needs_revision"] else END)
```

## 9. Codex 고수의 마인드셋

마지막으로, ChatGPT Codex를 진정한 생산성 도구로 만드는 마인드셋이다.

**"에이전트는 도구다, 판단은 인간이 한다"**

Codex는 강력하지만 실수한다. 환각, 보안 취약점, PRD 불일치 — 이 모든 것을 잡아내는 것이 개발자의 역할이다. PR 리뷰를 게을리하지 않는다.

**"작은 태스크가 좋은 코드를 만든다"**

거대한 태스크보다 작고 명확한 태스크가 더 좋은 결과를 낸다. 타임아웃도 없고, 충돌도 없고, 검토도 쉽다.

**"문서가 코드의 품질을 결정한다"**

AGENTS.md, PRD, ERD가 명확할수록 Codex의 결과물이 좋아진다. 문서에 투자하는 시간이 코드 수정에 드는 시간을 줄인다.

**"비동기를 두려워하지 않는다"**

Codex가 작업하는 동안 다른 일을 한다. 이것이 에이전트 시대의 멀티태스킹이다.

**"팀과 함께 성장한다"**

AGENTS.md를 팀이 함께 관리하고, PR 리뷰 문화를 함께 정립한다. Codex는 팀 도구다.

---

> **한줄 요약**
> Codex 고수는 명확한 AGENTS.md와 설계 문서로 재실행을 방지하고, 비동기 병렬 태스크로 시간을 절약하며, 팀 공유 지시문 라이브러리로 일관된 코드를 유지하고, 모든 PR을 사람과 동일한 기준으로 리뷰하며, 다음 단계로 OpenAI API와 LangGraph를 향해 나아간다.

## 시리즈 완주를 축하한다

15편의 여정을 통해 ChatGPT Codex의 입문부터 실전 마스터까지 완주했다.

이 시리즈에서 배운 핵심:
1. Codex는 에이전틱 코딩 플랫폼이다 (1편)
2. GitHub 연동과 AGENTS.md가 기반이다 (2~3편)
3. 명확한 태스크 지시문이 성공을 결정한다 (4편)
4. GitHub와 CI/CD를 연동하면 자동화된다 (5편)
5. 비동기 병렬 실행으로 시간을 절약한다 (6편)
6. 샌드박스 환경을 이해하면 오류가 줄어든다 (7편)
7. 에이전트 친화적 PRD와 설계서가 품질을 결정한다 (8~9편)
8. PRD → 코드, 설계서 → 코드 전환 전략이 있다 (10~11편)
9. 실전 풀스택 구현은 분할하여 정복한다 (12편)
10. 품질 자동화로 기술 부채를 없앤다 (13편)
11. 20가지 오류를 알면 막힐 것이 없다 (14편)
12. 팀과 함께 성장하는 것이 진정한 마스터다 (15편)

다음 여정은 OpenAI API, Assistants API, LangGraph로 이어진다.
