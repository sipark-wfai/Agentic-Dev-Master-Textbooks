# 04. 태스크 요청 마스터 — 효과적인 지시문 작성과 결과 검토법

> **학습 목표**
> - Codex 태스크 요청의 기본 구조와 원칙을 이해한다
> - 10가지 태스크 유형별 최적의 지시문 패턴을 익힌다
> - PR 결과를 효과적으로 검토하는 방법을 배운다
> - 재요청(refinement)으로 결과를 개선하는 기술을 습득한다
> - 멀티 게시판 프로젝트의 실전 태스크 5개를 완성한다

## 1. 태스크 요청의 기본 구조

좋은 태스크 지시문은 에이전트가 "무엇을", "어떻게", "어느 수준까지" 해야 하는지 명확하게 알려준다.

### 1.1 기본 구성 요소

```
┌─────────────────────────────────────────────────────────┐
│                   태스크 지시문 구조                       │
├─────────────────────────────────────────────────────────┤
│  1. 목표 (Goal)                                         │
│     무엇을 만들거나 수정해야 하는가?                       │
│                                                         │
│  2. 범위 (Scope)                                        │
│     어느 파일·모듈에서 작업하는가?                         │
│                                                         │
│  3. 성공 기준 (Success Criteria)                         │
│     어떻게 하면 완료된 것인가?                             │
│                                                         │
│  4. 참조 정보 (Reference)                                │
│     관련 이슈, 파일, 문서는 무엇인가?                      │
│                                                         │
│  5. 제약 조건 (Constraints)                              │
│     사용하면 안 되는 것, 반드시 지켜야 하는 것은?           │
└─────────────────────────────────────────────────────────┘
```

### 1.2 최소형 vs 완성형 비교

**최소형 (권장하지 않음)**:
```
"사용자 로그인 API 만들어줘"
```

이 지시문은 다음 정보가 빠져 있다:
- JWT 방식인지 세션 방식인지 불명확
- 요청/응답 형식 불명확
- 어느 모듈에 추가할지 불명확
- 테스트 포함 여부 불명확

**완성형 (권장)**:
```
"apps/backend/src/auth 모듈에 JWT 기반 로그인 API를 구현해줘.

[목표]
POST /auth/login 엔드포인트를 만들어줘.

[요청 형식]
{
  "email": "string",
  "password": "string"
}

[응답 형식]
성공: 200 OK
{
  "accessToken": "JWT 토큰 (15분 만료)",
  "user": {
    "id": "number",
    "email": "string",
    "role": "ADMIN | USER"
  }
}
실패: 401 Unauthorized
{
  "message": "이메일 또는 비밀번호가 올바르지 않습니다"
}

[기술 요건]
- Passport.js LocalStrategy 사용
- 비밀번호: bcrypt 검증
- JWT: @nestjs/jwt 사용
- 토큰을 HttpOnly Secure 쿠키에 설정

[성공 기준]
- pnpm build 성공
- 단위 테스트 3개 이상 (성공 케이스 1, 실패 케이스 2)
- pnpm test 통과

[참조]
- docs/PRD.md의 AUTH-001 스펙
- 기존 UserService (apps/backend/src/user/user.service.ts)"
```

## 2. 효과적인 지시문 작성 원칙

### 원칙 1: "무엇을"이 아닌 "왜"부터 시작한다

에이전트는 목적을 이해하면 더 나은 구현을 선택한다.

```
❌ "갤러리 게시물에 thumbnailUrl 필드를 추가해줘"
✅ "갤러리 게시판에서 목록 화면에 이미지 미리보기를 보여주기 위해
    이미지 업로드 시 자동으로 썸네일을 생성하고 DB에 저장해줘.
    thumbnailUrl 필드를 Post 모델에 추가하고, 
    업로드 시 sharp 라이브러리로 200x200 리사이즈 후 저장해줘."
```

### 원칙 2: 범위를 명확히 제한한다

너무 광범위한 태스크는 실패하거나 예상치 못한 변경을 일으킨다.

```
❌ "인증 시스템을 만들어줘"

✅ "apps/backend/src/auth 모듈에만 집중해서 다음을 구현해줘:
    1. AuthModule 생성
    2. AuthController (POST /auth/login, POST /auth/logout)
    3. AuthService (validateUser, login, logout)
    4. JwtStrategy (Passport.js)
    
    다른 모듈(UserModule, PostModule 등)은 건드리지 않는다."
```

### 원칙 3: 성공 기준을 테스트 가능하게 작성한다

"잘 작동해야 한다"는 성공 기준이 아니다.

```
❌ "테스트를 작성해줘"
✅ "다음 테스트를 모두 작성해줘:
    - POST /auth/login with valid credentials → 200 + accessToken 반환
    - POST /auth/login with wrong password → 401 반환
    - POST /auth/login with non-existent email → 401 반환
    - POST /auth/login without email field → 400 반환
    Jest + Supertest 사용, 커버리지 90% 이상 달성"
```

### 원칙 4: 참조 파일을 구체적으로 명시한다

```
❌ "기존 코드 스타일을 따라줘"
✅ "apps/backend/src/user/user.service.ts와
    apps/backend/src/user/dto/create-user.dto.ts를 참조하여
    동일한 패턴으로 구현해줘"
```

### 원칙 5: 제약 조건을 명시한다

```
"주의 사항:
- 기존 UserModule을 변경하지 않는다
- 새 패키지 설치가 필요하면 사전에 알려준다
- Prisma 스키마를 변경하는 경우 마이그레이션도 함께 작성한다"
```

## 3. 10가지 태스크 유형별 지시문 패턴

### 패턴 1: 신규 기능 구현

```
"[기능명] 기능을 구현해줘.

[목적]
[이 기능이 왜 필요한지 비즈니스 이유]

[구현 위치]
- 백엔드: apps/backend/src/[module]/
- 프론트엔드: apps/frontend/src/routes/[path]/

[기능 상세]
1. [세부 기능 1]
2. [세부 기능 2]
3. [세부 기능 3]

[API 스펙] (백엔드 기능인 경우)
- Method: [GET|POST|PUT|DELETE]
- Path: /[path]
- Request: { ... }
- Response: { ... }

[데이터베이스] (DB 변경이 필요한 경우)
- 새 테이블: [테이블명] (필드 목록)
- 기존 테이블 수정: [테이블명]에 [컬럼명] 추가
- 마이그레이션 파일 생성 포함

[성공 기준]
- pnpm build 성공
- 단위 테스트 [N]개 이상
- pnpm test 통과"
```

**실제 예시 — 댓글 기능 구현**:
```
"board-hub 프로젝트에 댓글 기능을 구현해줘.

[목적]
게시물에 사용자가 댓글을 달 수 있도록 한다.

[구현 위치]
apps/backend/src/comment/ 모듈 신규 생성

[API 스펙]
POST /posts/:postId/comments
  요청: { content: string }
  응답: { id, content, author, createdAt }

GET /posts/:postId/comments
  응답: { comments: [...], total: number }

DELETE /comments/:id
  조건: 본인 댓글 또는 ADMIN만 삭제 가능

[데이터베이스]
prisma/schema.prisma에 Comment 모델 추가:
- id, content, authorId, postId, createdAt, updatedAt, deletedAt

마이그레이션 파일 생성 필수

[성공 기준]
- 빌드 성공
- 댓글 CRUD 테스트 5개 이상
- pnpm test 통과"
```

### 패턴 2: 버그 수정 (Issue 연동)

```
"GitHub Issue #[번호]를 수정해줘.

[이슈 설명]
[이슈 제목 및 내용 요약]

[재현 방법]
1. [재현 단계 1]
2. [재현 단계 2]
3. [발생하는 오류]

[예상 동작]
[정상적으로 동작해야 하는 결과]

[의심 위치]
[버그가 있을 것으로 의심되는 파일/함수]

[성공 기준]
- 위의 재현 방법으로 더 이상 오류가 발생하지 않음
- 회귀 테스트 추가 (동일 버그가 재발하지 않도록)
- 빌드 + 테스트 통과"
```

**실제 예시 — 썸네일 버그**:
```
"GitHub Issue #42를 수정해줘.

[이슈 설명]
갤러리 게시판에 이미지를 업로드할 때 썸네일이 생성되지 않는 버그.
thumbnailUrl이 항상 null로 저장된다.

[재현 방법]
1. 갤러리 게시판에 로그인
2. POST /posts 에 이미지 파일 첨부하여 요청
3. 응답의 thumbnailUrl이 null

[예상 동작]
thumbnailUrl에 /uploads/thumbs/[파일명] 경로가 저장되어야 함

[의심 위치]
apps/backend/src/file/file.service.ts의 generateThumbnail() 함수

[성공 기준]
- 이미지 업로드 후 thumbnailUrl에 값이 저장됨
- 회귀 테스트: 이미지 업로드 후 thumbnailUrl 검증 테스트 추가"
```

### 패턴 3: 리팩터링

```
"[파일/모듈명]을 리팩터링해줘.

[현재 문제점]
1. [문제 1: 중복 코드 등]
2. [문제 2: 너무 긴 함수 등]

[목표]
- [리팩터링 후 달성하려는 상태]

[범위 제한]
- 변경 파일: [파일 목록]
- 변경하지 않을 파일: [파일 목록]
- 기능 변경 없음 (동작은 동일해야 함)

[성공 기준]
- 기존 테스트가 모두 통과해야 함 (동작 변경 없음 증명)
- 코드 줄 수 [N]% 감소
- 함수 하나당 [N]줄 이하"
```

### 패턴 4: 테스트 작성

```
"[모듈명]의 테스트를 작성해줘.

[대상 파일]
apps/backend/src/[module]/[module].service.ts

[필요한 테스트 케이스]
1. [메서드명]
   - 성공 케이스: [설명]
   - 실패 케이스 1: [설명]
   - 실패 케이스 2: [설명]

2. [메서드명 2]
   - [테스트 케이스 목록]

[테스트 도구]
- Jest + @nestjs/testing
- Prisma Mock: jest.fn()으로 모킹
- 외부 서비스 Mock: jest.spyOn()

[성공 기준]
- 커버리지 [N]% 이상
- 모든 테스트 통과"
```

### 패턴 5: 문서화

```
"[모듈명]의 API 문서를 자동 생성되도록 설정해줘.

[도구]
- NestJS Swagger (@nestjs/swagger)

[추가할 내용]
- 모든 Controller 메서드에 @ApiOperation 추가
- 모든 DTO에 @ApiProperty 추가
- 에러 응답 @ApiResponse 추가

[형식]
- 한국어 설명
- 예시 요청/응답 포함

[파일 위치]
apps/backend/src/[module]/ 내의 모든 파일"
```

### 패턴 6: 데이터베이스 마이그레이션

```
"Prisma 마이그레이션을 작성해줘.

[변경 내용]
[테이블명] 테이블에 다음 컬럼 추가:
- [컬럼명]: [타입] ([제약조건])

[Prisma 스키마 변경]
model [ModelName] {
  // 기존 필드들
  [새 필드]: [타입] [속성]
}

[마이그레이션 이름]
add_[column]_to_[table]

[주의사항]
- 기존 데이터 처리: 기본값 [값]으로 설정
- down 마이그레이션 불필요 (Prisma는 up만 지원)

[성공 기준]
- pnpm prisma migrate dev 성공
- 기존 테스트 모두 통과"
```

### 패턴 7: 코드 리뷰

```
"PR #[번호]를 리뷰해줘.

[리뷰 포인트]
1. TypeScript 타입 안전성
2. 보안 취약점 (SQL 인젝션, XSS, IDOR)
3. 성능 문제 (N+1 쿼리, 불필요한 루프)
4. AGENTS.md 규칙 준수 여부
5. 테스트 커버리지 충분성

[결과 형식]
- 치명적 문제: 반드시 수정 필요
- 개선 권장: 수정하면 더 좋음
- 정보: 참고만 함

[주의]
코드를 수정하지 말고, 리뷰 코멘트만 작성해줘."
```

### 패턴 8: 보안 점검

```
"apps/backend/src/[module]/ 의 보안을 점검해줘.

[점검 항목]
- SQL 인젝션 취약점
- 인증/인가 누락
- 민감 데이터 로깅
- 입력값 검증 누락
- 레이트 리미팅 미적용

[취약점 발견 시]
즉시 수정하고 수정 내용을 PR 설명에 포함해줘.

[성공 기준]
- 발견된 모든 취약점 수정 완료
- 보안 관련 테스트 추가"
```

### 패턴 9: 성능 최적화

```
"[엔드포인트/모듈]의 성능을 최적화해줘.

[현재 문제]
- [현재 응답 시간]: [N]ms
- [문제 원인 예상]: N+1 쿼리, 불필요한 데이터 로드 등

[최적화 목표]
- 응답 시간 [N]ms 이하

[허용 방법]
- Prisma include 최적화
- 인덱스 추가
- Redis 캐싱 (있는 경우)

[불허 방법]
- Raw SQL (Prisma.sql 제외)
- 기능 제거로 인한 성능 향상

[성공 기준]
- 기존 테스트 모두 통과
- 동작 변경 없음"
```

### 패턴 10: 의존성 업그레이드

```
"[패키지명]을 [현재 버전]에서 [목표 버전]으로 업그레이드해줘.

[업그레이드 배경]
- 보안 취약점 수정 / 새 기능 필요

[Breaking Changes]
[버전 업그레이드 릴리즈 노트에서 확인한 주요 변경사항]
1. [변경사항 1]
2. [변경사항 2]

[작업 범위]
- package.json 버전 업데이트
- Breaking Change에 따른 코드 수정
- 테스트 통과 확인

[성공 기준]
- 모든 기존 테스트 통과
- 빌드 성공"
```

## 4. 태스크 결과 검토 방법

### 4.1 PR Diff 분석 체크리스트

```
파일 구조 확인
[ ] 의도한 파일만 변경되었는가?
[ ] 관련 없는 파일이 수정되지 않았는가?
[ ] 새 파일이 올바른 위치에 생성되었는가?

코드 품질 확인
[ ] TypeScript 타입이 적절히 정의되었는가?
[ ] any 타입이 사용되지 않았는가?
[ ] JSDoc 주석이 있는가?
[ ] 에러 처리가 적절한가?

기능 정확성 확인
[ ] 요청한 기능이 모두 구현되었는가?
[ ] API 요청/응답 형식이 명세와 일치하는가?
[ ] 엣지 케이스가 처리되었는가?

테스트 확인
[ ] 테스트 파일이 포함되었는가?
[ ] 성공 케이스 테스트가 있는가?
[ ] 실패 케이스 테스트가 있는가?
[ ] 테스트가 의미 있는가? (trivial 테스트는 커버리지만 채움)

보안 확인
[ ] 민감 데이터가 하드코딩되지 않았는가?
[ ] 입력값 검증이 있는가?
[ ] 인증/인가가 올바르게 적용되었는가?
```

### 4.2 PR Diff 읽는 방법

```
GitHub PR → Files changed 탭에서:

1. 먼저 Overview를 읽는다
   - 변경된 파일 수
   - 추가·삭제된 줄 수

2. 핵심 파일부터 리뷰한다
   - service 파일 (비즈니스 로직)
   - controller 파일 (API 정의)
   - spec 파일 (테스트)

3. 지원 파일을 확인한다
   - module 파일 (의존성 주입)
   - dto 파일 (입력 검증)
   - schema.prisma (DB 변경)
```

### 4.3 AI가 생성한 코드에서 자주 발견되는 문제

```
1. 환각 (Hallucination)
   - 존재하지 않는 라이브러리 API 사용
   - 실제로 없는 메서드 호출
   → 해결: 공식 문서와 대조 확인

2. 불필요한 변경
   - 관련 없는 파일 수정
   - 스타일만 변경하여 diff를 늘림
   → 해결: 변경 이유를 PR 코멘트로 질의

3. 테스트 껍데기
   - test('동작한다', () => { expect(true).toBe(true); })
   → 해결: 실제 기능을 테스트하는지 확인

4. 과도한 추상화
   - 단순한 기능에 불필요한 인터페이스 추가
   → 해결: YAGNI 원칙 언급하여 재요청

5. 의존성 과다 설치
   - 필요 없는 패키지 추가
   → 해결: 설치된 패키지 목적 확인 후 제거 요청
```

## 6. 멀티 게시판 프로젝트 실전 태스크 5개

### 실전 태스크 1: 사용자 인증 모듈 구현

```
"board-hub 프로젝트에 JWT 기반 인증 모듈을 구현해줘.

[구현 위치]
apps/backend/src/auth/ 모듈 신규 생성

[구현 API]
1. POST /auth/register
   요청: { email, password, username }
   응답: { user: { id, email, username, role }, message }
   
2. POST /auth/login
   요청: { email, password }
   응답: { accessToken } + HttpOnly 쿠키 설정
   
3. POST /auth/logout
   응답: HttpOnly 쿠키 삭제
   
4. GET /auth/me (인증 필요)
   응답: { id, email, username, role }

[기술 요건]
- Passport.js LocalStrategy + JwtStrategy
- bcrypt (salt rounds 12)
- JWT 만료: accessToken 15분
- HttpOnly Secure 쿠키 사용
- UserModule과 연동 (User 조회용)

[데이터베이스]
prisma/schema.prisma의 User 모델 사용 (이미 정의됨 가정)

[성공 기준]
- 회원가입 → 로그인 → /auth/me 플로우 E2E 테스트
- 단위 테스트: validateUser, login, logout
- 빌드 + 테스트 모두 통과"
```

### 실전 태스크 2: 게시판 CRUD API

```
"board-hub 프로젝트에 게시판 관리 API를 구현해줘.

[구현 위치]
apps/backend/src/board/ 모듈 신규 생성

[구현 API]
1. GET /boards
   응답: 전체 게시판 목록 (id, name, type, description)
   인증: 불필요 (공개)
   
2. GET /boards/:boardId
   응답: 단일 게시판 상세 (위 + createdAt)
   인증: 불필요
   
3. POST /boards (ADMIN 전용)
   요청: { name, type, description }
   type: GENERAL|GALLERY|VIDEO|QNA|NOTICE|FAQ|PRIVATE|FREE
   응답: 생성된 게시판
   인증: JWT + ADMIN Role
   
4. PATCH /boards/:boardId (ADMIN 전용)
   요청: { name?, description? }
   
5. DELETE /boards/:boardId (ADMIN 전용)
   응답: soft delete (deletedAt 설정)

[데이터베이스]
prisma/schema.prisma에 Board 모델 추가:
model Board {
  id          Int          @id @default(autoincrement())
  name        String
  type        BoardType
  description String?
  isActive    Boolean      @default(true)
  createdAt   DateTime     @default(now())
  updatedAt   DateTime     @updatedAt
  deletedAt   DateTime?
  posts       Post[]
}
enum BoardType {
  GENERAL GALLERY VIDEO QNA NOTICE FAQ PRIVATE FREE
}

[성공 기준]
- 전체 CRUD 테스트 (ADMIN 권한 포함)
- 비로그인 사용자의 ADMIN API 접근 시 401 반환 테스트
- 일반 사용자의 ADMIN API 접근 시 403 반환 테스트
- 마이그레이션 실행 성공
- 빌드 + 테스트 통과"
```

### 실전 태스크 3: 파일 업로드 모듈

```
"board-hub 프로젝트에 파일 업로드 기능을 구현해줘.

[구현 위치]

[구현 API]
POST /files/upload

[데이터베이스]

[성공 기준]
```
